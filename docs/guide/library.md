# API Server Library (Rust, C, Python)

[← Documentation index](README.md) · [日本語](ja/library.md)

Besides being a reverse proxy, veil can be embedded in your own program as a **library** for writing API
servers. You register ordinary functions as HTTP handlers (or TCP/UDP handlers), and veil's network layer —
io_uring, TLS, kTLS, HTTP/1.1, HTTP/2, HTTP/3, hot reload, sandboxing — does the rest.

Three front ends share the same implementation:

| Front end | Where | Typical use |
|-----------|-------|-------------|
| Rust library | the `veil` crate with the `api` feature set | the fastest option; macros, OpenAPI, tower, gRPC, any GraphQL library |
| C API | [`crates/veil-capi`](../../crates/veil-capi/README.md) (`libveil.so` / `libveil.a`, `veil.h`) | C, C++ and any language with a C FFI |
| Python | [`crates/veil-python`](../../crates/veil-python/README.md) (wheel, `import veil`) | FastAPI-style decorators |

## Architecture

- A handler is registered as a `type = "Handler"` route in veil's normal routing table. The library injects
  `[[route]]` entries into the configuration while it is loaded, so handlers coexist with `File`, `Proxy`
  and other route types you write in `config.toml`.
- **Handlers run on veil's own runtime.** Each `async fn` handler is polled on the worker thread that accepted
  the connection, on the same io_uring (or epoll/kqueue) event loop that serves the connection. The data
  plane has no tokio or monoio. tokio-based libraries (hyper, reqwest, sqlx, ...) run on the same workers through
  veil's tokio-free tokio compatibility layer ([tokio compatibility](#tokio-compatibility)).
- Blocking work must not run on a worker. A **synchronous** `fn` handler (Rust), a C callback and a Python
  handler are executed on a separate handler thread pool (`[api] handler_threads`) through veil's `offload`,
  so a slow database call does not stall other connections.
- **The release binary contains no library code.** The `handler`, `macro`, `openapi`, `tokio-compat`,
  `tokio-compat-bridge`, `l4-handler`, `grpc-handler`, `api-core` and `api` features are in neither `default` nor `full*`. `cargo build --features full`
  produces exactly the same proxy as before.
- Everything that works for the proxy still works: the `[server]`, `[tls]`, `[security]`, `[logging]`,
  `[prometheus]`, ... sections, SIGHUP reload, graceful shutdown (SIGINT/SIGTERM or `veil::shutdown()`).

## Depending on veil

### Cargo features

| Feature | Adds |
|---------|------|
| `handler` | native `Handler` routes, `Request`/`Response`, configuration builder, library default configuration (implies `http2`) |
| `macro` | `#[veil::route]`, `#[veil::main]`, `#[veil::l4_handler]`, `#[derive(veil::Schema)]` (implies `handler`) |
| `openapi` | OpenAPI 3.1 generation, `/openapi.json` and Swagger UI (implies `macro`) |
| `tokio-compat` | tokio-free tokio compatibility layer (`veil::tokio`, `App::tokio_service`, [`veil::api::tokio_compat`]); see [tokio compatibility](#tokio-compatibility) |
| `tokio-compat-bridge` | the alternative to `tokio-compat`: bundles a real tokio runtime and runs futures on it (mutually exclusive with `tokio-compat`) |
| `l4-handler` | Rust functions as TCP/UDP handlers on `[[l4]]` listeners (implies `l4-proxy`) |
| `grpc-handler` | gRPC server; messages are encoded by a codec you choose (prost through `veil-build`) ([`veil::api::grpc`], see [gRPC](#grpc)) (implies `handler`, `grpc`) |
| `api-core` | `handler`, `macro`, `openapi`, `l4-handler`, `grpc-handler` and tower `Layer`/`Service` compatibility ([`veil::api::tower`]) |
| `api` | `api-core` + `tokio-compat` (the default way to use the library) |

To use the tokio bridge instead, select `features = ["full", "api-core", "tokio-compat-bridge"]`. Enabling both
`tokio-compat` and `tokio-compat-bridge` is a compile error.

`vds` and `acme` are separate, are part of `full*`, and work in the proxy binary and the library alike
(see [VDS](vds.md) and [ACME](acme.md)).

### Cargo.toml

The crate is published on crates.io as **`veil-proxy`** (the name `veil` belongs to another project). Keep the
dependency key `veil`: the library is called `veil`, and the code generated by the macros refers to `::veil::`.
Pick a feature set: `full` includes HTTP/3, kTLS, gRPC, WASM and the other proxy features, and `full-container` is
the variant for containers. Turn `default-features` off (see [Memory allocator](#memory-allocator) for how the
allocator is chosen). API reference: [docs.rs/veil-proxy](https://docs.rs/veil-proxy).

```toml
[dependencies]
veil = { package = "veil-proxy", version = "0.8", default-features = false, features = ["full", "api"] }
# or the repository / a local checkout:
# veil = { package = "veil-proxy", git = "https://github.com/aofusa/veil-proxy", default-features = false, features = ["full", "api"] }
# veil = { package = "veil-proxy", path = "../veil-proxy", default-features = false, features = ["full", "api"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

Nothing else is needed — no `.cargo/config.toml` settings, also for HTTP/3 on Linux. quiche and rustls share
one `aws-lc-sys`; quiche calls it through `aws-lc-sys`'s Rust bindings, so the build works whether `aws-lc-sys`
uses its default symbol prefix or not. (An `AWS_LC_SYS_NO_PREFIX_<triple>` entry that you added for earlier
versions is harmless and can be removed.) Building `aws-lc-sys` needs a C compiler, CMake and libclang (bindgen).

The vendored quiche that packs STREAM frames of several streams into one packet (F-172) is a normal dependency
(`veil-proxy-quiche`), so no `[patch]` is needed.

A minimal feature set for plain HTTP APIs is `features = ["api"]` with `default-features = false` (no TLS,
no HTTP/3). `examples/api/rust-showcase` is a complete project that uses every feature.

### Minimal program

```rust
use veil::prelude::*;

#[veil::route(path = "/users/{id}", method = "GET")]
async fn get_user(id: u64) -> Json<serde_json::Value> {
    Json(serde_json::json!({ "id": id }))
}

#[veil::main]
async fn main() -> Result<(), veil::api::Error> {
    veil::serve(Config::load()?).await
}
```

`veil::serve(config)` blocks the calling thread until shutdown. Without macros, use the `App` builder:

```rust
use veil::prelude::*;

fn main() -> Result<(), veil::api::Error> {
    App::new()
        .get("/hello", |_req: Request| async { "hello" })
        .post("/echo", |req: Request| async move { req.body().clone() })
        .run()
}
```

`App` offers `get/post/put/delete/patch`, `route(&[methods], path, f)`, `route_blocking(...)` (runs on the
handler pool), `state(value)`, `config(cfg)`, `without_macro_routes()` and `on_setup(f)` (runs once before the
routes are registered).

## Configuration in library mode

The library has its own **default configuration** (embedded in the crate, `src/api/default_config.toml`):

```toml
[server]
listen_cleartext = "127.0.0.1:8080"  # plaintext HTTP/1.1 + h2c (prior knowledge), auto-detected; loopback only; no `listen`, no [tls]
enable_secure_redirect = false     # serve plaintext (the server default is a 301 to HTTPS)
http2_enabled = true

[logging]
level = "info"

[access_log]
enabled = true         # one line per request on standard output (the proxy binary's default is false)
format = "text"

[security]
enable_seccomp = false # do not restrict the host language / your code
enable_landlock = false

[api]
openapi_enabled = true
openapi_path = "/docs"
openapi_json_path = "/openapi.json"
openapi_title = "veil API"
openapi_version = "0.1.0"
```

plus `[server] threads` = the number of CPUs. So the server starts with no configuration file at all, speaks
plaintext HTTP/1.1 and h2c on `127.0.0.1:8080`, and needs **no TLS certificate** (`[tls]` may be omitted only in
this plaintext-only configuration; see [Configuration](configuration.md#plaintext-only-servers-without-tls)).

The default listener is bound to the **loopback address only**, so an application started without configuration
is not reachable from other hosts. To expose it (for example inside a container or behind a load balancer), set the
address explicitly: `listen_cleartext = "0.0.0.0:8080"` in `config.toml`, `.listen_cleartext("0.0.0.0:8080")` in
Rust, `veil_config_listen_cleartext(cfg, "0.0.0.0:8080")` in C, `veil.run(listen_cleartext="0.0.0.0:8080")` in
Python, or `VEIL_OVERRIDE_1='server.listen_cleartext = "0.0.0.0:8080"'`.

### Access log

In library mode every request is logged to **standard output** by default, as one `text` line
(`timestamp=… type=access method=… path=… status=… duration_ms=…`), next to the application log. Lines are
written by a background thread and flushed every `flush_interval_ms` (default 1000 ms), so they can appear up to
one second after the response.

- Turn it off: `[access_log] enabled = false` in `config.toml`, `.set("access_log.enabled = false")?` on the
  builder, `VEIL_OVERRIDE_1='access_log.enabled = false'`, or the same override from Python
  (`veil.run(...)` reads `VEIL_OVERRIDE_<n>`) and C.
- JSON or a file: `format = "json"`, `file_path = "/var/log/app/access.log"`, `fields = [...]` — the keys are the
  proxy's [`[access_log]`](observability.md) keys.
- Logging costs some throughput per request; turn it off when you benchmark against servers that do not log.

### Sources and precedence

The configuration is composed, lowest to highest priority:

1. the library default configuration above;
2. `config.toml` in the current directory, if it exists (`Config::load()` / `App::new()`), or the file given to
   `Config::from_file(path)`, or the string given to `Config::from_toml_str(..)`. The file is deep-merged over
   the defaults, so you only write the keys you want to change;
3. environment overrides `VEIL_OVERRIDE_<n>` (same rules as the proxy, see
   [Running](running.md#configuration-override-via-environment-variables-veil_override_n));
4. overrides set in Rust code with the builder (`ConfigBuilder`).

Then the handler routes and the built-in OpenAPI routes are injected, and all routes are sorted by specificity
(see [Routing macros](#routing-macros)).

The same composition runs again on every SIGHUP reload, so builder and environment overrides **survive a
reload**; only the contents of `config.toml` are re-read. `[server] listen` / `listen_cleartext`, `[tls]`, `[[l4]]` and the thread
count still cannot change without a restart (same as the proxy).

### Builder

```rust
let config = Config::load()?            // or Config::new() (defaults only), Config::from_file("app.toml")?
    .builder()
    .listen_cleartext("0.0.0.0:8080")   // [server].listen_cleartext (exposes it; the default is 127.0.0.1:8080)
    .threads(4)                         // [server].threads
    .log_level("warn")                  // [logging].level
    .openapi_title("My API")            // [api].*
    .max_body_size(1 << 20)
    .set("security.enable_seccomp = true")?     // any key, same syntax as `--override`
    .build();
```

Typed setters: `listen_cleartext` (plaintext address), `listen` (TLS address), `allow_http`, `allow_h2c`, `secure_redirect`, `threads`, `http2_enabled`, `log_level`, `openapi_enabled`,
`openapi_path`, `openapi_json_path`, `openapi_title`, `openapi_version`, `max_body_size`, `handler_threads`,
`grpc_max_message_size`, `grpc_response_compression`, `grpc_response_compression_min_size`, `tls(cert, key)` and `http3(listen)`. `set("key = value")` and `set_value(path, toml_value)` reach every other
key. `Config::to_toml_string()` returns the composed result (before environment overrides and route injection)
for debugging.

### `[api]` keys (library only)

`[api]` is read only in library mode; the proxy binary does not know it.

| Key | Default | Description |
|-----|---------|-------------|
| `openapi_enabled` | `true` | publish `/openapi.json` and the Swagger UI |
| `openapi_path` | `"/docs"` | Swagger UI path (loads `swagger-ui-dist` from unpkg.com in the browser) |
| `openapi_json_path` | `"/openapi.json"` | OpenAPI document path |
| `openapi_title` | `"veil API"` | `info.title` |
| `openapi_version` | `"0.1.0"` | `info.version` (your API's version) |
| `openapi_description` | none | `info.description` |
| `max_body_size` | `10485760` | maximum request body handed to a handler, in bytes |
| `handler_threads` | `0` | threads of the handler pool used for synchronous Rust fns, C callbacks and Python handlers (`0` = built-in default) |
| `tokio_threads` | `2` | worker threads of the bundled tokio runtime (`tokio-compat-bridge` only) |
| `grpc_max_message_size` | `4194304` | maximum size of one received gRPC message (`grpc-handler`) |
| `grpc_max_send_message_size` | `0` | maximum size of one sent gRPC message (0 = no limit) |
| `grpc_response_compression` | `"none"` | compress gRPC response messages: `"none"`, `"gzip"` or `"deflate"` (only when the client lists it in `grpc-accept-encoding`; needs the `compression` feature) |
| `grpc_response_compression_min_size` | `1024` | gRPC response messages smaller than this many bytes are not compressed |
| `grpc_web_cors_origins` | `[]` | origins allowed to call gRPC methods with gRPC-Web from a browser (`["*"]` for any); empty sends no CORS headers and rejects preflights with 403 |

## Routing macros

```rust
#[veil::route(path = "/users/{id}", method = "GET", tags = ["users"], summary = "Get a user")]
async fn get_user(id: u64, verbose: Option<bool>) -> Result<Json<User>, ApiError> { ... }
```

| Argument | Meaning |
|----------|---------|
| `path` (required) | path pattern: `{name}` is one segment (non-empty), a trailing `{*name}` captures the rest (may be empty); other segments are exact |
| `method = "GET"` / `methods = ["GET", "POST"]` | allowed methods; omit for all. A `GET` route also answers `HEAD` |
| `name` | handler name (default: the function name); must be unique |
| `tags`, `summary`, `description` | OpenAPI metadata (doc comments are used when `summary`/`description` are absent) |
| `status = 201` | default success status for OpenAPI |
| `offload = true/false` | run on the handler pool; default `true` for a sync `fn`, `false` for `async fn` |
| `hidden = true` | leave the route out of the OpenAPI document |

### Arguments (FastAPI style)

Arguments are bound by type and name:

| Argument | Source |
|----------|--------|
| `&Request` / `Request` | the whole request |
| `Json<T>` | JSON body |
| `Query<T>` | the whole query string deserialized into `T` |
| `Form<T>` | `application/x-www-form-urlencoded` body |
| `State<T>` | shared state registered with `App::state` |
| `Headers`, `Bytes` (alias `Body`) | request headers / raw body |
| a name that matches `{name}` in the path | path parameter, parsed with `FromStr` |
| any other plain type | query parameter; `Option<T>` makes it optional |

Failures to bind (missing, unparsable) and failed validation return **422** in FastAPI's format (see below).

### Ordering and conflicts

`first-match` routing would make route order significant, so the library sorts all routes (macros, `App`, and
`[[route]]` written in `config.toml`) by specificity, most specific first: more path segments, then more static
segments, then exact over prefix/catch-all, then routes with a method condition, then more `host`/`header`/
`query`/`source_ip` conditions; equal routes keep declaration order. `/users/me` beats `/users/{id}`, which
beats `/users/{*rest}`.

Two routes with the **same** host, normalized path (parameter names are ignored) and other conditions, and
overlapping methods (or both without methods) make the later one unreachable; that is a **startup error**
listing both. A path in `config.toml` that points at a handler by name (`type = "Handler"`, `handler = "get_user"`)
replaces the automatically injected route for that handler, so you can add `[route.security]` and other
route settings to it.

> Handler paths are exact matches. A static `path` in a TOML `[[route]]` is a segment-boundary prefix match.

## Request, Response and errors

`Request` gives `method()`, `path()`, `query()`, `query_param(name)`, `header(name)`, `headers()`, `body()`
(`&Bytes`), `text()`, `json::<T>()`, `param(name)`, `param_as::<T>(name)`, `client_ip()`, `version()`
(HTTP/1.1, 2 or 3) and `state::<T>()`.

A handler may return anything that implements `IntoResponse`:

| Return type | Response |
|-------------|----------|
| `&'static str`, `String` | 200 `text/plain` |
| `Html<T>` | 200 `text/html` |
| `Json<T>` (`T: Serialize`), `serde_json::Value` | 200 `application/json` |
| `Bytes`, `Vec<u8>` | 200 binary |
| `()` | 204 |
| `(u16, T)` | status override, e.g. `(201, Json(..))` |
| `Option<T>` | `None` is 404 |
| `Result<T, E>` | both sides are `IntoResponse` |
| `Response` | full control: `Response::new(status)`, `Response::json(&v)`, `.with_status()`, `.with_header()`, `.with_body()` |
| `ApiError` | `{"detail": "message"}` with the given status |

`ApiError::new(status, msg)`, `bad_request`, `not_found` and `internal` are meant for `?`; a `serde_json::Error`
converts to a 400 `ApiError`.

### Streaming bodies and trailers

`Response::stream(status, stream)` sends the body as it is produced: the stream yields `BodyChunk::Data(bytes)`,
optionally ends with `BodyChunk::Trailers(fields)`, and `BodyChunk::Abort(reason)` stops it midway. HTTP/1.1 uses
chunked encoding (trailers after the last chunk, abort closes the connection), HTTP/2 sends DATA frames and a
trailing HEADERS frame (abort is RST_STREAM), and HTTP/3 sends the same (abort resets the stream). Chunks that are
already available are merged up to 16 KiB per frame. For `HEAD` the stream is dropped without being polled.

A route that needs the request body as it arrives sets `streaming = true` (`#[veil::route(..., streaming = true)]`
or `App::route_fn_streaming`) and reads it with `req.take_body_stream()` (a `Stream<Item = Bytes>`). Over HTTP/2
the handler runs as soon as the headers arrive and request and response flow in both directions at once; over
HTTP/1.1 and HTTP/3 the body is read first and handed over as one chunk. `max_body_size` does not apply to a
streaming route over HTTP/2 (limit it while reading). Both directions pass through tower layers unchanged.

```rust
#[veil::route(path = "/upper", method = "POST", streaming = true)]
async fn upper(req: &Request) -> Response {
    use futures::StreamExt;
    let body = req.take_body_stream()
        .map(|c| BodyChunk::Data(bytes::Bytes::from(c.to_ascii_uppercase())));
    Response::stream(200, body).with_header("content-type", "text/plain")
}
```

## Validation and OpenAPI

`#[derive(veil::Schema)]` implements a JSON Schema (`ApiSchema`) and a validator (`Validate`) for a struct or
enum. When a `Json<T>`, `Query<T>` or `Form<T>` argument's `T` derives it, the macro validates automatically.

```rust
#[derive(Deserialize, veil::Schema)]
struct CreateUser {
    /// Display name
    #[validate(length(min = 1, max = 50))]
    name: String,
    #[validate(range(min = 0, max = 150))]
    age: u32,
    #[validate(email)]
    email: Option<String>,
    #[schema(example = "https://example.com", description = "Home page")]
    #[validate(url)]
    home: Option<String>,
}
```

| Attribute | Effect |
|-----------|--------|
| `#[validate(range(min, max, exclusive_min, exclusive_max))]` | numeric bounds; also `minimum`/`maximum` in the schema |
| `#[validate(length(min, max, equal))]` | string / collection length; `minLength`/`maxLength` |
| `#[validate(email)]`, `#[validate(url)]` | simple format checks; `format` in the schema |
| `#[validate(nested)]` | validate the inner struct as well |
| `#[validate(custom = "path::to::fn")]` | `fn(&T) -> Result<(), impl Display>` |
| `#[schema(description, example, format, pattern)]` | schema metadata (doc comments also become `description`) |
| serde `rename`, `rename_all`, `default`, `skip`, `flatten` | respected when building the schema |

Unknown `#[validate(...)]` keys (such as `regex`) are accepted and ignored so the derive can be used next to the
`validator` crate.

### 422 format

Failures return status 422 with the same shape as FastAPI:

```json
{"detail": [
  {"type": "less_than_equal", "loc": ["query", "limit"], "msg": "Input should be less than or equal to 100"},
  {"type": "too_short", "loc": ["body", "name"], "msg": "Value should have at least 1 item(s)/character(s)"}
]}
```

`loc` starts with `path`, `query` or `body`, followed by the field path (array indices are numbers).
Typical `type` values: `missing`, `parsing`, `json_invalid`, `greater_than_equal`, `less_than_equal`,
`too_short`, `too_long`, `length`, `value_error`, `url_parsing`.

### OpenAPI and Swagger UI

With the `openapi` feature, an OpenAPI **3.1** document is generated once at startup (and on every reload) from
the macro metadata — paths, parameters, request bodies, response types inferred from the return type
(`Json<T>`, `Result<Json<T>, _>`, `(u16, Json<T>)`, strings), `components.schemas`, and the 422 response for
validated routes — and kept in memory; a request just returns the stored bytes. It is served at
`openapi_json_path` (`/openapi.json`) and a Swagger UI at `openapi_path` (`/docs`). Set `[api]
openapi_enabled = false` to turn both off.

## Shared state

```rust
struct Db { /* pool */ }

#[veil::route(path = "/items", method = "GET")]
async fn items(db: State<Db>) -> Json<Vec<String>> { ... }

App::new().state(Db::connect()?).run()?;
```

`State<T>` is an `Arc<T>`; values are frozen at startup and read without locking. `veil::api::state::<T>()` and
`req.state::<T>()` read it outside extractors. Handlers run on several worker threads, so `T` must be
`Send + Sync` and use interior mutability (atomics, `Mutex`, ...).

## tower layers and tokio libraries

Requests and responses are exchanged as `http::Request<Full<Bytes>>` / `http::Response`.

```rust
App::new()
    // a tower Layer around every route; runs on veil's worker
    .layer(tower_http::set_header::SetResponseHeaderLayer::overriding(name, value))
    // only routes under /admin (segment-boundary prefix)
    .layer_on("/admin", RequireToken)
    // mount an existing tower Service (e.g. an axum Router)
    .tokio_service(&["GET", "POST"], "/legacy/{*rest}", axum_router)
    .run()?;
```

- `layer` / `layer_on` (`api-core`) wrap handlers inside veil's event loop.
- `tokio_service` (`tokio-compat` or `tokio-compat-bridge`) mounts a tower service. With `tokio-compat` it runs on
  the worker that accepted the request, like any handler; with `tokio-compat-bridge` it runs on the bundled tokio
  runtime and the result comes back through the same result-slot-plus-notification-fd mechanism as `offload`.
- Inside any handler, `veil::api::tokio_compat::run(fut)` runs a tokio-based future. With `tokio-compat` this is the
  same as `fut.await` (kept so the code does not change between the two features); with `tokio-compat-bridge` the
  future runs on the bundled runtime (`[api] tokio_threads` workers, default 2, started lazily).

  ```rust
  let body = veil::api::tokio_compat::run(async move {
      reqwest::get("https://example.com").await?.text().await
  }).await?;
  ```

  `run` panics (→ 500) if the task panicked; `try_run` returns `Result`; `spawn` starts a detached task and
  `handle()` returns the runtime handle.

## tokio compatibility

`tokio-compat` (part of `api`) implements tokio's public API on top of veil's own runtime **without depending on
tokio**. tokio-based crates (hyper, reqwest, sqlx, tower-http, ...) then run directly on veil's io_uring (or
epoll/kqueue) workers. Nothing changes in the data plane or in veil's runtime: the layer only uses the existing
runtime API, and it is not compiled into the proxy binary.

### Using it

Replace the `tokio` crate of the whole dependency tree with veil's shim (package name `tokio`, version 1.99.0,
which re-exports `veil::tokio`):

```toml
[dependencies]
veil = { package = "veil-proxy", version = "0.8", default-features = false, features = ["full", "api"] }
tokio = { version = "1", features = ["full"] }        # resolved to the shim
reqwest = "0.12"
sqlx = { version = "0.8", features = ["runtime-tokio", "postgres"] }

[patch.crates-io]
# the shim is not on crates.io (its package name is `tokio`), so it comes from the repository. Take veil from the
# same tag so that the shim and your code use one copy of veil (two copies would mean two runtimes).
tokio = { git = "https://github.com/aofusa/veil-proxy", tag = "v0.9.0", package = "tokio" }   # crates/veil-tokio/tokio-shim
veil-proxy = { git = "https://github.com/aofusa/veil-proxy", tag = "v0.9.0" }
```

Code that names `veil::tokio` directly (`use veil::tokio as tokio;`) works without the patch.
`#[tokio::main]` / `#[tokio::test]` start a veil runtime (current-thread or multi-thread flavor).

### How it differs from tokio

- **No work stealing.** A task runs on the thread that spawned it; `spawn` from a non-runtime thread through a
  `Handle` is forwarded to the runtime's thread. I/O objects are bound to the thread that created them. A server
  that accepts on one listener and spawns a task per connection (`axum::serve`, a hyper accept loop) therefore
  runs on one thread even on a multi-thread runtime; use one listener per thread with `SO_REUSEPORT` or mount the
  service in a veil `App` (see [Performance](#performance)).
- **Cross-thread wake-ups** (a `Sender` on another thread, `spawn_blocking`, a `Waker` sent elsewhere) are delivered
  to the owning thread through a notification fd; veil's own wakers are never called from another thread.
- `spawn_blocking`, `block_in_place` and `fs` run on veil's handler thread pool (`[api] handler_threads`).
- Supported: `task` (spawn, `JoinHandle`, `JoinSet`, `LocalSet`, `task_local!`, `yield_now`, cooperative budget,
  `unconstrained`), `time` (incl. `pause`/`advance`/`start_paused`), `io` (traits, utilities, `split`, `duplex`,
  `copy_bidirectional`, buffered I/O), `net` (TCP, UDP, Unix stream/datagram/listener, `AsyncFd`, `lookup_host`),
  `sync` (mpsc, oneshot, watch, broadcast, `Mutex`, `RwLock`, `Semaphore`, `Notify`, `Barrier`, `OnceCell`,
  `SetOnce`), `signal`, `fs`, `select!`/`join!`/`try_join!`/`pin!`, `runtime::{Runtime, Builder, Handle}`.
- Not supported: `process`, runtime metrics, task dumps/tracing hooks, io_uring-backed `fs`, Windows named pipes.
  On **Windows** (F-204), `net` has TCP, UDP and `lookup_host` (Unix sockets and `AsyncFd` are unix-only, as in
  tokio; `net::windows::named_pipe` exists so that crates referring to it build, but pipes cannot be opened), and
  `signal` has `ctrl_c` and `signal::windows::{ctrl_c, ctrl_break, ctrl_close, ctrl_logoff, ctrl_shutdown}`
  (`SetConsoleCtrlHandler`; an event nobody listens for goes on to the next handler, e.g. veil's own Ctrl-C shutdown).
  Crates that need these (or tokio's internals) should use `tokio-compat-bridge`.

## GraphQL

veil does not depend on a GraphQL library: you pick one (async-graphql, juniper, ...) and mount it as an ordinary
handler with `App::route_fn` (`GET` and `POST` on one path). The handler reads the query from `Request::body()` or
`Request::query()` and returns the result as JSON; subscriptions can be streamed as Server-Sent Events with
`Response::stream`.

[`examples/api/rust-graphql`](../../examples/api/rust-graphql/) does this for async-graphql in one file you can copy
(`src/graphql.rs`, about 100 lines):

```rust
mod graphql;   // copied from examples/api/rust-graphql/src/graphql.rs

let schema = Schema::build(QueryRoot, MutationRoot, SubscriptionRoot).finish();
graphql::graphql(App::new(), "/graphql", schema).run()?;
```

It serves `POST` with a JSON body (single or batch) and `GET` with `?query=...&variables=...`, GraphiQL for a browser
`GET` without a query (`Accept: text/html`), `application/graphql-response+json` when the client asks for it
(otherwise `application/json`), and subscriptions over SSE (GraphQL over SSE, distinct connections mode) when the
request has `Accept: text/event-stream`: one `event: next` per result and a final `event: complete`.

> Up to v0.7 the `graphql` feature provided `App::graphql(path, schema)`. It was removed (F-207) so that the API
> library does not pull in async-graphql; copy `src/graphql.rs` from the example to keep the same behaviour.

## gRPC

Requires `grpc-handler` (part of `api`). The wire handling (5-byte framing, `grpc-status`/`grpc-message` trailers,
`grpc-timeout`, gzip/deflate) is veil's own, and neither tokio nor tonic is used. veil does not depend on a protobuf
implementation either: messages are encoded and decoded by a **codec** (`veil::api::grpc::Codec<T>`) that you pass
when a method is registered. Code generated by `veil-build` uses [prost](https://docs.rs/prost) messages and a
generated `ProstCodec`; any other protobuf library, or JSON, works by implementing `Codec`. gRPC calls are ordinary handler routes (`POST /<package>.<Service>/<Method>`) on the same
listeners, over HTTP/2 (TLS or h2c) and HTTP/3.

### Code generation

Add `veil-build` as a build dependency and `prost` (0.13, the version `veil-build`'s prost-build generates code for)
as a dependency:

```rust
// build.rs
fn main() -> std::io::Result<()> {
    veil_build::compile_protos(&["proto/helloworld.proto"], &["proto"])
}
```

```rust
pub mod hello { veil::include_proto!("helloworld"); }
use hello::greeter_server::{add_greeter, Greeter};
use veil::api::grpc::{Request, Response, Status};

struct MyGreeter;
impl Greeter for MyGreeter {
    async fn say_hello(&self, req: Request<hello::HelloRequest>)
        -> Result<Response<hello::HelloReply>, Status> {
        Ok(Response::new(hello::HelloReply { message: format!("Hello {}", req.get_ref().name) }))
    }
}

add_greeter(App::new().grpc_health(), MyGreeter).run()
```

For each service `veil-build` generates a module `<service>_server` with a trait (one method per RPC; implement
them with `async fn`, the futures need not be `Send`), `add_<service>(app, impl)`, `METHODS` and `ProstCodec`
(the prost codec that `add_<service>` registers the methods with). Server and
bidirectional streaming methods return `Response<BoxStream<T>>`; client streaming and bidirectional methods receive
`Request<Streaming<T>>`. `veil_build::configure().veil_path("::my_veil")` changes the crate path and `config_mut()`
exposes the `prost_build::Config`.

### Without code generation

Register methods with a codec. A codec for prost messages (`#[derive(prost::Message)]`) is ten lines:

```rust
use veil::api::grpc::{Bytes, BytesMut, Codec, Request, Response, Status, Streaming};

#[derive(Clone, Copy)]
struct ProstCodec;
impl<T: prost::Message + Default + 'static> Codec<T> for ProstCodec {
    fn encode(&self, m: &T, out: &mut BytesMut) -> Result<(), Status> {
        m.encode(out).map_err(|e| Status::internal(e.to_string()))
    }
    fn decode(&self, buf: Bytes) -> Result<T, Status> {
        T::decode(buf).map_err(|e| Status::internal(e.to_string()))
    }
    fn encoded_len(&self, m: &T) -> usize { m.encoded_len() }   // optional: one allocation per message
}

App::new()
    .grpc_unary("/pkg.Svc/Get", ProstCodec, |req: Request<GetRequest>| async move { Ok(Response::new(reply)) })
    .grpc_server_streaming("/pkg.Svc/Watch", ProstCodec, |req: Request<WatchRequest>| async move {
        Ok(Response::new(futures::stream::iter(items.into_iter().map(Ok))))
    })
    .grpc_client_streaming("/pkg.Svc/Upload", ProstCodec, |req: Request<Streaming<Chunk>>| async move { .. })
    .grpc_bidi("/pkg.Svc/Chat", ProstCodec, |req: Request<Streaming<Msg>>| async move { .. })
```

`veil::api::grpc::BytesCodec` passes the encoded message through as `Bytes` (`Request<Bytes>`, `Response<Bytes>`),
for example to decode it yourself or to forward it.

> Up to v0.7 the methods took no codec and required prost messages, and `veil::api::grpc::prost` re-exported prost.
> Since F-208 code generated by `veil-build` registers `ProstCodec` itself (rebuild to update); hand-written
> registrations add a codec argument as above, and depend on `prost` directly.

### Types and behaviour

| Item | Behaviour |
|------|-----------|
| `Request<T>` | `get_ref()`, `into_inner()`, `metadata()` / `metadata_value(name)` (request headers except `content-type`, `te`, `grpc-timeout`, `grpc-encoding`), `deadline()`, `client_ip()` |
| `Response<T>` | `with_metadata(name, value)` (response headers), `with_trailer(name, value)` (after `grpc-status: 0`) |
| `Status` | `Status::new(Code::X, msg)` or `Status::not_found(msg)` etc., `with_metadata` adds trailers. An error before the first message is sent as a Trailers-Only response |
| Error details | `Status::with_details(bytes)` sends an encoded `google.rpc.Status` (with `BadRequest`, `ErrorInfo`, ...) as `grpc-status-details-bin`; encode it with the protobuf library you use |
| Interceptors | `App::grpc_interceptor(prefix, \|req: &Request<()>\| -> Result<(), Status>)` runs before every gRPC method under `prefix` (`"/"` or `"/pkg.Svc/"`) with the metadata, deadline, client address and `method()`; an `Err` ends the call with that status (authentication, quotas). Other requests on the same prefix pass through |
| Send limit | `[api] grpc_max_send_message_size` (default 0 = no limit): a larger response message ends the call with `RESOURCE_EXHAUSTED` |
| `Streaming<T>` | `Stream<Item = Result<T, Status>>` and `message().await` |
| Deadline | `grpc-timeout` is enforced with veil's timer: the handler is cancelled and the call ends with `DEADLINE_EXCEEDED` (for streams, checked between messages) |
| Cancellation | a client RST_STREAM / disconnect drops the handler future and the response stream |
| Compression | requests with `grpc-encoding: gzip` or `deflate` are decompressed (needs the `compression` feature, which `full` includes; without it only `identity` is accepted and other encodings get `UNIMPLEMENTED`); responses are compressed when `[api] grpc_response_compression` (or `Response::with_compression(Compression::Gzip)` for one call) names an encoding that the client accepts in `grpc-accept-encoding`, for messages of at least `grpc_response_compression_min_size` bytes; otherwise they are sent uncompressed |
| Size limit | `[api] grpc_max_message_size` (default 4 MiB) per received message, `RESOURCE_EXHAUSTED` when exceeded. For a compressed message the limit applies to the decompressed size, and decompression stops as soon as it is exceeded |
| gRPC-Web | `application/grpc-web`, `application/grpc-web+proto` and the base64 variants `application/grpc-web-text(+proto)` are served by the same methods, over HTTP/1.1, HTTP/2 and HTTP/3: the trailers come as the last frame of the body (flag `0x80`), so browsers (grpc-web, Connect) call veil directly without a translating proxy. `OPTIONS` preflights are answered from `[api] grpc_web_cors_origins` |
| Errors | `content-type` other than `application/grpc*` is 415; a gRPC call (not gRPC-Web) over HTTP/1.1 gets `grpc-status: 13`; an unknown method of a registered service, or a gRPC call to a path that no route serves, gets `UNIMPLEMENTED` |
| Health | `App::grpc_health()` registers `grpc.health.v1.Health` (`Check`, `Watch`); the whole server (`""`) is `SERVING`, `veil::api::grpc::health::set_serving_status(service, status)` changes a service |
| Reflection | `App::grpc_reflection(&[hello::greeter_server::FILE_DESCRIPTOR_SET])` registers `grpc.reflection.v1` and `v1alpha` (`ServerReflectionInfo`), so grpcurl, Postman and grpcui list the services and fetch their types without the `.proto` files. `FILE_DESCRIPTOR_SET` is generated by `veil-build`; pass one per compiled package. `list_services` reports every registered gRPC service; the types of the built-in health and reflection services are not described |

gRPC routes are not listed in OpenAPI. A complete example is `examples/api/rust-grpc` (unary, the three streaming
kinds, deadlines, errors, health), tested with a tonic client and an HTTP/3 client by
`tests/api/library_e2e.sh grpc`.

## L4 (TCP/UDP) handlers

Requires `l4-handler`. A `[[l4]]` listener with a `handler` key does not forward to upstreams; it passes each
TCP connection (or UDP datagram) to a Rust function. Listeners without `handler` keep the unchanged `splice(2)`
forwarding path. See also [L4 proxy](l4-proxy.md#native-handlers).

```rust
#[veil::l4_handler(name = "tcp_echo", protocol = "tcp")]
async fn tcp_echo(conn: &mut L4Connection) -> Result<(), L4Error> {
    let mut buf = [0u8; 4096];
    loop {
        let n = conn.read(&mut buf).await?;      // 0 = peer closed
        if n == 0 { return Ok(()); }
        conn.write_all(&buf[..n]).await?;
    }
}

#[veil::l4_handler(name = "udp_echo", protocol = "udp")]
async fn udp_echo(dgram: L4Datagram) -> Option<bytes::Bytes> {
    Some(dgram.data)                              // Some(..) is sent back to the sender
}
```

```toml
[[l4]]
name = "tcp_echo"
listen = "0.0.0.0:9000"
handler = "tcp_echo"        # no upstreams needed

[[l4]]
name = "udp_echo"
listen = "0.0.0.0:9001"
protocol = "udp"
handler = "udp_echo"
```

Without writing TOML, `App::l4_tcp(name, listen, f)` and `App::l4_udp(name, listen, f)` register the handler and
inject the `[[l4]]` entry (a `[[l4]]` with the same `name` in `config.toml` wins). `L4Connection` offers `read`,
`read_bytes`, `write`, `write_all`, `write_bytes` (zero-copy `Bytes`), `shutdown_write`, `peer_addr` and
`listener_name`; every operation is bounded by the listener's `idle_timeout_secs` (`L4Error::Timeout`). A handler
name that is missing or registered for the other protocol is a startup error. As for all `[[l4]]` listeners,
SIGHUP does not reload them.

## TLS and HTTP/3

The default is plaintext. To serve HTTPS (HTTP/1.1 + HTTP/2 via ALPN):

```rust
let config = Config::load()?.builder().listen("0.0.0.0:8443").tls("/etc/veil/cert.pem", "/etc/veil/key.pem").build();
```

`listen(addr)` is the TLS listener (`[server].listen`) and `tls()` sets `[tls] cert_path/key_path`; the library's default
plaintext listener (`listen_cleartext = "127.0.0.1:8080"`, loopback only) stays unless you change it. Move it with `listen_cleartext(..)`,
or make it redirect to the TLS port with `.secure_redirect(true)`. Add `.http3("0.0.0.0:8443")` (needs the `http3`
feature, included in `full`) for HTTP/3 on a UDP port (`[http3] enabled = true` + `[http3] listen`). All other `[tls]`, `[http2]`, `[http3]` and `[security]` keys can be set in `config.toml` or with
`set(..)`. The security sandbox is **off** by default in library mode; enabling `enable_seccomp` /
`enable_landlock` is possible but must allow whatever your handlers do (files, sockets, DNS).

## Memory allocator

When veil is used as a library (any build with the `handler` feature, which `api` includes), it does **not**
declare a `#[global_allocator]`: the application chooses. The allocator features (`veil-alloc` in `full`,
`mimalloc` in `default`) still compile the allocator code, so you can pick it explicitly in your binary:

```rust
// veil's own allocator (unix; `veil-alloc` is part of `full`)
#[cfg(unix)]
#[global_allocator]
static GLOBAL: veil::veil_alloc::VeilAlloc = veil::veil_alloc::VeilAlloc;

// or mimalloc (add the `mimalloc` crate to your dependencies)
// #[global_allocator]
// static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
```

Without any declaration the Rust system allocator is used (on Windows the example above falls back to it). The `veil` binary (built without `handler`) keeps
selecting its allocator as before. `examples/api/rust-showcase` declares `VeilAlloc`.

Allocator features are mutually exclusive (see [Memory allocators](performance.md#memory-allocators-f-183)).
The C and Python builds ([`veil-capi`](../../crates/veil-capi/README.md), [`veil-python`](../../crates/veil-python/README.md))
enable no allocator feature, so they never replace the allocator of the host process (a C program or the Python
interpreter). On Linux they are built on the epoll (readiness reactor) backend rather than io_uring; other systems
use their default reactor (kqueue, WSAPoll). They are built without the gRPC, WASM, VDS and ACME features.

## C API

`crates/veil-capi` builds `libveil.so` (dynamic) and `libveil.a` (static) and the header
[`veil.h`](../../crates/veil-capi/include/veil.h). A C callback is registered per route and called with a
request and a response object:

```c
#include "veil.h"

static int hello(const veil_request_t *req, veil_response_t *resp, void *ud) {
    return veil_response_set_text(resp, "Hello from C");
}

int main(void) {
    veil_config_t *cfg = veil_config_new();           /* or veil_config_from_file("config.toml") */
    veil_config_listen_cleartext(cfg, "0.0.0.0:8080");   /* plaintext, exposed (default 127.0.0.1:8080); TLS: veil_config_listen + veil_config_tls */
    veil_register_route(cfg, "/hello", "GET", hello, NULL);
    return veil_run(cfg);                              /* blocks; consumes cfg */
}
```

```bash
cargo build -p veil-capi --release      # target/release/libveil.so and libveil.a
gcc hello.c -Icrates/veil-capi/include -Ltarget/release -lveil -lpthread -ldl -lm \
    -Wl,-rpath,$PWD/target/release -o hello          # dynamic
gcc hello.c -Icrates/veil-capi/include target/release/libveil.a -lpthread -ldl -lm -o hello   # static
```

On other systems the dynamic library is `libveil.dylib` (macOS) or `veil.dll` + `veil.dll.lib` (Windows, MSVC),
and the system libraries for a static link differ (OpenBSD and NetBSD have no `libdl`, Windows needs `ws2_32.lib`
and others). Ask rustc for the list:
`cargo rustc -p veil-capi --release --crate-type staticlib -- --print native-static-libs`
(`examples/api/c-hello/Makefile` takes it as `LIBS=...`; `tests/api/library_e2e.sh` shows the MSVC command line).

**Threading.** By default the callback runs on the **handler pool** (`[api] handler_threads`), so it may block
(database, files), but it is called from **several threads at once** — protect shared data and make `user_data`
thread-safe. `veil_register_route_ex(..., VEIL_ROUTE_INLINE)` runs the callback on the network worker instead
(no thread hop); only use it for work that finishes immediately, because blocking stalls every connection of that
worker. Request accessors return non-NUL-terminated pointers valid until the callback returns. OpenAPI is
generated for C routes too (pass an Operation Object as JSON to `veil_register_route_ex` to describe them).
Settings are applied with `veil_config_set(cfg, "server.threads", "4")`, and `VEIL_OVERRIDE_<n>` works as usual.
Details (ownership table, error codes, API list): [crates/veil-capi/README.md](../../crates/veil-capi/README.md).
Example: [examples/api/c-hello/](../../examples/api/c-hello/).

**Streaming, gRPC and L4 (F-210).** The C API has the same features as the Rust one; veil only moves bytes, and
you serialize messages with the library of your choice (protobuf-c, nanopb, upb, ...):

- Streaming response: `veil_stream_t *s = veil_response_stream(resp)` sends the status and headers set so far and
  returns a handle that stays valid after the callback returns (another thread may keep writing);
  `veil_stream_write` (copies, waits when the queue is full, `VEIL_ERR_CLOSED` after the client left),
  `veil_stream_set_trailer`, and `veil_stream_close` (required; ends the body and frees the handle).
- Request body: `veil_request_body_read(req, buf, cap)` reads the next chunk (0 = end). With the route flag
  `VEIL_ROUTE_STREAM_BODY` the callback is called before the body has arrived and chunks are returned as they come.
- gRPC: `veil_register_grpc(cfg, "/pkg.Svc/Method", VEIL_GRPC_UNARY | ..._SERVER_STREAMING | ..._CLIENT_STREAMING | ..._BIDI, fn, ud)`;
  inside the callback `veil_grpc_recv` / `veil_grpc_send` (encoded message bytes), `veil_grpc_set_status`,
  `veil_grpc_set_header` / `_set_trailer`, `veil_grpc_metadata`, `veil_grpc_deadline_ms`.
  `veil_register_grpc_health(cfg)` adds `grpc.health.v1.Health`. Compression, deadlines, gRPC-Web and the
  `[api] grpc_*` keys behave as for Rust handlers; HTTP/2 and HTTP/3 both work.
- L4: `veil_register_l4_tcp(cfg, name, listen, &callbacks, ud)` with `on_connect` / `on_data` / `on_close`
  (called on the handler pool, one at a time per connection; `veil_l4_write` / `veil_l4_close` inside a callback),
  and `veil_register_l4_udp(cfg, name, listen, fn, ud)` (`veil_l4_reply` answers a datagram).
- Streaming functions cannot be used on `VEIL_ROUTE_INLINE` routes (`VEIL_ERR_STATE`).

Example of all of these: [examples/api/c-features/](../../examples/api/c-features/) (it passes the same tonic
interoperability checks as the Rust gRPC example).

## Python

`crates/veil-python` is a PyO3 extension (abi3, Python 3.9+) imported as `veil`:

```bash
pip install maturin
cd crates/veil-python && maturin develop --release     # or: maturin build --release   (wheel in target/wheels/)
pip install pydantic                                    # optional
```

```python
import veil

@veil.get("/hello/{name}")
def hello(name: str, greeting: str = "Hello"):          # name: path, greeting: query (typed by annotation)
    return {"message": f"{greeting}, {name}"}

@veil.post("/users", status_code=201,
           body_constraints={"name": {"type": "string", "minLength": 1, "required": True}})
def create_user(body: dict):
    return body

veil.run(listen_cleartext="0.0.0.0:8080")               # blocks (exposed; default 127.0.0.1:8080); Ctrl-C / SIGTERM stops gracefully
```

- Decorators: `@veil.get/post/put/delete/patch/route`, or `app = veil.App(title=..., version=...)` with
  `@app.get(...)` and `app.run()`. Arguments are bound by name and annotation, returns are converted
  (dict/list → JSON, `str` → text, `veil.Response`, `(body, status)`, `None` → 204), `veil.HTTPException(404, "...")`
  gives `{"detail": ...}`. With **pydantic** installed, `BaseModel` bodies are validated and described in OpenAPI;
  without it, `body_constraints` validates dict bodies. OpenAPI is served at `/openapi.json` and `/docs`.
- **offload and the GIL.** Handlers hold the GIL while they run. By default (`offload=True`) they run on the
  handler pool, so the event loop never waits for the GIL. `offload=False` runs on the network worker and is for
  trivially cheap handlers only. Pure-Python handlers are limited to the GIL's parallelism; for CPU-bound work use
  several processes.
- **Inside the server** a handler receives a Rust-backed request (`veil._veil.NativeRequest`, an instance of
  `veil.Request` for `isinstance`) with the same attributes and methods; attributes are created only when the
  handler reads them, and common return values (`str`, `bytes`, `dict`/`list`, `None`, `veil.Response`) are turned
  into the response in Rust without copying the body (F-212). `async def` handlers run on one event loop per
  handler-pool thread. Python 3.9 or later is required.
- **Streaming (F-210).** Return a generator or async generator (sent chunk by chunk as `text/plain`), a
  `veil.StreamingResponse(iterable, media_type=..., trailers=[...])`, or a `veil.EventSourceResponse(iterable)` for
  Server-Sent Events (items are strings, JSON-able values or `{"event", "data", "id", "retry"}` dicts).
  `@veil.post(..., stream_body=True)` calls the handler before the body has arrived; `for chunk in request.stream()`
  reads it as it comes (it also works in `async def` handlers, blocking the pool thread for each chunk).
- **gRPC (F-210)** in `veil.grpc`, with no dependency: `@veil.grpc.unary_unary("/pkg.Svc/Method",
  request_deserializer=Req.FromString, response_serializer=Resp.SerializeToString)` and `unary_stream`,
  `stream_unary`, `stream_stream` (the same argument names as grpcio, so any serializer works: protobuf,
  betterproto, JSON, or raw `bytes` when omitted). The `context` has the main methods of grpcio's
  `ServicerContext` (`abort`, `set_code`, `set_details`, `invocation_metadata`, `send_initial_metadata`,
  `set_trailing_metadata`, `time_remaining`, `is_active`). With `pip install veil-api[grpc]`, code generated by
  `grpc_tools.protoc` runs unchanged: pass `veil.grpc.Server()` to `add_<Service>Servicer_to_server`, then
  `server.add_insecure_port(...)` and `server.wait_for_termination()`. `veil.grpc.add_health()` adds
  `grpc.health.v1.Health`. `async def` methods and async generators work.
- **L4 (F-210):** `@veil.l4_tcp(name, listen)` on a `veil.Protocol` subclass (`connection_made` /
  `data_received` / `connection_lost`, like asyncio; `self.transport.write` inside a callback) and
  `@veil.l4_udp(name, listen)` on `def f(data, peer) -> bytes | None`.
- **GraphQL:** mount any library as an ordinary route; [examples/api/python-graphql/](../../examples/api/python-graphql/)
  uses strawberry (queries, mutations, and subscriptions over SSE).
- Configuration: `veil.run(config_path=None, *, listen_cleartext, listen, tls_cert, tls_key, threads, overrides={"server.threads": 4}, openapi=True)`;
  `VEIL_OVERRIDE_<n>` works as usual.

Full documentation (quickstart, FastAPI migration table, API reference): <https://veil-api.readthedocs.io>.
Details: [crates/veil-python/README.md](../../crates/veil-python/README.md). Examples:
[examples/api/python-hello/](../../examples/api/python-hello/),
[examples/api/python-fastapi-like/](../../examples/api/python-fastapi-like/),
[examples/api/python-features/](../../examples/api/python-features/) (streaming, L4),

## Performance

Measured with [tools/api-bench](../../tools/api-bench/README.md): the same two endpoints (`GET /plaintext` →
`Hello, World!`, `GET /json/{name}` → `{"message":"Hello, <name>"}`) in each framework, HTTP/1.1 keep-alive,
`wrk -t2 -c64 -d10s`, 3 rounds alternating the order of the targets, median. The server runs on one physical core
(2 hyperthreads, CPUs 0-1, 2 server threads / workers) and wrk on the other (CPUs 2-3) of an Intel i5-3320M
(2 cores / 4 threads, 2012 laptop), so the absolute numbers are small; compare the ratios. "CPU µs/req" is the busy
time of the server's cores (including the kernel's loopback processing) divided by the requests. Raw data:
`docs/artifacts/api_bench_{rust,python}.tsv` after running the script.

### Rust: axum on tokio, axum on `veil::tokio`, veil handlers

| Target | plaintext req/s | json req/s | p99 ms (plaintext) | CPU µs/req (plaintext) | RSS MB |
|---|---:|---:|---:|---:|---:|
| axum + tokio, `axum::serve` | 66,061 | 59,630 | 1.50 | 30.6 | 5.3 |
| axum + tokio, per-core (`SO_REUSEPORT`) | 67,811 | 62,077 | 1.34 | 29.8 | 5.0 |
| axum + `veil::tokio`, `axum::serve` | 38,218 | 35,099 | 2.27 | 28.1 | 8.7 |
| axum + `veil::tokio`, per-core | 54,491 | 49,930 | 1.48 | 37.2 | 8.2 |
| axum + `veil::tokio`, per-core (epoll) | 56,607 | 52,010 | 1.35 | 35.8 | 7.0 |
| veil `App` + axum `Router` (`tokio_service`) | 49,960 | 46,013 | 3.37 | 41.5 | 12.0 |
| veil `App` + axum `Router` (epoll) | 46,905 | 44,225 | 3.34 | 44.0 | 9.8 |
| veil native handler (`#[veil::route]`) | 68,832 | 63,069 | 2.83 | 29.4 | 11.4 |
| veil native handler (epoll) | 67,013 | 61,303 | 2.78 | 30.2 | 10.0 |

The `App` + `Router` rows were measured after F-202 (handler path: 14 → 4 allocations per request, the response head
and a small body written at once), in the same alternating run as axum + tokio per-core at 68,343 / 61,675 req/s;
before F-202 they were 33,349 / 36,702 req/s. The two native rows were re-measured after F-205 (5 alternating rounds
against axum + tokio per-core at 66,980 / 61,184 req/s in the same run; `docs/artifacts/f206_final_h1.tsv`).

- **axum runs on `veil::tokio` unchanged** (the same source, with the `tokio` crate patched to the shim). Per core it
  reaches about **80% (io_uring) to 84% (epoll)** of axum on tokio, and uses 20–25% more CPU per request.
- **`axum::serve` on a multi-thread `veil::tokio` runtime uses only one thread**: there is no work stealing, so every
  connection task stays on the thread that accepted it (the server cores are only ~85% busy out of 200%). For
  multi-core use, run one current-thread runtime and one `SO_REUSEPORT` listener per thread (the "per-core" rows,
  `run_percore` in `tools/api-bench/common.rs`), or mount the router in a veil `App`, whose workers each accept.
- **veil's native handler reaches 103% (io_uring) / 100% (epoll) of axum on tokio** for both endpoints, with less or
  equal CPU per request (29.4 / 30.2 µs against 30.5 µs). On io_uring a keep-alive connection that sends its next
  request quickly is read with one bounded `RECV` instead of a readiness poll followed by a read (F-205,
  `[performance] keepalive_direct_read_ms`); idle connections still hold no read buffer. Mounting an axum `Router`
  adds a conversion to and from `http::Request`/`http::Response`. Since F-235 the conversion shares the request's
  path and header values (`Bytes`) instead of copying them, takes the response body without collecting it into a
  queue, and no longer puts the veil `Request` into the extensions of a mounted service: 30 → 22 allocations per
  request (the native handler: 4), and the mount went from 67% to 76% of the native handler (49,960 against
  65,945 req/s in the same alternating run, 2026-10-16). Of the 22, about 12 are inside axum (routing, extensions,
  boxed futures).

### HTTP/2 (h2c) and HTTP/3

`h2load -t2 -c64 -m10 -D10` (h2c; HTTP/3 with an h2load built with ngtcp2), same machine and endpoints, 3 alternating
rounds, median (`docs/artifacts/f206_final_{h2c,h3}.tsv`). axum has no HTTP/3, so the HTTP/3 rows have nothing to
compare against and are kept to watch for regressions.

| Target | protocol | plaintext req/s | json req/s | CPU µs/req (plaintext) |
|---|---|---:|---:|---:|
| axum + tokio, per-core (hyper HTTP/2) | h2c | 87,586 | 78,050 | 23.3 |
| veil native handler | h2c | 123,615 | 109,938 | 16.6 |
| veil native handler (epoll) | h2c | 126,200 | 110,824 | 16.2 |
| veil native handler (TLS) | HTTP/3 | 69,039 | 63,752 | 29.5 |
| veil native handler (TLS, epoll) | HTTP/3 | 83,638 | 76,200 | 24.4 |

Over h2c veil serves **1.4× the requests of axum on tokio** with 30% less CPU per request (the frames of all
streams of a connection that are ready in one loop iteration go out in one write).

### Python: FastAPI (uvicorn) and veil

| Target | plaintext req/s | json req/s | p99 ms (plaintext) | CPU µs/req (plaintext) | RSS MB |
|---|---:|---:|---:|---:|---:|
| FastAPI `async def`, uvicorn 1 worker | 5,502 | 4,333 | 14.46 | 189.4 | 49.4 |
| FastAPI `async def`, uvicorn 2 workers | 6,859 | 5,473 | 10.17 | 296.2 | 136.4 |
| FastAPI `def`, uvicorn 2 workers | 3,661 | 3,174 | 50.23 | 551.5 | 140.6 |
| veil, `offload=True` (default), 2 threads | 25,494 | 22,567 | 6.70 | 71.1 | 31.3 |
| veil, `offload=False`, 2 threads | 26,229 | 24,226 | 2.95 | 77.0 | 30.4 |

FastAPI 0.143 / uvicorn 0.54 with uvloop and httptools; pydantic 2. uvicorn's workers are processes, veil runs one
process. The veil rows were re-measured after F-212 (5 alternating rounds against the previous binding,
`docs/artifacts/f212_ab_py.tsv`; before F-212: 15,848 / 12,237 req/s and 110 µs/req with `offload=True`); the
FastAPI rows are from the F-201 run. veil serves **3.7–4.4× the requests of FastAPI with 2 workers** (4.6–5.6× of one
worker) with about a quarter of the CPU per request and less than a quarter of the memory, because HTTP parsing,
routing and the response are done in Rust and only the handler body runs in Python (the request object is created in
Rust and only the attributes the handler reads become Python objects). Python handlers are still serialized by the GIL, so a
single process does not scale with cores; `offload=True` keeps the event loop free of the GIL at the cost of a
handoff to the handler pool (the higher p99).

## Platforms

The library (Rust, C, Python), its gRPC server and VDS were checked on each system with `tests/api/library_e2e.sh`
and `tests/standalone_e2e.rs` (F-203, 2026-10):

| System | Proxy and VDS (`standalone_e2e`) | Rust API | gRPC (h2c, h3) | C | Python | `veil::tokio` ecosystem |
|---|---|---|---|---|---|---|
| Linux x86_64 (io_uring, epoll) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ (incl. PostgreSQL) |
| macOS 15 arm64 (kqueue) | ✓ | ✓ | ✓ | ✓ (clang) | ✓ | ✓ |
| FreeBSD 14.3 x86_64 (kqueue) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| OpenBSD 7.9 x86_64 (kqueue) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

- The C library is built with the system's toolchain (cc/clang, MSVC on Windows); see [C API](#c-api) for linking.

builds and starts the Rust showcase, the C example (dynamic and static) and the Python examples and calls them

## Limitations

- `serve` / `run` can be called **once per process** (configuration hooks and shared state are process-wide); a
  second call returns an error.
- gRPC: veil serves gRPC but has no gRPC client of its own (use tonic on `veil::tokio`).
- Python handlers are bound by the GIL; C callbacks must be thread-safe.
- The Swagger UI page loads `swagger-ui-dist` from a CDN, so the browser needs internet access to render `/docs`
  (`/openapi.json` works offline).
- Library mode does not use a configuration file in `/etc/veil`: `config.toml` in the current directory (or the path
  you pass) is the only file.
