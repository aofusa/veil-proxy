# B-66: FreeBSD 平文 HTTP/1.1 の大レスポンス配信が計測を重ねると劣化する（要再検証）

- 優先度: P3（当初 P1 として起票したが、根拠の大半が計測不備由来と判明したため格下げ）
- 状態: 完了（未再現のためクローズ。2026-08-17 再検証）
- 発見: F-155（FreeBSD perf 最適化）の `h1_file_plain` シナリオ追加時、2026-08-17
- 環境: FreeBSD 14.3-RELEASE aarch64 / QEMU+HVF on Apple Silicon / 4 vCPU・4GB /
  サーバ 2 コア（cpuset 0,1）・負荷生成 2 コア（cpuset 2,3）・loopback
- 関連: F-155（発見契機）、F-156（計測不備の判明契機）

---

## 重要: 当初の根拠の大半は**計測不備**であり、撤回する

本チケットは当初「veil 側にラウンドごとの単調劣化があり p99 が 2.0〜9.5 秒に達する。
F-155 適用前の `b148615` でも再現するので回帰ではない」と起票した。
しかしその後、**根拠として挙げた A/B のほぼ全てが計測不備で無効**だったことが判明した。

### 何が起きていたか

`tools/perf/freebsd/run_perf_freebsd.sh` は計測のたびに `pkill -x veil` で veil を落としていた。
`pkill -x` は**プロセス名の完全一致**なので、A/B のために
`VEIL_BIN=/root/veil.baseline` や `/root/veil.f156` のように**別名のバイナリ**を指定すると、
プロセス名が `veil.baseline` / `veil.f156` となり **1 つも kill されない**。

さらに veil のリスナーは `SO_REUSEPORT`（FreeBSD は `SO_REUSEPORT_LB`）で bind するため、
**取り残された旧プロセスが同じポートを掴んだまま生き残り、カーネルが新旧プロセスへ
接続を分散する**。つまり:

1. 計測ラウンドを重ねるほど veil プロセスが積み上がり、**同じ 2 コア（cpuset 0,1）を
   奪い合う**（＝ラウンドごとに単調劣化するのは当然）。
2. 「新バイナリ」を測っているつもりで、**旧バイナリとの混合**を測っていた。

実際に確認した時点で **13 個の veil プロセスが残存**していた:

```
2861 veil.nopushON /root/veil.nopushON -c .../veil_l4.toml
2935 veil.nopushON /root/veil.nopushON -c .../veil_file.toml
3000 veil.f156     /root/veil.f156     -c .../veil_l4.toml
...（計 13 プロセス）
pgrep -x veil → 0   /   pgrep veil → 13
```

**「各ラウンドは別プロセスだからプロセス内リークでは説明できない」という当初の推論の
前提そのものが誤りだった**（プロセスは落ちておらず、積み上がっていた）。

### 撤回する根拠

- baseline（`b148615`）vs F-155 の交互 A/B の表（174 rps、64 接続全滅、p99 9550ms 等）
  → **全て無効**。別名バイナリを使ったため取り残しが累積した状態での計測。
- `TCP_NOPUSH` ON/OFF の交互 A/B → **全て無効**（同上）。

### 残っている（まだ有効な）観測

`VEIL_BIN` を既定（`target/release/veil`、プロセス名が `veil`）のまま実行した
**最初の 1 回だけ**は取り残しが起きていない。その 3 反復連続の値:

| iter | veil rps | veil p99 | nginx rps | veil/nginx |
|---|---|---|---|---|
| 1 | 87,749 | 0.86ms | 94,799 | 0.93 |
| 2 | 70,804 | 1.01ms | 76,889 | 0.92 |
| 3 | 52,638 | 1.36ms | 58,390 | 0.90 |

**veil も nginx も同じ割合で落ちており、対 nginx 比は 0.90〜0.93 でほぼ一定**である。
これは「veil 固有の劣化」ではなく **VM 全体が計測を重ねるごとに遅くなっている**
（ホスト側の QEMU/HVF の熱・スケジューリング等）ことを示す。p99 も 0.86〜1.36ms で健全。

**つまり、この有効なデータの範囲では B-66 の事象は観測されていない。**

---

## 再発防止（F-156 で実施済み）

`tools/perf/freebsd/run_perf_freebsd.sh` に以下を入れた:

1. `stop_veil()`: `VEIL_BIN` をフルパスで狙い撃つ `pkill -f` と、従来の `pkill -x veil` の 2 段構え。
2. `start_veil()`: 起動前に `pgrep veil` で残存プロセスを数え、**1 つでも残っていたら
   `die` して計測を中止する**（黙って混ざった値を出さない）。

## 今後の扱い

- 本チケットは**「事象が存在するかどうか自体が未確認」**の状態に戻す。
- 再検証するなら、修正後のハーネスで `h1_file_plain` を
  **VM を再起動した直後から**複数ラウンド回し、**対 nginx 比**（絶対値ではなく）が
  ラウンドを追って下がるかを見ること。絶対値は VM 側の要因で必ず下がる。
- 比が一定なら本チケットは Close してよい。


## 2026-08-17 再検証（F-157 の計測ついでに実施）

FreeBSD 14.3 aarch64（QEMU/HVF）で `h1_file_plain`（54,576B、平文 HTTP/1.1、
`sendfile(2)` + `sf_hdtr` 経路）を複数ラウンド取り直した。

| ラウンド群 | 対 nginx 比 |
|---|---|
| 初回 8 シナリオ実行（3 反復） | 1.03（中央値） |
| キャッシュ有効化後（4 反復） | 0.92 / 0.98 / 1.07 / 1.03 |
| 最終確認（4 反復） | 0.90 / 0.98 / 1.07 / 1.03 |

- **ラウンドを重ねるごとの単調劣化は観測されなかった。**
- p99 は 0.75〜1.24ms で、起票時に報告された 2.0〜9.5 秒のスパイクは**一切再現しない**。
- veil / nginx とも同じ傾きで絶対値が下がる（VM 側要因）が、**対 nginx 比はほぼ一定**。

撤回時の結論（「事象は計測不備由来であり、実際には観測されていない」）が追試でも
裏付けられたため **クローズ** する。再発を疑う場合は絶対値ではなく **対 nginx 比の推移**で
判定し、`pgrep veil` で取り残しが無いことを先に確認すること。
