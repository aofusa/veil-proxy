# B-66: FreeBSD 平文 HTTP/1.1 の大レスポンス配信がラウンドごとに単調劣化し p99 が数秒に達する

- 優先度: P1
- 状態: 未対応（要調査）
- 発見: F-155（FreeBSD perf 最適化）の `h1_file_plain` シナリオ追加時、2026-08-17
- 環境: FreeBSD 14.3-RELEASE aarch64 / QEMU+HVF on Apple Silicon / 4 vCPU・4GB /
  サーバ 2 コア（cpuset 0,1）・負荷生成 2 コア（cpuset 2,3）・loopback
- 関連: F-155（本バグの発見契機）、B-63（FreeBSD aio の停止）、B-61

## 事象

**veil に平文 HTTP/1.1 で 54KB の静的ファイルを wrk（64 接続・15 秒）で要求すると、
計測ラウンドを重ねるごとにスループットが単調に落ち、p99 レイテンシが数秒に達する。**
同一ラウンドで同じ負荷を受ける nginx は約 50,000 rps で完全に安定しているため、
負荷生成側やホストの問題ではなく **veil 側の事象**である。

初回は健全な値が出る（対 nginx 0.92）が、繰り返すほど悪化する。
各ラウンドは `pkill -x veil` を挟んだ**別プロセス**なので、プロセス内リークでは説明できない。

### 実測（`tools/perf/freebsd/run_perf_freebsd.sh h1_file_plain`、`-p /index.html` = 54,576B）

健全だった初回（3 反復連続）:

| iter | veil rps | veil p99 | nginx rps |
|---|---|---|---|
| 1 | 87,749 | 0.86ms | 94,799 |
| 2 | 70,804 | 1.01ms | 76,889 |
| 3 | 52,638 | 1.36ms | 58,390 |

その後の交互 A/B（1 ラウンド = 1 反復。`veil.baseline` = F-155 適用前 = b148615、
`nopushON` = F-155 適用後）:

| round | 変種 | veil rps | veil p99 | errors |
|---|---|---|---|---|
| 1 | baseline | 174 | 3.26ms | 0 |
| 1 | F-155 | 9,732 | 4130ms | 0 |
| 2 | baseline | 8,732 | 69.81ms | **64** |
| 2 | F-155 | 10,391 | 5100ms | 0 |
| 3 | baseline | 16,687 | 2690ms | 0 |
| 3 | F-155 | 6,660 | 2.04ms | 0 |
| 4 | baseline | 5,570 | 185.61ms | **64** |
| 4 | F-155 | 1,758 | 2.13ms | 0 |

同じラウンドの nginx は一貫して 48,000〜65,000 rps・p99 1.1〜1.3ms で安定していた。

## 切り分け済み（原因ではないと確定したもの）

1. **F-155 の変更（sf_hdtr / TCP_NOPUSH / batch accept 等）ではない。**
   F-155 適用前の `b148615` をビルドした `veil.baseline` でも**同じように再現する**
   （上表。むしろ baseline のほうが悪いラウンドもある）。両者を交互に走らせた
   A/B なので、時間経過によるドリフトの影響も受けていない。
2. **`TCP_NOPUSH` ではない。** F-155 の `nopush_guard` を有効/無効にした 2 バイナリを
   交互に 4 ラウンド走らせたが、劣化の度合いに一貫した差は出なかった（両方とも劣化した）。
3. **keep-alive が壊れているわけではない。** 1 接続で 2 リクエストを投げると
   2 本目は `num_connects=0`（接続再利用）で成功し、レスポンスヘッダも
   `Connection: keep-alive` / `Content-Length: 54576` と正しい。
4. **レスポンス本体の破損ではない。** 平文 HTTP/1.1 で取得した 54,576B の md5 は
   配信元ファイルと一致する。小さい応答（3B）も正しい。

## 未検証の候補

- 小応答（3B）でも同じラウンドで劣化するが度合いが小さい（111k → 80k、p99 27ms → 82ms）。
  **サイズ（帯域）に強く依存する**ことから、送信側のバッファ/キューの枯渇が疑わしい。
- ラウンドをまたいで悪化する = **システム（カーネル）側の状態が蓄積している**。
  FreeBSD の mbuf / sendfile バッファ（`sysctl kern.ipc.nmbclusters`、`vfs.numvnodes`、
  `kern.ipc.maxsockbuf`）や、close されずに残るソケットを `netstat -m` / `netstat -an` で
  時系列に観測するのが入口。
- 平文 HTTP/1.1 は **メインリスナー（TLS ポート）のプロトコル検出経由**でしか到達しない
  （`h2c_listen` は h2c 専用で HTTP/1.1 を拒否する）。この
  `detect_protocol_with_buffer` → `accept_plain` 経路に固有の問題である可能性がある
  （TLS 経路・h2c 経路では同じ劣化が観測されていない）。

## 影響

- 平文 HTTP/1.1 で大きな静的ファイルを配信する構成（TLS 終端を前段に置くケース等）で、
  時間経過とともにスループットが落ちレイテンシが数秒に達しうる。
- `tools/perf/freebsd/run_perf_freebsd.sh` の `h1_file_plain` シナリオは、
  **本バグが直るまで安定した計測値を出さない**（F-155 の `sf_hdtr` の効果も、
  初回ラウンドの対 nginx 0.92 以外は正確に測れない）。
