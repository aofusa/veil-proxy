# B-90: TLS ハンドシェイクで 4KB を超えて届いた暗号文を捨てていた（B-68 の真因）＋ HTTP/3 の早期応答で上り本文が停止する

## 事象

FreeBSD の E2E で `test_http3_large_request_body` が失敗し続けていた（B-68。2026-08 から未解決）。
今回の検証では FreeBSD x86_64 / aarch64 とも **環境起動後の 1 回目だけ成功し、2 回目以降は
すべて失敗**する、決定的な再現条件が得られた。

## 原因 1（主因）: ハンドシェイクループが `read_tls` を 1 回しか呼んでいない

`ktls_rustls.rs` と `simple_tls.rs` の `do_server_handshake` / `do_client_handshake` は、
生ソケットから読んだ暗号文を `conn.read_tls(&mut &read_buf[..n])?` で **1 回だけ** rustls へ
渡し、戻り値（取り込んだバイト数）を見ていなかった。rustls の deframer は 1 回の `read_tls` で
**最大 4KB**（`READ_SIZE`）しか取り込まないため、`n > 4KB` のとき**残りが黙って失われる**。

クライアントの Finished と直後のアプリケーションデータ（リクエストヘッダ + 最初の本文）が
1 回の read にまとまって届くと、サーバ側で 4KB 以降が欠落し、以降のレコード境界がずれて
`cannot decrypt peer's message` になる。

- 計測: フロント（HTTP/3 → TLS バックエンド）の送出レコードはすべて正しい長さで、
  バックエンド側が本文 4,549 バイト（最初の QUIC 本文断片）を復号した直後に失敗していた。
- 1 回目だけ成功するのは、初回はフル・ハンドシェイクで往復が多く Finished と本文が別の read に
  分かれ、2 回目以降はセッション再開で短くなりまとめて届くため。
- Linux / macOS で表面化しにくかったのはタイミング（ソケットバッファ・スケジューリング）の差で、
  コードはプラットフォーム共通である。

**修正**: 受信した暗号文を全量投入する `tls_writev::read_tls_all` を追加し、6 箇所
（サーバ/クライアント × 2 実装 + 先読みデータ投入）を置き換えた。

## 原因 2: バックエンドが本文の途中で応答・切断すると、HTTP/3 クライアントの上り本文が止まる

原因 1 でバックエンドが 400 を返して切断すると、フロントのバックエンドタスクは終了するが、
`drive_request_pump` は req チャネルを落とすだけで `recv_body` を呼ばなくなっていた。未受信の
本文が quiche に溜まって **QUIC のフロー制御ウィンドウが補充されず**、本文を送り切ってから応答を
読むクライアントは送信が止まったまま応答を受け取れない（B-68 の「詰まると 30 秒待ち」の正体）。

**修正**: 本文が不要になった時点（チャネルの受信側が閉じた。満杯のまま閉じた場合も検出する
`Sender::is_closed` を追加）で RFC 9114 §4.1.1 のとおり `STOP_SENDING(H3_NO_ERROR)` を送る。
テストクライアントも、送信を止められても応答を読みに行くようにした（RFC 上の正しい挙動）。

## 検証

- 単体: `tls_writev::read_tls_all_tests`（Finished + 10KB を 1 回で投入して全量届くこと、
  単発 `read_tls` は 4KB 未満しか取り込まないこと）。
- E2E: `test_http3_early_backend_response_does_not_stall_upload`（4MB を即 500 を返す
  バックエンドへ POST）を追加。**STOP_SENDING を外すと Linux でも 20 秒で停止して失敗**、
  修正ありでは 37ms で応答。
- FreeBSD x86_64 で `test_http3_large_request_body` + TLS ストリーミング 2 件を 10 回連続実行し
  10/10 成功（修正前は 2 回目以降すべて失敗）。

## 教訓

rustls の `read_tls` は「渡したバイト列を全部読む」API ではない。データ転送経路のループは
正しく書かれていたが、ハンドシェイク経路だけ単発呼び出しのまま残っていた。**ハンドシェイク直後に
アプリケーションデータが同じ read に乗るかどうかはタイミング次第**で、フル・ハンドシェイクでは
再現しにくく、セッション再開で初めて頻発する。
