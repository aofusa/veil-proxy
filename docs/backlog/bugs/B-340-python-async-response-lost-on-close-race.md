# B-340: `async def` のハンドラの応答を、ワーカーがまれに取りこぼして 500 にする

**状態: 修正済み（feat/v0120-perf、2026-11-08）**

親: [F-295](../features/F-295-v0120-perf-harness.md)（v0.12.0 の最終計測の non2xx の列で見つけた）。

## 事象

`tools/api-bench/run_bench.py --group python`・`tools/perf/api_ab.py --scenario python` の `async def` の行だけ、15 秒（200〜260 万要求）に
1〜2 件の 2xx 以外が出る。v0.11.0 のホイールでも出る（最終計測の 15 行の非 0 のうち 4 行は v0.11.0 の側）。

アクセスログを出して同じ負荷を掛けると（`veil_app.py`、`BENCH_ASYNC=1`、2 スレッド・CPU 0,1、`wrk -t2 -c64 -d15s`、3 回）、
約 690 万要求に 5 件が `status=500`・`duration_ms=0`・本文 34 バイト（`{"detail":"Internal Server Error"}`）で、Python の例外の出力は無かった。
`offload=True`（約 980 万要求）は 0 件。

## 原因

`async def` のハンドラの応答は、常駐のイベントループが `Out`（`crates/veil-python/src/aio.rs`）へ「積む（`send`）→ 閉じる（`close_tx`）」の順で
返す。ワーカーの `Out::recv` は、キューの錠を取って空なら錠を放し、その後で閉じた旗を読んでいた。

錠を放してから旗を読むまでの間にワーカーのスレッドが止まり（割り込み・横取り）、その間にループが応答を積んで閉じると、ワーカーは
「空で閉じた」と判断して応答を捨て、500 を返す。ストリーミングの応答では最後の `End`（トレーラ）を落として本文を打ち切る
（`the handler failed while streaming`）。サーバの CPU をスレッドより少なく絞った計測（CPU 2 つに、ワーカー 2 本・ループ・アクセスログ）で
横取りが多く、表に出た。

同期のハンドラの応答（`api::bridge::AsyncReceiver::recv`）は錠を持ったまま旗を見ているので起きない。

## 修正

`Out::recv` は閉じた旗をキューの錠を持ったまま読む。錠の中でキューが空なら、ループが積むのはこの後なので、閉じるのもこの後になる。

## 試験

窓は錠を放してから旗を読むまで（数十 ns）で、そこでワーカーが止まったときだけ起きる。修正前のホイールに、ストリーミング（64 断片を待たずに
返す非同期ジェネレータ）とパイプラインのふつうの応答を 4 プロセスから掛けても（約 3 万本のストリームと 58 万要求）再現せず、決定的に
再現する試験は書けない（`crates/veil-python` は pyo3 の拡張モジュールで、Rust の単体試験を持てない）。修正の前後に、事象と同じ負荷を
掛けて確かめた。

| ホイール | 要求数 | 500 |
|---|---:|---:|
| 修正前（`4fbe17a3`） | 約 690 万 | 5 |
| 修正後 | 約 676 万 | 0 |

修正前の頻度（100 万要求に約 0.7 件）のままなら、676 万要求で 0 件になる確率は 1% 未満。
検出は `run_bench.py`・`api_ab.py` の non2xx の列（どちらも既に出している）。
