# B-64: `load_backend` がリクエストごとに `realpath`/`fstat` を実行していた

**状態: 修正済み（syscall 除去は確認。ただし交互 A/B でスループットに差は出なかった＝ここはボトルネックではなかった）**

> **【重要な訂正】** 本チケットは当初「`open_file_cache` が効いていない」という
> 見立てで書いたが、**それは誤りだった**。DTrace の `ustack()` で実際のコールスタックを
> 取ったところ、原因は `open_file_cache` ではなく **`config::load_backend` が
> リクエストごとに呼ばれ、その中で `canonicalize()` と `fs::metadata()` を
> 実行していたこと**だった。`open_file_cache` は正しく機能している。

## 事象と原因

HTTP/2 静的配信のホットパスで `__realpathat` と `fstatat` が最多の syscall
（`poll` の 5 倍以上）だった。`ustack()` の結果:

```
libc.so.7`__sys___realpathat
veil`std::sys::fs::unix::canonicalize
veil`veil::config::load_backend        ← リクエストごとに呼ばれている
```

`load_backend` は `src/upstream.rs` の `find_backend_unified`（ルート照合）から
**リクエストのたびに**呼ばれ、そこで Backend を組み立て直している。その中で:

1. `canonicalize()` — **F-145 で筆者が追加したもの**。F-145 は「毎リクエストの
   base_path 二重解決を config ロード時の 1 回へ集約する」意図だったが、
   集約先の `load_backend` 自体がリクエストごとに呼ばれるため、
   別の場所に同等のコストを作り直していた。
2. `fs::metadata()`（`is_dir` 判定）— 以前から存在。

さらに `load_backend` には
`// 理由付き allow: 起動・リロード・設定検証時のみ実行されるコールドパス（データプレーン非経由）`
という **事実と異なる根拠**の `#[allow(clippy::disallowed_methods)]` が付いており、
clippy が正しく検出していた「ホットパス上の同期 FS 呼び出し」を抑制していた。

## 修正

いずれも「設定に対して不変な値」なので、設定パス文字列をキーに**スレッドローカルで
メモ化**した（`canonical_base_memoized` / `is_dir_memoized`）。

- 最初はプロセス共有の `RwLock<HashMap>` にしたが、`load_backend` が毎リクエスト
  呼ばれるため**リクエストごとにロック取得**が発生し、実測でスループットが改善しなかった。
  ウォームな VFS キャッシュ上の `realpath`/`fstat` は 1μs 程度と安く、ワーカー間で
  共有するロックの読み取り競合の方が高くつく。veil は thread-per-core なので
  スレッドローカルにすればワーカーごと 1 回の解決で済み、以降は syscall もアトミック操作も無い。
- **解決失敗（`None`）はメモしない**。起動時にディレクトリが無くても後から作成されれば
  動作する、という既存の運用挙動を壊さないため。
- `#[allow]` の根拠コメントを事実（「この関数はリクエストごとに呼ばれる。高コストな
  解決はメモ化済み」）へ書き直した。

## 実測

DTrace（FreeBSD 14.3 aarch64、3B ファイル / HTTP/2 `-c32 -m16`、6 秒窓）:

| syscall | 修正前 | 修正後 |
|---|---|---|
| `__realpathat` | 94,880 | **0** |
| `fstatat` | 94,880 | **0** |
| `poll` | 17,790 | 19,772 |
| `write` / `read` | 5,930 | 6,590 / 6,594 |

**syscall の除去は確実**（両方とも完全に消えた）。

## 交互 A/B の結果: **スループットには効かなかった**

メモ化あり/なしの 2 バイナリを**同一ラウンド内で交互に**計測した（設定は同一、
`tools/perf/freebsd/ab_content_cache.sh` の `BIN_OFF`/`BIN_ON`、HTTP/2・3B と 54KB）:

| ラウンド | メモ化なし 54KB | メモ化あり 54KB |
|---|---|---|
| 1 | 22,801 | 25,137 |
| 2 | 30,297 | 29,336 |
| 3 | 31,419 | 32,659 |
| 4 | 41,696 | 37,573 |

中央値は約 30,858 対 約 31,000 で**差は誤差範囲**（ラウンドごとに符号が反転する）。
3B でも両方取れたラウンドで 233,424 対 225,067 と有意差なし。

**結論: ウォームな VFS キャッシュ上の `realpath`/`fstat` は十分に安く、
これらは nginx との差のボトルネックではなかった。** 当初の見立ては誤りだった。

なお同一バイナリでもラウンド間で 22,801 → 41,696 rps と 1.8 倍変動している。
時間をまたいだ比較が無意味であることの再確認であり、交互 A/B が必須である。

## 変更を残す判断

スループットに効かないと分かった後も、以下の理由で修正は残す:

- **ホットパスから同期 FS 呼び出しを 2 つ除去した**こと自体は AGENTS.md の
  ホットパス絶対規則に沿う（実測で syscall が 0 になることは確認済み）。
- **事実と異なる `#[allow]` の根拠コメントを正した**。「コールドパスなので許容」と
  書かれていたが実際はリクエストごとに呼ばれており、clippy の警告は正しかった。
  この誤った記述を残すと、次に触る人が同じ勘違いをする。
- 計測上のデメリットが無い（誤差範囲）。

## 次の調査先

nginx との残り差（3B で約 0.54 倍）の主因は別にある。現在の syscall 内訳では
**`poll` が 1 リクエストあたり約 3 回で最多**であり、次はここを疑うべき。
`reactor` の readiness 経路（`Readable`/`Writable` の投機的 `poll(2)` プローブ）が
関係している可能性がある（F-145 で一度削除を試みてハングし撤回した箇所）。
