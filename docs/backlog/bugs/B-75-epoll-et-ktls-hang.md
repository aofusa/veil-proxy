# B-75: epoll の readiness ヒント（F-166 A-1）が kTLS + HTTP/2 で恒久ハングする

## 事象

`full-container`（epoll reactor）ビルドで、perf ハーネスの
`h2_1_ktls_1_lb_cbpf_ofc_0`（**kTLS 有効** + CBPF + HTTP/2）を計測すると、
**HTTP/1.1（wrk）フェーズ 3 本の後の h2load（HTTP/2）が停止**し、以後まったく進まない。

- veil の CPU は **0.2%**、クライアントも 0%（＝ビジーループではなく**起床の取りこぼし**）
- 2026-08-25 の同一構成・同一ハーネスでは正常に計測できていた（3,708〜4,089 rps）
- **単体 934 件・統合 54 件・E2E 544 件（epoll ビルド含む）はすべて通過する**
- **io_uring 既定ビルド（`full`）では発生しない**（同じ構成を完走する）
- `tools/perf` のフルスイートでのみ検出できた（36 分ぶら下がってスイートが停止した）

## 切り分け（すべて同一手順の再現テスト: `wrk ×3 → h2load` の順で実行）

| 対象 | 内容 | 結果 |
|---|---|---|
| `veil:ab-base-container` | F-166 A 適用**前** | **OK**（423ms） |
| `veil:alloc-prev-container` | F-166 A（A-1/A-2/A-3）適用 | **HANG** |
| ツリー（A-2 = `EPOLLET` を差し戻し済み） | A-1 + A-3 | **HANG** |
| ツリー（さらに **A-1 のヒント消費のみ無効化**） | A-3 のみ | **OK**（238ms） |
| ツリー（A-1 を完全削除した最終形） | A-3 のみ | **OK**（254ms） |

→ **ハングに必要だったのは A-1（epoll の readiness ヒント）**。A-2（ET）は差し戻した
状態でもハングしたので、**A-2 単独が原因ではない**。

## 原因（確定部分と仮説の区別）

**確定**: epoll バックエンドで「直前の起床でこの方向のイベントを観測した」という
consume-once ヒントを使い、`Readable`/`Writable` が確認用 `poll(2)` を省いて
`Poll::Ready` を返す経路を有効にすると、kTLS + HTTP/2 の負荷で恒久ハングする。
ヒント消費を止めるだけでハングは消える。

**仮説（未実証、ただし整合的）**: epoll は `EPOLLONESHOT` なので、イベント発火時点で
カーネル側の interest は無効化されており、**再武装は `register()`（= `EPOLL_CTL_MOD`）
でしか行われない**。ヒントで `Ready` を返した待機は `register()` を通らないため、
fd は disarm されたままになる。ここに **kTLS 特有の「`poll(2)` は `POLLIN` を返すのに
`recvmsg` は `EAGAIN` を返す」状態**（レコード未完成 / 先頭がアプリケーションデータ以外）が
重なると、「読めないが再武装もされない」組み合わせに入り得る。
io_uring バックエンドは待機のたびに `POLL_ADD` を出す（＝毎回再武装相当）ため無傷である。

## 対応

- **A-1（epoll の readiness ヒント）を完全に削除する。** `read_hint`/`write_hint` と
  `take_read_hint`/`take_write_hint` は **kqueue 専用（F-141）に戻す**
  （kqueue の `data` は「読み取り可能バイト数」という実データで、epoll の
  「イベントが来た」だけの真偽値とは性質が違う）。
  **削除による損失はほぼ無い**: 実測で省けていた `poll(2)` は 0.558 → 0.531/req（-5%）だった。
- **A-2（`EPOLLET` 常時登録）も差し戻したままにする。** ET 単独の安全性は未検証であり、
  ET の前提（`EAGAIN` ⇒ レベルでも not ready）は上記の kTLS 挙動と相性が悪い。
  `EPOLLONESHOT` + 待機ごとの `EPOLL_CTL_MOD` は、**再武装のたびにカーネルが
  レベル状態を再評価する**ため、この種の取りこぼしが構造的に起こらない。
- **A-3（`WakerSlot` による Waker のインライン化）は維持する**（レベル/エッジの
  意味論に依存せず、再現テストでも OK）。

## 教訓

1. **「確認用 syscall を省く」最適化は、その syscall が同時に持っている
   副作用（ここでは再武装＝レベル状態の再評価）を奪っていないか確認する。**
2. **kTLS は「`poll` は ready、`read` は EAGAIN」を返しうる特殊なソケット層**であり、
   readiness ベースの最適化の前提を壊す。reactor + kTLS は二重の空白地帯。
3. **単体・統合・E2E をすべて通過した。検出できたのは `tools/perf` のフルスイート
   （kTLS 有効構成 × HTTP/2）だけ。** 性能計測は性能のためだけの道具ではない。
4. 原因の切り分けは**イメージのビルド 20 分を待つのではなく、ホスト上で veil を直接
   起動する再現スクリプト（約 1 分/試行）**に切り替えたことで一気に進んだ。
