# B-75: epoll の `EPOLLET` 常時登録（F-166 A-2）が kTLS + HTTP/2 で恒久ハングする

## 事象

`full-container`（epoll reactor）ビルドで、perf ハーネスの
`h2_1_ktls_1_lb_cbpf_ofc_0`（**kTLS 有効** + CBPF + HTTP/2）を計測すると、
**HTTP/1.1（wrk）フェーズ 3 本の後の h2load（HTTP/2）が 70% 付近で停止**し、
以後まったく進まなくなる。

- veil の CPU は **0.2%**、クライアントも 0%（＝ビジーループではなく**起床の取りこぼし**）
- veil のログは HTTP/1.1 フェーズ終了時の `sendfile error: Broken pipe` の洪水で終わっている
- 2026-08-25 の同一構成・同一ハーネスでは正常に計測できていた（3,708〜4,089 rps）
- **単体 934 件・統合 54 件・E2E 544 件（epoll ビルド含む）はすべて通過する**

## 切り分け

同一構成で 3 つのイメージを比較した（`wrk ×3 → h2load` の順序を再現）:

| イメージ | 内容 | 結果 |
|---|---|---|
| `veil:ab-base-container` | F-166 A 適用**前** | **OK**（423ms で完走） |
| `veil:alloc-prev-container` | F-166 A（A-1/A-2/A-3）のみ適用 | **HANG** |
| `veil:container` | 全変更適用 | **HANG** |

→ **原因は F-166 A-2（`EPOLLET` + fd あたり `epoll_ctl(ADD)` 生涯 1 回）**。

## 根本原因

ET（エッジトリガ）は「**`EAGAIN` が返る ⇒ レベル的にも読めない ⇒ 次の到着が必ず新しい
エッジを生む**」ことを前提にする。**この前提は kTLS ソケットでは成り立たない。**

kTLS では `poll(2)` が `POLLIN` を返す状態でも `recvmsg` が `EAGAIN` を返しうる
（TLS レコードが未完成、あるいはキューの先頭がアプリケーションデータ以外のレコード）。
この状態に入ると:

1. データ到着のエッジは既に消費済み（`epoll_wait` が報告済み）
2. `read(2)` は `EAGAIN` を返す（レコードが揃っていない）
3. 新しいバイトはもう来ない（クライアントは応答待ち）ため **エッジが二度と発生しない**
4. → タスクは park したまま起きない（恒久ハング、CPU 0%）

F-166 A-2 の設計では「ヒントが無ければ park 前に `poll(2)` で確認する」ことで
取りこぼしを塞ぐつもりだったが、**`ReadFuture`/`WriteFuture`（try-first の
`read(2)`/`write(2)` を行う本来の I/O 経路）は `poll(2)` を通らず、`EAGAIN` を見たら
そのまま `register_read` して park する**。ここが穴だった。

旧実装の `EPOLLONESHOT` + 待機ごとの `EPOLL_CTL_MOD` 再武装は、
**再武装のたびにカーネルがレベル状態を再評価する**ため、この状況でも次の周回で必ず
起床できていた（＝旧実装が正しく、かつその「無駄に見える MOD」が正しさの要だった）。

## 対応

**A-2 のみを差し戻す**（`EPOLLONESHOT` + `EPOLL_CTL_MOD` 再武装を復元）。
F-166 A-1（readiness ヒントによる確認用 `poll(2)` の省略）と A-3（`WakerSlot` による
Waker のインライン化＝待機・起床ごとの malloc/free 排除）は**維持する**
（どちらもレベル/エッジの意味論に依存せず、`poll(2)` フォールバックも残っている）。

syscall/req は epoll_ctl が戻る分だけ増える（54KB: 4.72 → 約 6.0）。**正しさを優先する。**

## 教訓

1. **ET は「EAGAIN ⇒ レベルでも not ready」を仮定する。kTLS のようにカーネルが
   ソケットの内部状態で `EAGAIN` を返す層が挟まると、この仮定は崩れる。**
   ET へ移行するなら、全ての `EAGAIN` → park 経路に `poll(2)` 確認を入れる必要がある
   （そして kTLS ではその `poll(2)` が readable を返し続けるため、今度はビジーループになる）。
2. **「毎回発行している一見無駄な syscall」が、実は再評価による正しさの担保であることがある。**
   削る前に「これが無いと壊れるケースは何か」を、kTLS のような特殊なソケット層まで含めて洗う。
3. **この不具合は単体・統合・E2E をすべて通過した。** 検出できたのは
   `tools/perf` のフルスイート（kTLS 有効構成 × HTTP/2）だけである。F-145 の
   「reactor はテストの空白地帯」に加えて、**kTLS × reactor はさらに深い空白地帯**。
