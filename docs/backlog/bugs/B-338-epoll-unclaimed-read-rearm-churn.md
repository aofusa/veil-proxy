# B-338: epoll で待機者のいない読み取りイベントのたびに武装を下げ、待ち直しで上げ直していた（取り下げ）

**状態: 取り下げ（仮説を実測で否定した。feat/v0120-perf、2026-11-07）**

親: [F-297](../features/F-297-core-limited-latency.md)（epoll をレベルトリガの常時武装にした変更）。

## 起票の理由

最終の A/B（`proxy_ab.py`、サーバを 4 CPU・4 スレッドに絞ったサーバ律速の条件）で、epoll の h2c の 54KB の静的配信だけが main より遅かった
（0.920×、勝ち 0/3、CPU/要求 20.50 → 22.49 µs）。

## 仮説（誤り）

F-297 の `dispatch_event` は、読み取り可能のイベントで起こす相手がいなければその場で武装を下げる（`EPOLL_CTL_MOD`）。HTTP/2 の接続の
ループが起こされてから待ち直すまでの間に実行器の `epoll_wait` をまたぐと、そのイベントで下げられ、待ち直しの `register` で上げ直す。
1 周に `epoll_ctl` が 2 本になり、待ちごとに 1 本だった main（`EPOLLONESHOT`）より多くなる、と考えた。

試した修正は「待機者のいない読み取りイベントは 1 回目は下げずに印を付け、続けて誰も待たないまま届いたら下げる」。

## 否定した計測

同じ条件（h2c 54KB、サーバ 4 CPU、h2load `-c 128 -m 10`）で 1 要求あたりのシステムコールを数えた（LD_PRELOAD、2 回ずつ交互）。

| | `epoll_ctl` / 要求 | CPU / 要求 |
|---|---:|---:|
| main | 0.152〜0.158 | 19.6〜20.4 µs |
| 改修後 | 0.001 | 20.7〜21.0 µs |
| 改修後 + この修正 | 0（数えられる量なし） | 20.0〜22.2 µs |

改修後の `epoll_ctl` は main の 100 分の 1 で、上げ下げの往復は起きていなかった。修正を入れても CPU は変わらなかった。JSON の identity の
行（`api_ab.py --scenario json`、5 ラウンドの交互 A/B の中央値）では、この修正と最初の B-339 の修正を両方入れたビルドが改修後の 0.91 倍、
この修正だけのビルドの 0.97 倍で、速くはならなかった。コードは入れていない。

残った差は、プロファイル（`perf record`、ユーザ空間）では本文のコピー（`memmove`）の割合が 27.3% → 30.8% に増えた分で、システムコールの
数ではない。[F-297](../features/F-297-core-limited-latency.md) の「HTTP/2 の転送の退行」に続きを書く。
