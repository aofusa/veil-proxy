# B-332: reactor で応答の速い接続がワーカーを占有し、同じワーカーの他の接続が秒単位で待たされる

**状態: 修正済み（feat/v0120-perf、2026-11-07）**

## 事象

epoll 版で閉ループの負荷をかけると、遅延の分布に秒単位の外れが出る。

- gRPC、8 スレッド、256 接続 × 100 ストリーム: p50 45 ms に対し p99 1.18 s、p99.9 3.1 s、最大はほぼ計測時間（`h2load` でも最大 1.38 s）。
- Python（`offload=False`、1 スレッド、64 接続）: p50 86 µs に対し p90 30 ms（64 接続が公平なら最悪でも約 5.5 ms）。
- 計測中に 10% ほどの接続が全く進まない。

## 影響

reactor（Linux の epoll 版・コンテナ・Python の wheel・BSD・macOS・Windows）の全プロトコル。負荷の高いときのテール遅延。
外部の gRPC のテール遅延の主因。

## 調査メモ

- `Readable::poll` は `poll(2)` で可読なら `Ready` を返す。読み書きはどちらも try-first。つまり相手がすぐ次を送ってくる接続のタスクは
  `Pending` を返さず、1 回の `poll` の中で要求を処理し続ける。
- `run_ready_tasks` はキューが空になるまで回り、`park`（`epoll_wait`）へ戻らない。strace で 3 秒に `epoll_wait` 8 回。
- 他の接続はソケットにデータがあっても起こされない。

io_uring 版は完了のたびに CQE を経由するので接続の順番が公平で、この問題は起きない。

## 改修案

1. `run_ready_tasks` は 1 回に「入ったときのキューの長さ」までを処理し、キューに残りがあれば `park(0)`（待たない）でイベントを取り込む。
2. I/O の協調的な予算: タスクの 1 回の `poll` の中で続けて成功できる I/O の回数に上限を置く。使い切ったら自分を起こして `Pending` を返す（ready の末尾へ回る）。
   予算は `Future` ごとの分岐 1 つとスレッドローカルのカウンタだけ（確保もシステムコールも増やさない）。

予算はタスクごとで、インラインの初回 poll（`spawn_inline`）にも別に渡す。呼び元の接続と分け合うと、束の途中のストリームが要求を送る前に `Pending` へ落ちて
1 周回遅れる（HTTP/2 の 54KB の転送で −5%。[F-297](../features/F-297-core-limited-latency.md)）。

## 受け入れ条件

- 上の 2 つの負荷で秒単位の外れが消える（p99.9 が p50 の数倍の範囲）。
- スループットが落ちない（交互 A/B）。

## 結果

- gRPC（epoll、8 スレッド、256 接続 × 100 ストリーム、閉ループ）: 318k → 1.60M rps、p99.9 1.95 s → 26 ms（`api_ab.py --scenario grpc`、F-295 の最終計測）。
- Python（`offload=False`、2 スレッド、64 接続、2012 年のノート PC）: p50 109 µs・p99.9 21.6 ms → p50 1.45 ms・p99.9 4.0 ms。改修前は一部の接続だけが
  回り続け、残りが待たされていた（スループットは F-299 と合わせて 2.2 倍）。
- **受け入れ条件の例外:** epoll の h2c・h2 の 54KB の静的配信をサーバ律速で測ると main より遅い（同じバイナリの切り替えで約 4%、最終の A/B で h2c 0.929・h2 0.953）。予算と間隔を両方外したときだけ戻り、原因は
  「1 つの接続を続けて回すと作業集合が温かい」ことだった（不公平の利得）。値の掃引・回し続ける負荷・`perf stat` は
  [F-297](../features/F-297-core-limited-latency.md) の「静的配信の 54KB（サーバ律速）に残る差」。
