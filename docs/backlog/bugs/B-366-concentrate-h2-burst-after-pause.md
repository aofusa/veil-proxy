# B-366: 接続の集約（F-303）の後、負荷の切れ目に来た HTTP/2 の接続の束が少数のワーカーに固まる

**状態: 修正済み（feat/beat-nginx、2026-11-13）**

[F-303](../features/F-303-concentrate-connections.md) の後の性能の総当たり（`tools/perf/run_perf.sh`、v0.12.0 と交互）で見つけた。

## 事象

proxy cache の構成（`h2_1_proxy_cache`）の HTTP/2 だけが v0.12.0 を下回った（lab26、4 ラウンド、1 反復）。

| | 1 | 2 | 3 | 4 |
|---|---:|---:|---:|---:|
| v0.12.0 | 33.4k | 29.1k | 35.4k | 34.3k |
| feat/beat-nginx（beat8） | 27.0k | 26.0k | 29.7k | 26.5k |

同じバイナリで `[performance] concentrate_connections` を有効・無効に切り替えて交互に測ると（lab31、2 ラウンド × 3 反復）、
有効のときは HTTP/1.1 の直後の 1 回目だけが落ちる（2 回目・3 回目は無効と同じ）。HTTP/1.1 は有効の方が 1.74 倍速い。

| HTTP/2 | 1 回目 | 2 回目 | 3 回目 |
|---|---:|---:|---:|
| 有効（ラウンド 1・2） | 28.3k・26.8k | 36.2k・35.0k | 36.7k・38.7k |
| 無効（ラウンド 1・2） | 38.3k・28.7k | 37.7k・38.1k | 37.3k・38.4k |

## 原因

`run_perf.sh` は 1 つの構成を wrk の準備運転 → wrk × 3 → h2load の準備運転（`-n 1000 -c 10`）→ h2load × 3 の順に測る。
HTTP/1.1 の間に集約は N を 16 本のうち数本まで縮める。集約が全ワーカーへ戻すのは負荷の無い状態が 5 秒続いたときだけで、
HTTP/1.1 と HTTP/2 の 1 回目の間の h2load の準備運転がその数え上げを振り出しに戻すため、1 回目の 100 本の HTTP/2 の接続は
縮めた数本のワーカーで受理された。HTTP/2 の接続は後から動かせない（GOAWAY で張り直さないクライアントがある）ので、
その回は数本のワーカーだけで処理した。接続の急増の検出（基準の 2 倍）は 2 周回（0.2 秒）続いてから働くので、
接続を一度に張る負荷には間に合わない（2 回目・3 回目は落ちなかった。反復の間には準備運転が無い）。

あわせて次の 2 点も、負荷の切れ目をまたぐと誤った判断になっていた。

- 試しの測定の途中で負荷が止むと、測定は 0 になり「遅くなった」として戻し、30 秒以上の待ちを付けていた（準備運転の終わり等）。
- 接続の数の基準（急増の判定に使う）は負荷の無い間も 2 秒で下がり、切れ目の後に同じ数で戻った負荷を急増と見て、
  見つけた本数を捨てて全ワーカーから探し直していた。

## 対応（`src/active_workers.rs` の `Policy`）

- **負荷の切れ目（0.5 秒、`SPREAD_IDLE_TICKS`）で全ワーカーへ広げる。** 新しい接続をどのワーカーでも受けるので、
  切れ目の後に来た HTTP/2 の接続の束は全ワーカーに散る。広げる前の N は覚えておく（`resume`）。接続は動かさない。
  接続が 1 本も残っていなければ 0.5 秒を待たず、要求が止んだ最初の周回で広げる（動かす接続が無いので広げて失うものが無い。
  lab34 のログでは負荷の間の切れ目は 6〜9 周回で、閾値ちょうどの 5 周回の回もあり、少し短ければ広げ損ねていた）。
- **負荷が戻ったら、覚えた N へすぐ縮めてみる（`ProbeKind::Resume`）。** HTTP/1.1 の接続は応答の区切りで張り直して動き、
  スループットが落ちなければ残す（従来の 5 秒を待たずに前の本数で受ける）。外したワーカーが公平な割合の半分以上を
  受けたまま（HTTP/2・WebSocket 等の動かない接続）なら全ワーカーへ戻して当分は縮めない。遅くなったら（前の負荷より重い）
  全ワーカーへ戻していつもどおり探す（失敗に数えない）。接続が急増して戻ったとき（準備運転の後の本番）は使わず探し直す。
- **測定の途中で負荷が止んだ試しはやめる**（変える前の本数へ戻し、失敗に数えない）。切れ目の前の本数を試していたなら、
  次に負荷が戻ったときにまた試す（HTTP/2 の準備運転の後の本番）。
- **接続の数の基準は負荷の無い間は下げない**（急増は前の負荷の数と比べる）。
- 接続を動かさない変更（試しをやめた・戻した）では、残っている「閉じる接続の割り当て」を取り消す（戻したワーカーの
  接続を閉じない）。

データプレーンは変わらない（制御スレッドの判断だけ）。負荷の無い状態が 5 秒続いたら失敗の待ちを捨てるのは従来どおり。

## テスト

- `active_workers` の単体試験（24 件。追加・更新 8 件）: 切れ目で広げて戻った負荷で前の本数を試す・接続が無くなればすぐ広げる・
  動かない接続なら全ワーカーへ戻す・遅くなったら失敗に数えず探し直す・測定中に負荷が止んだ試しをやめる・短い準備運転の後も
  前の本数を覚えている・急増して戻ったら探し直す・要求の少ないときは縮めずに広げる。
- 計測（aofish、同じバイナリを環境変数で従来の制御に切り替えて交互に。lab32〜34）: 下の表。

## 計測

aofish（16 論理 CPU）、`tools/perf/run_perf.sh` のとおり（wrk の準備運転 → wrk `-t4 -c100 -d10s` × 3 → h2load の準備運転 →
h2load `-t4 -n 30000 -c100 -m10` × 3）。同じ一時的なビルドを環境変数で従来の制御に切り替えて交互に測った（制御の判断を WARN で
ログへ出すビルド。lab34、3 ラウンド × 3 反復）。

| 構成 | | 従来 | B-366 | 比 |
|---|---|---:|---:|---:|
| `h2_1_proxy_cache` | HTTP/1.1（9 回の中央値） | 84.0k | 83.7k | 1.00 |
| | HTTP/2 の 1 回目（各ラウンド） | 27.6k・26.2k・26.9k | 35.1k・35.4k・31.5k | 1.30 |
| | HTTP/2（9 回の中央値） | 35.8k | 37.7k | 1.05 |
| `h2_1_feat_proxy` | HTTP/1.1（9 回の中央値） | 42.6k | 42.6k | 1.00 |
| | HTTP/2 の 1 回目（各ラウンド） | 28.1k・35.3k・32.1k | 30.4k・36.1k・34.5k | 1.07 |
| | HTTP/2（9 回の中央値） | 37.5k | 36.3k | 0.97 |

- ログでは全部の回で判断が設計どおりだった。wrk の 2・3 回目の前の切れ目（負荷のコンテナの起動の約 0.6 秒）で全ワーカーへ広げ、
  負荷が戻った最初の周回で前の本数（4・5・8 本）へ縮めてそのまま残した。h2load の準備運転の試しは負荷が止んでやめ（失敗に
  数えない）、HTTP/2 の 1 回目の接続の束は全ワーカーで受けた。そこで縮めてみた試しは、外したワーカーの接続が動かないので
  全ワーカーへ戻した。
- lab33（`h2_1_proxy_cache`、2 ラウンド × 3 反復）も同じ: HTTP/1.1 の中央値 83.0k → 86.3k、HTTP/2 の 1 回目 27.9k・20.9k →
  37.5k・36.1k。
- lab32（ログを出さない、判断は同じビルド。2 ラウンド × 3 反復）だけは、B-366 の HTTP/1.1 が `h2_1_proxy_cache` で 83.2k →
  68.8k、`h2_1_feat_proxy` で 43.5k → 40.0k と低かった（2 ラウンド目に偏る）。ログを出すビルドの 5 ラウンド（lab33・lab34）では
  再現していない。ログを出さないビルドでやり直した lab36（3 ラウンド × 3 反復）では HTTP/1.1 の中央値が `h2_1_proxy_cache` 83.2k
  （従来 84.3k）、`h2_1_feat_proxy` 45.3k（従来 37.9k）で、低い回は両方の制御に出た（B-366 は `h2_1_proxy_cache` の 1 ラウンド目の
  71〜75k・`h2_1_feat_proxy` の 3 ラウンド目、従来は `h2_1_feat_proxy` の 1・3 ラウンド目の 37〜38k）。制御による差ではない。
  HTTP/2 の 1 回目は `h2_1_proxy_cache` で 37.0k・36.4k・34.6k（従来 28.4k・25.2k・29.0k）。
- 接続が残ったまま（keep-alive の接続を保ったまま要求が止む）切れ目が 0.5 秒より短いと広げない（従来の 5 秒と同じく、その後の
  HTTP/2 の接続の束は縮めた本数で受ける）。`run_perf.sh` の負荷の間の切れ目は負荷のコンテナの起動の時間（0.6〜0.9 秒）で、
  lab32〜36 のビルド（接続の無いときにすぐ広げる規則の前）でも計測したすべての回で広げた。
