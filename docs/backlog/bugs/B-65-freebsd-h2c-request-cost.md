# B-65: FreeBSD の h2c 平文が対 nginx 0.68 に留まる（パス解決以外の要因）

- 優先度: P2
- 状態: 完了
- 関連: F-153（静的配信のパス解決をカーネル封じ込めへ）、F-146、B-26

## 事象

FreeBSD 14.3 amd64（QEMU/KVM、veil 2 コア固定・負荷生成 2 コア）で
**h2c 平文の静的配信が対 nginx 0.68** に留まる（3 バイト応答、`-c64`）。

| シナリオ（3B） | veil | nginx | 比 |
|---|---|---|---|
| h2c 平文 | 10,009 | 14,773 | **0.68** |
| HTTP/2 TLS | 10,306 | 11,877 | 0.87 |
| HTTP/1.1 TLS | 6,324 | 10,380 | 0.61 |

## パス解決が原因**ではない**ことは確定済み（F-153）

F-153 で静的配信のパス解決を `canonicalize()` からカーネル封じ込め
（`O_RESOLVE_BENEATH`）へ置き換え、**FreeBSD でも `__realpathat` が
1 回/リクエスト → 0 回になった**ことを `truss` で確認済み。
それでも比は 0.65 → 0.68 とほぼ変わらなかった。

理由は、**FreeBSD の `canonicalize` は元から単一 syscall（`__realpathat`）**であり、
削れたのが 1 syscall だけだったため（Linux の glibc は同じ処理に `readlink` を
パス深さぶん = 実測 7 回消費しており、そちらでは +17% の効果が出た）。

## 残る候補（`truss -f -c`、2,000 h2c リクエスト、F-153 適用後）

```
openat        2,000   (1 回/リクエスト)
fstatat       2,002   (1 回/リクエスト)
write         4,000   (2 回/リクエスト)   ← F-74 のフレーム連結が効いていない？
read          9,445   (約 4.7 回/リクエスト)
__realpathat      2   (起動時のみ = F-153 で除去済み)
```

- **`write` が 2 回/リクエスト**: HTTP/2 は F-74 で HEADERS + DATA を 1 バッファへ
  連結して **1 回の書き込み**にしているはず。h2c（平文）経路で連結が効いていない
  可能性がある。**最初に確認すべき候補。**
- **`read` が約 4.7 回/リクエスト**: 多い。空読み（`EAGAIN`）を含んでいる可能性。
- **offload のクロススレッド往復**: `openat`+`fstatat` のために毎リクエスト発生する。
  ただし Linux では `open_file_cache` を有効にしても +5% しか動かなかったため
  （F-153 の追加検証）、支配要因ではない可能性が高い。

## 原因確定（2026-08-16）: `write` 2 回は HTTP/2 フレーミングではなく **offload の eventfd 起床**だった

当初「`write` 2 回/リクエスト = F-74 のフレーム連結が効いていない疑い」と書いたが、
**これは誤りだった**。`strace -e trace=write,writev` で書き込みの中身を見たところ、

```
write(13, "\1\0\0\0\0\0\0\0", 8) = 8      ← eventfd への 8 バイト書き込み
```

**20 リクエストに対し write は 40 回、その全てが 8 バイトの eventfd 書き込み**であり、
**実データの `write` は 1 回も無い**（レスポンス本体は io_uring 経由で送出されるため
`write(2)` としては現れない）。つまり F-74 のフレーム連結は正しく効いている。

`write` 2 回/リクエストの正体は **`runtime::offload` のクロススレッド完了通知**であり、
**静的配信が 1 リクエストで offload を 2 回呼んでいる**ことを意味する:

1. `cache::get_file_info*` → `fetch_file_info`（パス解決 + stat）
2. `cache::get_or_load_content_cache` → `std::fs::read`（本体読み込み。
   `static_file_cache` は既定オフのため毎回ここを通る）

F-153 は 1 の**中の syscall 数**を削ったが、**往復の回数は 2 回のまま**だった。

## 改修方針: 2 回の offload 往復を 1 回に統合する

F-153 の `open_beneath` は**既にファイルを open して `fstat` している**。
その同じ offload クロージャの中で本体まで読んでしまえば、往復は 1 回で済む
（F-153 のチケットで「設計との差分（実装で見送った点）」として残していた
fd 再利用そのもの）。

- メタデータと本体を **1 回の offload** で取得する API を追加する。
- 両方のキャッシュ（`open_file_cache` / `static_file_cache`）がヒットする場合は
  **offload を 1 回も呼ばない**（従来どおり）。
- HEAD や 404 判定など**本体が要らない経路では従来どおりメタデータのみ**取得する
  （無駄な読み込みを増やさないこと）。

## 調査の入口

1. `write` が 2 回になっている理由（F-74 の連結バッファが h2c 経路で使われているか）。
   **1 変数の実験**: HTTP/2 over TLS では `write` が何回か数え、h2c と比較する。
2. `read` 約 4.7 回/リクエストの内訳（`truss` で戻り値を見て `EAGAIN` の割合を測る）。
3. nginx 側の同条件の syscall プロファイルと突き合わせる。

## 検証結果（2026-08-16）

### 機構が効いていることの直接確認

`strace -e trace=write`（write = offload の完了通知 eventfd 起床）で 20 リクエスト:

| | offload 往復 |
|---|---|
| 改修前 | **40 回（2 回/リクエスト）** |
| 改修後 | **20 回（1 回/リクエスト）** |

### テスト

- `cargo test --lib --features full`: **868 passed / 0 failed**（**3 回連続で安定**）
- `cargo test --test integration_tests --features full`: 54 passed
- E2E `full`（io_uring）/ `full,epoll`（reactor）: いずれも **544 passed / 0 failed**
- ビルド・clippy（`full` / `--no-default-features`）: warning 0

### スループット（Linux、**セキュリティ機能を有効にした状態**で交互 A/B、5 ラウンド）

`seccomp(filter)` + `Landlock` を有効にし、各計測前にウォームアップ 5,000 リクエスト。
3 バイト応答・`-c100 -m10`、veil 2 スレッドを `taskset -c 0,1`、負荷生成は別コア。

| ラウンド | 改修前 | 改修後 | nginx |
|---|---|---|---|
| 1 | 6,484 | **8,107** | 11,415 |
| 2 | 6,627 | **8,363** | 11,296 |
| 3 | 6,654 | **8,318** | 11,686 |
| 4 | 6,599 | **8,434** | 11,445 |
| 5 | 6,549 | **8,195** | 11,416 |
| **中央値** | **6,599** | **8,318（+26%）** | 11,416 |

**5 ラウンドすべてで改善**。ばらつきも小さい（改修前 ±1.3%・改修後 ±2%）ため、
これまでのノイズの大きい計測（±20%）と違い効果量を信頼できる。
対 nginx 比は **0.58 → 0.73**。

（改修前の値がこれまでの計測より低いのは、本計測が **seccomp + Landlock を有効にした
状態**だからである。セキュリティ機能のコストは約 15%。ベンチマークは本番に近い条件で
測るべきという方針に従い、以後この構成を標準とする。）

### 残るギャップ（正直な評価）

対 nginx 0.73 でまだ届いていない。offload 往復は 1 回まで減ったが、
**1 回残っている**（`open_file_cache` + `static_file_cache` を両方有効にすると
この 1 回も消えて offload ゼロになる）。既定でゼロにするにはキャッシュを既定オンに
する必要があり、それは `valid_duration_secs` の間ファイル更新が反映されなくなる
**観測可能な挙動変更**のため、性能だけを理由に既定を変えていない
（`docs/perf/README.md` の運用指針を参照）。

## 注意

**h2c は「TLS の暗号コストが無いぶんリクエスト単価がそのまま露出する」計測系**であり、
ここで見つかる無駄は HTTP/1.1・HTTP/2・HTTP/3 のすべてに効く（F-153 と同じ構図）。
h2c 固有の問題として扱わないこと。
