# B-65: FreeBSD の h2c 平文が対 nginx 0.68 に留まる（パス解決以外の要因）

- 優先度: P2
- 状態: 未対応（要調査）
- 関連: F-153（静的配信のパス解決をカーネル封じ込めへ）、F-146、B-26

## 事象

FreeBSD 14.3 amd64（QEMU/KVM、veil 2 コア固定・負荷生成 2 コア）で
**h2c 平文の静的配信が対 nginx 0.68** に留まる（3 バイト応答、`-c64`）。

| シナリオ（3B） | veil | nginx | 比 |
|---|---|---|---|
| h2c 平文 | 10,009 | 14,773 | **0.68** |
| HTTP/2 TLS | 10,306 | 11,877 | 0.87 |
| HTTP/1.1 TLS | 6,324 | 10,380 | 0.61 |

## パス解決が原因**ではない**ことは確定済み（F-153）

F-153 で静的配信のパス解決を `canonicalize()` からカーネル封じ込め
（`O_RESOLVE_BENEATH`）へ置き換え、**FreeBSD でも `__realpathat` が
1 回/リクエスト → 0 回になった**ことを `truss` で確認済み。
それでも比は 0.65 → 0.68 とほぼ変わらなかった。

理由は、**FreeBSD の `canonicalize` は元から単一 syscall（`__realpathat`）**であり、
削れたのが 1 syscall だけだったため（Linux の glibc は同じ処理に `readlink` を
パス深さぶん = 実測 7 回消費しており、そちらでは +17% の効果が出た）。

## 残る候補（`truss -f -c`、2,000 h2c リクエスト、F-153 適用後）

```
openat        2,000   (1 回/リクエスト)
fstatat       2,002   (1 回/リクエスト)
write         4,000   (2 回/リクエスト)   ← F-74 のフレーム連結が効いていない？
read          9,445   (約 4.7 回/リクエスト)
__realpathat      2   (起動時のみ = F-153 で除去済み)
```

- **`write` が 2 回/リクエスト**: HTTP/2 は F-74 で HEADERS + DATA を 1 バッファへ
  連結して **1 回の書き込み**にしているはず。h2c（平文）経路で連結が効いていない
  可能性がある。**最初に確認すべき候補。**
- **`read` が約 4.7 回/リクエスト**: 多い。空読み（`EAGAIN`）を含んでいる可能性。
- **offload のクロススレッド往復**: `openat`+`fstatat` のために毎リクエスト発生する。
  ただし Linux では `open_file_cache` を有効にしても +5% しか動かなかったため
  （F-153 の追加検証）、支配要因ではない可能性が高い。

## 調査の入口

1. `write` が 2 回になっている理由（F-74 の連結バッファが h2c 経路で使われているか）。
   **1 変数の実験**: HTTP/2 over TLS では `write` が何回か数え、h2c と比較する。
2. `read` 約 4.7 回/リクエストの内訳（`truss` で戻り値を見て `EAGAIN` の割合を測る）。
3. nginx 側の同条件の syscall プロファイルと突き合わせる。

## 注意

**h2c は「TLS の暗号コストが無いぶんリクエスト単価がそのまま露出する」計測系**であり、
ここで見つかる無駄は HTTP/1.1・HTTP/2・HTTP/3 のすべてに効く（F-153 と同じ構図）。
h2c 固有の問題として扱わないこと。
