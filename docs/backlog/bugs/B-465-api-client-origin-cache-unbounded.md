# B-465: API の HTTP クライアントが URL のオリジンを上限なく表に持ち続け、期限の切れた空き接続も別のオリジンへ要求しない限り残していた

**状態: 修正済み（fix/security-scan-fable-max、2026-11-18）**

fix/security-scan-fable-max のセキュリティスキャン（`CLAUDE-SECURITY-20261115-030813`）の指摘
「API HTTP client caches every distinct URL origin forever, with no size limit and no eviction」
から確認。

## 事象

- `api::client::Client::resolve` は、新しい `scheme://authority` ごとにオリジン（ホスト名を 5 回ほど持つ）を
  クライアントの表へ足し、上限も追い出しも無かった（DNS・接続に失敗しても残る）。ホスト名の長さも見ていなかった。
  要求から作った URL を長く使う 1 つのクライアントへ渡すアプリ（Webhook・リンクのプレビュー）では、長いホスト名を
  変えながら送るだけでメモリを使い切れた。
- HTTP/1.1 の空き接続の表（ワーカーごと）も、鍵（オリジン）は消さず、期限の切れた接続は同じオリジンへ次に要求する
  まで残った（fd を持ち続ける）。

## 対応

- オリジンの表は 1024 件で空にして作り直す（`Origin` は `Arc` で使用中の要求は持ち続け、接続のプールは
  `pool_key` の文字列で引くので同じ接続を使う）。ホスト名は 253 バイトまで、オリジンの部分は 1024 バイトまで。
- 空き接続の表は、空いた鍵を消し、新しいオリジンを足す前に期限の切れた接続と空の鍵を全部捨てる。オリジンの数は
  1024 まで（超えたら新しいオリジンの接続はプールせずに閉じる）。

## テスト

- `api::client::tests::origin_cache_is_bounded`（長いホスト名は URL の誤り、表は上限を超えない、作り直しても
  同じプールの鍵）。
