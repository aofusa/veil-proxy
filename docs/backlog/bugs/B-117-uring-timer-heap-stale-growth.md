# B-117: io_uring のタイマーヒープがキャンセル済みエントリで「要求レート × タイムアウト」まで膨らむ

**状態: 完了（feat/f185-memory-leak-check）**

## 事象

F-185 のリーク試験（`tools/perf/leak_check.sh`）で、設定リロードのシナリオ（HTTP/2 TLS → 上流プロキシの軽い負荷を
流しながら SIGHUP を繰り返す）の生存ヒープが、生存アロケーション数は一定のまま数十〜数百サイクルごとに +6MB
跳ねた（run1: サイクル 22、run2: サイクル 56 と 96。ワーカー 2 本で 1 回ずつ）。数が増えずにバイトだけ増えるのは、
1 つの容器が容量を倍にした形。512KB 以上の確保にバックトレースを出す一時ビルドで調べると、2 本のワーカーで
`runtime::uring::timer::TimerState::register` のヒープ（`BinaryHeap<Reverse<(Instant, u64)>>`）が
384KB → 768KB → 1.5MB → 3MB → 6MB と倍々に伸びていた（呼び出し元は `proxy::h2_relay_backend_response`）。

## 原因

B-72 でカーネルの `IORING_OP_TIMEOUT` を張るのをやめ、ユーザ空間の最小ヒープにした。I/O が先に終わって
`Sleep` が drop されたときはスロットだけ解放し、ヒープのエントリは stale として残す（デッドラインに達したときに
捨てる）。`timeout(READ_TIMEOUT, read)` のように I/O がほぼ必ず先に終わる使い方では、キャンセル済みエントリが
30〜60 秒ヒープに残るため、ヒープの長さは「ワーカーあたりの要求レート × タイムアウト秒数」に比例する。

負荷が一定ならこれ以上は増えない（リークではない）が、

- Vec の容量は縮まないので、ピーク時の大きさのまま残る（今回はワーカーあたり 6MB。ワーカーあたり 5 万 rps・
  タイムアウト 60 秒なら 1 ワーカーで 70MB 規模）。
- push / pop は O(log n) で、n の大部分が死んだエントリになる。

reactor 側は同じ問題を eba17c7 で直していた（キャンセル時に、ヒープが生存数の 2 倍 + 1024 を超えたら生存
エントリだけで作り直す）。そのコメントは「io_uring 側で B-72 が直したのと同型の問題」としていたが、io_uring 側には
圧縮が入っていなかった。

## 改修

`src/runtime/uring/timer.rs` に reactor 版と同じ圧縮を入れた。

- スロットに登録時のデッドラインを持たせ、Free 以外のスロット数（`live`）を数える。
- `cancel` で `heap.len() > 2 * live + 1024` なら、Armed のスロットだけでヒープを作り直す（既存の Vec を使い
  回すので確保しない。圧縮 1 回は O(n) だが、次の圧縮までに n/2 回以上のキャンセルがあるので償却 O(1)）。
- カーネルへのタイマーのアーム（park 直前に最近接の 1 本だけ）・満了の扱いは変えない。

単体テスト `cancelled_timers_do_not_accumulate_in_heap` と `compaction_keeps_live_timers` を io_uring 側にも追加した。

## 計測（`tools/perf/alloc_ab.sh`、Linux x86_64・io_uring・`full`、ワーカー 2、5 ラウンド交互）

| 負荷 | rps | 要求あたり CPU | 負荷中ピーク RSS |
|---|---|---|---|
| h1 TLS 54KB | +0.5% | −1.0% | −5.1% |
| h1 TLS 3B | +0.3% | +1.7%（下記） | −19.4% |
| h2 TLS 3B | −0.9% | +5.1%（下記） | −18.9% |
| h1 TLS → 上流 3B | +0.1% | −1.2% | −35.4% |
| h2c → 上流 54KB | −0.2% | +0.2% | −30.0% |
| TLS 1.2 / 1.3 接続チャーン | +0.1% / +0.1% | −2.4% / −0.8% | −33.8% / −39.7% |

負荷後の RSS は 75.2MB → 45.0MB（−40%）、アイドル RSS は同じ（17.2MB）。失敗要求はすべて 0。

alloc_ab は毎ラウンド同じ順（修正前 → 修正後）で回すため、CPU が高く出た 2 つを順番を入れ替えて 3 回ずつ
（計 6 回）測り直した: h2 TLS 3B は修正後のほうが要求あたり CPU −0.8%・rps +0.9%、h1 TLS 3B は +0.6%・−0.4%。
上の差は実行順による偏りで、退行は無い。
