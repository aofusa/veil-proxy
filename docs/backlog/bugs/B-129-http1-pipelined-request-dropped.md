# B-129: HTTP/1.1 のパイプラインで 2 つ目以降の要求が失われ、接続が止まる

**状態: 完了（feat/api-roadmap-impl、2026-10-14。F-205 の E2E を書いていて発見）**

## 症状

1 回の書き込みで 2 つの要求を送る（パイプライン）と、1 つ目の応答だけが返り、2 つ目には何も返らない
（接続はアイドルタイムアウトまで止まる）。平文・TLS とも、io_uring・epoll とも同じ。

```
printf 'GET / HTTP/1.1\r\nHost: x\r\n\r\nGET / HTTP/1.1\r\nHost: x\r\n\r\n' | nc 127.0.0.1 8081   # 応答は 1 つ
```

## 原因

`proxy::handle_requests` はヘッダを切り出した後の蓄積を **すべて** 現在の要求の本文の先頭（`initial_body`）として
`handle_backend` へ渡し、蓄積を空にしていた。本文の無い GET では 2 つ目の要求がまるごと 1 つ目の本文として扱われて
捨てられる。またループの先頭は蓄積に完全な要求があっても必ずソケットを読みにいくため、パイプラインの要求を
後ろに残したとしても、もう届かないデータを待ち続ける。

## 修正

- 本文の長さが決まっている要求（chunked・WebSocket 以外）は、`Content-Length` を超えた分を次の要求として残し、
  応答の後で蓄積へ戻す。
- 蓄積に次の要求のヘッダ（`\r\n\r\n`）が揃っていれば、ソケットを読まずに処理する。
- chunked の要求の後ろのパイプラインは対象外（今までどおり）。

## 試験

`tests/e2e_tests.rs::test_f205_keepalive_direct_read_and_fallback` の「1 回の書き込みに 3 要求」（io_uring・epoll）。
修正前は 2 つ目の応答を 5 秒待って失敗する。
