# B-500: 接続の集約（F-303）が、要求をパイプラインで送ってくる HTTP/1.1 の接続を動かし、クライアントが送っている途中の要求を失わせる

**状態: 完了（2026-11-25、feat/httparena-perf。F-317 の aofish の計測で見つけた）**

## 事象

- aofish（io_uring のビルド、HttpArena のエントリと同じ設定）で、Proxy-Wasm のフィルタが答える `/pipeline` へ veil-load の
  HTTP/1.1（256 接続、16 本ずつのパイプライン）を当てると、B-499 を直した後も 5 秒の計測ごとに約 930 要求を失った。veil-load の
  張り直しは 62 回で、失った要求は張り直し 1 回につき 15 本（パイプラインの深さ − 1）。
- 原因: 接続の集約が既存の接続を動かすとき、HTTP/1.1 は「本文の無い要求で、後ろに次の要求が届いていない（蓄積が空）」ときだけ
  `take_shed()` で応答の後に閉じる。しかしパイプラインで送るクライアントは応答を待たずに次の要求を送っているので、サーバの蓄積が
  その瞬間に空でも、次の要求はソケットの中か送る途中にある。閉じるとそれらは応答されずに失われる（RFC 9112 §9.3.2: 閉じられた
  接続のパイプラインの要求はクライアントが送り直す。veil-load は失敗として数える）。
- Wasm のルートだけで出たのは、この計測では Wasm の重い経路のときだけ集約が接続を動かしたため（`Respond` の `/plain3` では張り直し 0）。

## 対応

- `proxy/h1.rs` の要求のループ: 本文の無い要求の後ろに次の要求が届いていたことのある接続（`pipelining_seen`）は、
  集約のために閉じない（`take_shed()` を呼ばない。動かす接続は他の接続から選ばれる）。パイプラインで送るクライアントは
  ベンチマーク以外では少なく、集約が動かせない接続が残っても効率が下がるだけで要求は失わない。
- 試験: aofish の計測（veil-load の `--pipeline 16`）で、io_uring の Wasm の `/pipeline` の失った要求と張り直しが 0 になること
  （F-317 の計測の記録）。
