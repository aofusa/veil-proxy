# B-339: epoll のレベルトリガで起こす順が届いた順にならず、CPU を使い切る負荷で一部の要求が 2 周分待つ

**状態: 修正済み（feat/v0120-perf、2026-11-07）**

親: [F-297](../features/F-297-core-limited-latency.md)（epoll をレベルトリガの常時武装にした変更）。

## 事象

最終の A/B（`api_ab.py --scenario json`、epoll、5 ラウンド）で、gzip の行はスループットが main と同じ（中央値 62,041 / 60,970 rps）なのに、
p99 が 5 ラウンドとも悪かった（main 6.1〜6.4 ms、改修後 8.1〜9.4 ms）。p50 と p90 はほぼ同じで、伸びたのは p90 より先だけだった。
io_uring のビルドは同じ行で p99 が良くなっている（6.3 → 5.1 ms）。

## 原因

CPU を使い切っているワーカーでは、実行器は `epoll_wait` が返した束を全部実行してから次の `epoll_wait` を呼ぶ。gzip の行では
1 要求 125 µs、1 ワーカーに 32 接続ほどで、1 周が約 4 ms になる。起こす順は `epoll_wait` が返した順だった。

レベルトリガのカーネルは、報告した fd を準備済みリストの末尾へ戻し、次の走査まで置いておく（`ep_send_events`）。その間に次のデータが
届いても、リストにつながっている fd はつなぎ直さない（`ep_poll_callback` はつながっていない fd だけを末尾へ足す）。次の走査では、
前の回に報告して今も読める fd を **前の回の報告の順** で返し、その後に、前の回の走査で読めずに外れた fd を、データが届いた順で返す。

束の最後に応答した接続は、次の要求が届く前に次の走査が終わるので、その走査でリストから外れる。次の要求が届くと末尾へつながり、
その次の束では、前の束で応答した全部の接続（どれも次の要求を送ってきている）の後ろに回る。この接続は次の束でも最後に応答するので、
毎回 2 周（約 8 ms）待つ。1 ワーカーに 32 接続なら要求の 3% ほどで、p99 が p50 の 2 倍になる形と合う。

main は `EPOLLONESHOT` で、報告した fd はリストに戻らず、データが届いた時点か待ち直しの `EPOLL_CTL_MOD` の時点でつながった
（ほぼ届いた順）。io_uring は完了の順に起こす。kqueue は `EV_ONESHOT` で、WSAPoll は待つたびに配列を渡すので、どちらも当てはまらない。

## 最初の修正（採らなかった）

前の回にも報告した fd を後ろへ回す（`epoll_wait` の回を fd ごとに残し、イベントの配列を 2 回見る）。p99 は変わらず（8.4 ms 対 8.4 ms、
5 ラウンドの交互 A/B）、飽和のスループットは 0.97〜0.98 倍になった。

前の回にも報告した fd の、カーネルの返す順は前の回の **報告の順** で、こちらが **起こした順** ではない。前へ回した接続は、次の走査では
報告の順の最後にいるので（前の回にカーネルが最後に返した）、次の束で最後に起こされて 2 周待つ。2 回に 1 回は 2 周待つことになり、
1 ワーカーに 32 接続なら要求の 1.6% で、p99 は動かない。

## 修正

読み取りの待ちを、待ち始めた順に起こす。

- `register` は読み取りの待機者を置くたびに、ワーカーごとの通し番号を `FdRecord::read_wait_seq` に書く。
- `park` は `epoll_wait` が 2 件以上返したら、読み取りの待機者のいるイベントを待ち始めたのが古い順に並べてから配送する
  （`wake_order`。経過 = 今の通し番号 − 待ち始めた番号。待機者のいない読み取り・書き込みのイベントは先に回す）。
  並べ替えはスタックの配列で行い、確保しない。1 件のときは何もしない。

閉ループの相手では、待ち始めた順（応答を送った順）は次の要求が届いた順とほぼ同じで、`EPOLLONESHOT` のときの順に戻る。
追加はイベントごとの表の参照 1 回と束の並べ替えで、システムコールは増えない。

## テスト

`runtime::reactor::executor::tests::read_waits_are_woken_oldest_first`: pipe を 2 本使い、1 回目は a、b の順に待ってデータを入れて報告させる
（カーネルのリストに a、b の順で残る）。読み切ってから b、a の順に待ち直し、データも b、a の順に入れる。カーネルは前の回の順（a、b）で
返すので、並べ替えなしの起こす順は `[1, 2, 1, 2]`、修正後は `[1, 2, 2, 1]`（並べ替えを外して失敗することを確かめた）。

### identity の差（コードの配置）

json の identity の行だけ、修正後のビルドが修正前より 7〜12% 遅かった（交互 A/B を 3 回。接続数 64・128・512 でも 0.92〜0.94 倍で、
接続の作業集合の大きさでは変わらなかった）。並べ替えを環境変数で切れるようにしたビルドを 1 つ作り、同じバイナリの中で比べた
（4 ラウンドの中央値）。

| ビルド | rps | p99 |
|---|---:|---:|
| 修正前 | 170,653 | 3.62 ms |
| 修正後 | 144,556 | 4.62 ms |
| 修正後 + 切り替え（並べ替えあり） | 156,725 | 2.80 ms |
| 同じバイナリで並べ替えなし | 157,274 | 3.92 ms |

同じバイナリの中では、並べ替えの有無でスループットは変わらず（0.99×）、p99 は 3.92 → 2.80 ms になった。差を作っていたのは
ビルドごとのコードの配置で、`perf stat`（ユーザ空間）では 1 要求あたりの命令数は同じ（11 万前後）まま、サイクルが 6.1 万 → 7.3 万、
フロントエンドの停止が 2.5 万 → 3.35 万サイクル、分岐予測ミスが 340〜390 → 516〜534 回に増えていた（L1 のキャッシュミスは同程度）。
ホットな関数は serde_json の直列化（全体の 37%）で、修正の入ったコードは通らない。

最終候補（[F-301](../features/F-301-api-response-single-write.md) も入れたもの）でも同じ切り替えで比べた（5 ラウンドの中央値）。
並べ替えありが 186,426 rps・p99 2.51 ms、なしが 185,706 rps・p99 3.00 ms で、スループットは同じ（1.00×）だった。
