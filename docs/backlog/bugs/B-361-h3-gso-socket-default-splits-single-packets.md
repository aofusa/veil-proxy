# B-361: HTTP/3 の GSO を有効にすると、1200 バイトを超える単発のパケットがカーネルで分割されていた

**状態: 修正済み（feat/beat-nginx、2026-11-12）**

[F-305](../features/F-305-h3-gso-default.md) で `[http3] gso_gro_enabled` を既定で有効にする前の確認で見つけた。

## 事象

`QuicUdpSocket::configure_gso_gro` は GSO に対応しているかを確かめるため、ソケットに `UDP_SEGMENT = 1200` を
設定していた。ソケット単位の `UDP_SEGMENT` は cmsg を付けない送信すべての既定のセグメント長になるので、cmsg の無い
単発の送信（`segments == 1` のエントリ）のうち 1200 バイトを超えるものが、カーネルで 1200 バイトと残りの 2 つの
データグラムに分けられていた（QUIC のパケットとしては壊れており、相手は捨てる）。

- 経路 MTU の探索（`discover_pmtu = true`、既定）の探索のパケットは常に単発で 1200 バイトを超えるので必ず壊れ、
  探索が一度も成功せずにパケットの大きさが 1200 バイトに留まっていた（GSO 無しでは 1452 バイトまで上がる）。
- 経路 MTU が上がった後に 1 接続の送り出しがちょうど 1 パケットで終わった場合も同じく壊れる。

計測（aofish の lab13、h2load の HTTP/3 で 54KB の静的配信）では、GSO を有効にした veil のパケットが nginx
（1452 バイト）より約 2 割多く、負荷側の CPU を要求あたり約 2 割多く使わせていた（負荷側が飽和する条件では
そのまま rps の差になる。veil 33〜35k・nginx の `quic_gso on` 41〜44k）。

ソケットが GSO を拒む経路（[F-305](../features/F-305-h3-gso-default.md) の自動の退避）でも、ソケット単位の値が
残っていると単発の送信まで GSO として扱われて拒まれ、退避しても送れなかった。

## 対応

対応の確認は `UDP_SEGMENT = 0`（既定の分割なし）の設定で行う（対応しないカーネルは `setsockopt` が失敗する）。
束ごとのセグメント長は従来どおり sendmsg の cmsg で渡す。

## テスト

- 単体: `gso_socket_keeps_single_large_packets_whole`（GSO を有効にしたソケットから単発の 1350 バイトと 1300 バイト × 3 の
  束を送り、1350・1300・1300・1300 の 4 つのデータグラムとして届く。修正前は 1200・150・1300・1300 になって失敗する）。
