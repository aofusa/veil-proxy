# F-303: 接続を負荷に見合う本数のワーカーへ集める（コンテナ間の HTTP/1.1 で nginx に劣る）

**状態: 実装中（feat/beat-nginx）**

## 問題

v0.12.0 のフルスイート（aofish、Docker のコンテナ間、wrk 4 スレッド・100 接続）で、HTTP/1.1 + TLS の静的配信
（`h2_1_ktls_0_lb_kernel_ofc_1`、54KB）が nginx を下回っていた（veil 44.1〜44.7k、nginx 57.7〜63.3k req/s）。
同じ構成の HTTP/2 と、端末の上の計測（ループバック・コアを分けた構成）では veil が上回っている。

ワーカー数を固定して掃引すると、原因はワーカーの数そのものだった（lab1・lab2。16 論理 CPU = 8 コア × SMT、
サーバ・wrk・上流はすべて同じ WSL2 の VM の中のコンテナ）。

| サーバ | ワーカー | req/s | サーバ CPU/要求 | コンテキストスイッチ/要求 |
|---|---:|---:|---:|---:|
| nginx | 16（auto） | 48.4〜56.9k | 138〜163 µs | 0.16〜0.21 |
| veil | 16（既定） | 37.2〜43.5k | 93〜107 µs | 0.54〜0.57 |
| veil | 8 | 52.1〜55.3k | 76〜79 µs | 0.34〜0.35 |
| veil | 4 | 75.1〜83.2k | 44〜50 µs | 0.04〜0.05 |
| veil | 2 | 44.8〜47.9k | 40〜43 µs | 0.00 |

100 接続を 16 本へ散らすと、各ワーカーは数件の要求を処理するたびに眠り、起きる（io_uring の `submit_and_wait`・
futex・スケジューラの移動）。1 要求あたりのサイクルの半分以上がこの往復で、ワーカーを 4 本に絞ると 1 要求の CPU は
半分以下になり、スループットは 1.9 倍になった。接続数を変えても（25・100・400・1600）同じ傾向で、最適な本数は
負荷と仕事の重さで変わる（圧縮のように重い仕事は 4 本では CPU が足りない。lab4）。

## 対応

リスナー（Linux の TCP）ごとに「新しい接続を受けるワーカーの本数 N」を実行時に決め、SO_REUSEPORT のグループへ
付ける CBPF のプログラムを差し替えて、新しい接続をグループの先頭の N 本へだけ振り分ける。

1. **計測**（`src/active_workers.rs`）: ワーカーごとに、眠っていた時間（実行器の park の前後。`park_begin`・`park_end`）・
   応答の数（`logging::log_access` の `note_response`）・接続の数（`ConnectionTicket`）を原子的な累計で持つ。
   ホットパスの追加は Relaxed の加算だけで、要求ごとの確保・ロック・syscall は無い。
2. **振り分け**（`src/system.rs`）: `create_reuseport_cbpf_range_program(base, count)` は `base + hash % count` を返す
   （`base = 0` のときは従来の 5 命令と同じ）。最初のワーカーのリスナーを複製してグループの fd として持ち、制御スレッドが
   プログラムを付け替える（受理は止まらない）。グループの添字とワーカーの順を一致させるため、ワーカーは順番に bind する。
3. **既存の接続の移動**: N を変えるとき、HTTP/1.1 のキープアライブの接続は、外したワーカー（縮める）・広げる前のワーカー
   （新しい本数に見合う割合）が応答の区切りで `Connection: close` を返して閉じる（`take_shed`）。クライアントは張り直し、
   新しい振り分けで受ける。広げるときは、張り直しが落ち着くまで増やしたワーカーへだけ振り分ける（古い側へ戻らない）。
   HTTP/2 の接続は動かさない。
4. **制御**（`Policy`、100ms ごと）: 起動時は全ワーカー。
   - 使用率が低い（0.80 以下が 0.5 秒）とき、目標の使用率 0.85 に見合う本数まで、ただし 1 回に半分までに縮めてみて、
     スループットが 3% 以上落ちなければ残す。縮め続ける間は最初に縮める前のスループットと比べる（少しずつ落ちていくのを防ぐ）。
     外したワーカーの接続が動かなければ（HTTP/2 等）振り分けだけ元に戻す。
   - 使用率が飽和（0.95 以上が 0.2 秒）したら半分ずつ広げてみて、5% 以上速くならなければ戻す。飽和していなくても
     使用率が 0.5 以上なら時々広げてみる（上流を待つ中継は、ワーカーが足りなくても使用率が飽和まで上がらない）。
     失敗が続くたびに試す間隔を倍にする（広げる 10〜160 秒、探索 30〜300 秒、縮める 30〜300 秒）。
   - 接続の数が N を変えたときの 2 倍（かつワーカーの数以上の増加）になったら全ワーカーへ戻して探し直す（軽い準備運転の
     後に本番の負荷が来たとき、少ない本数のまま受けない）。一時的な減少では基準を下げない（2 秒続いたらその間の最大値）。
   - 負荷が変わったら（接続の数の倍増・半減、負荷の無い状態が 5 秒）、全ワーカーで受けていても失敗の待ちを最初に戻す
     （lab7: 準備運転の 10 接続で縮めてみて失敗した 30 秒の待ちが残り、続く本番の 100 接続を 16 本に散らしたまま受けた）。
   - 負荷の切れ目（要求の無い状態が 0.5 秒。接続が残っていなければすぐ）で全ワーカーへ戻し、負荷が戻ったら切れ目の前の本数へすぐ縮めてみる
     （[B-366](../bugs/B-366-concentrate-h2-burst-after-pause.md)。当初は負荷が 5 秒無いときだけ戻していた）。
     本数の下限はワーカーの数の 4 分の 1（2 以上）。
5. **設定・観測**: `[performance] concentrate_connections`（既定 `true`。`false` は従来どおり全ワーカーへ振り分ける）、
   メトリクス `veil_proxy_active_workers{listener}`。CBPF を付けられない環境（seccomp 等）は警告して従来どおり。

## 計測

aofish（Windows + WSL2 + Docker Desktop、16 論理 CPU）のコンテナ間。wrk `-t4 -c100 -d14s`、54,576B、TLS（kTLS 無し）。
nginx は `tools/perf/nginx/nginx.conf`（`worker_processes auto`）。値は 3 回（lab10）・2 回（lab6・lab7）の各回。

| 構成 | nginx | v0.12.0（集約無し） | 集約あり | 比（nginx） |
|---|---:|---:|---:|---:|
| 静的配信 HTTP/1.1（lab10） | 52.0k・52.5k・51.1k | 37.8k（lab7） | 97.9k・78.6k・87.2k | **1.69×** |
| 中継 HTTP/1.1（lab10） | 37.7k・34.1k・31.6k | 33.1k（lab7） | 47.1k・44.2k・42.5k | **1.29×** |
| 圧縮 HTTP/1.1（lab7） | 12.4k | 22.6k | 31.5k | 2.5× |
| 静的配信 HTTP/2（lab7・lab10） | 36.5k | 53.5k | 53.4k・54.6k・51.5k | 1.46× |
| 中継 HTTP/2（lab7・lab10） | 25.0k | 45.4k | 51.2k・45.0k・44.9k | 1.88× |

- 1 要求あたりのサーバの CPU（lab10）: 静的配信 40〜51 µs（nginx 152〜167 µs）、中継 129〜142 µs（nginx 202〜237 µs）。
  コンテキストスイッチは静的配信で 0.04/要求（v0.12.0 は 0.54）。
- 中継は使用率が飽和しないので、使用率だけで決めると縮めすぎる（固定 4 本は 31.2k、8 本は 45.9k、16 本は 37.1k。lab6）。
  広げてみて測る探索（`EXPLORE_UTIL`）で 8〜12 本に落ち着く。
- lab7 の 2 回目の静的配信が 45.3k だったのは、準備運転（10 接続・2 秒）の間に縮めてみて失敗し、30 秒の待ちが本番の 14 秒に
  残ったため（接続のハッシュの偏りで 1 本に 4 接続が集まった）。負荷が変わったら待ちを捨てるようにして、lab10 の 3 回は
  78.6k〜97.9k。
- 動かす接続の応答に `Connection: close` を付けていなかった（[B-360](../bugs/B-360-h1-proxy-close-without-connection-close.md)）
  ので lab7 の中継の 1 回目に wrk の read のエラーが 171 出た。lab10 は 0。

## 範囲外・制限

- UDS のリスナー（SO_REUSEPORT が無い）と HTTP/3（UDP）は対象外。
- HTTP/2 の接続は動かせないので、少ない本数のときに来た HTTP/2 の接続は閉じるまでそのワーカーに残る（下限で抑える）。
- N を変えるたびに、動かす HTTP/1.1 の接続は張り直しの費用（TLS のハンドシェイク）を払う。
