# F-300: io_uring の SQE を park でまとめて提出する、HTTP/2 の初回 poll をインラインにする

**状態: 進行中（feat/v0120-perf）**

親: [F-295](F-295-v0120-perf-harness.md)。要求事項には無いが、F-297 の計測の途中で見つけた。

## 問題

既定の Linux ビルド（io_uring）は、要求事項の 4 領域のどれでも epoll ビルドより遅かった。同じコード・同じ負荷で:

| シナリオ | io_uring | epoll | 備考 |
|---|---:|---:|---|
| `/baseline11` 閉ループ（1024 接続） | 417k、18.76 µs/要求 | 606k、12.85 µs/要求 | CPU はサーバ全体（user 5.47 / sys 13.31 と user 3.43 / sys 9.80） |
| gRPC c256 m100 | 887,861、8.89 µs/要求 | 1,715,839、4.61 µs/要求 | 下の第 1 段のあと |
| h2 GET c256 m100 | 1,067,072、7.40 µs/要求 | 2,359,993、3.32 µs/要求 | 同上 |

io_uring は「システムコールをまとめられる」のが取り柄なのに、ランタイムがそれを使っていなかった。原因は 2 つあった。

### 1. TCP の Future が操作ごとに `io_uring_enter` していた

`runtime::uring::tcp` の 11 箇所と `splice` が、SQE を 1 つ積むたびに `submit_sqes()` を呼んでいた。1 要求あたり RECV と SEND で 2 回の
`io_uring_enter` が走る。ループバックではサーバの `send` が相手の受信処理と起床の費用を払うので、提出を 1 本ずつ行うと相手を 1 本ずつ起こすことになる
（Hyper-V の下では起床の IPI が特に高い）。

### 2. HTTP/2 のストリームを全部作ってから実行していた

F-158 は HTTP/2 のインライン初回 poll を reactor だけに入れた。io_uring ではフレームの束を読んだあと、ストリームのタスクを全部 spawn してから実行するので、
c256 m100 では 1 接続で 100 個ぶんの future の状態（数 KB ずつ）を書き終えてからもう一度読み直すことになり、キャッシュから落ちる。
プロファイルでは `memmove` が 23.8%（epoll は 12%）、`drive_h2_streams` が 8.1%（同 3.3%）、ユーザ時間が全体の 93% だった。カーネルの費用ではない。

## 設計

### SQE は park で提出する

- TCP の Future は SQE を積むだけにする。提出は実行器の park の `submit_and_wait(1)` がまとめて行う。積む操作は 1 周回ぶんがまとまる。
- 周回が長いときの保険に `SUBMIT_INTERVAL`（1024 回の poll）ごとに提出する。これはタスクが自分を起こし続けて park へ戻らないときのためで、提出の本体ではない。
- UDP（`udp_send.rs`・`udp_recv.rs`）は即時の提出のまま残す。送信は束の全 SQE を積んでから 1 回の `io_uring_enter` で提出していて（F-130）、遅らせても束は増えない。
- 新しいオペコードは足さない（`IORING_OP_*` は増えない。増えたのはセットアップのフラグ 1 つ）。

### fd の不変条件

カーネルは SQE を **提出のときに** fd を解決する。提出前に fd を閉じると、番号が別のワーカーの接続に再利用されたときに、そちらのソケットへ送る
（接続をまたいだ漏洩になる）。これが遅延提出の唯一の危険で、次のように防いでいる:

- 未提出の SQE は生きている Future のものだけになる。Future が生きている間、その fd の所有者は閉じない。
- 実行中の Future を drop する経路は必ず `detach_op` → `submit_cancel` を通り、`submit_cancel` は本物の `submit_sqes()` を呼ぶ。この提出は SQ の全部を流すので、
  所有者が fd を閉じる前に積まれた SQE はカーネルへ渡る。
- キャンセルの `user_data` には世代が入っていて、再利用されたスロットの操作を取り消さない。
- `TcpStream` の drop は同期の `close(2)` で、`ReadFuture` などは生の fd だけを持つ。Future を構造体に保存している箇所は無く（`.await` の一時値だけ）、
  状態機械は後で作った一時値から drop するので、Future が stream より長く生きることはない。Future と stream を同じ構造体に持たせるときは Future を先に drop する順で書く。
- `detach_op` がキャンセルを投げないのは CQE を受け取り済みのとき（＝提出済み）だけ。`detach_op_no_cancel` は fd を持たない TIMEOUT 専用。

SQE が指すバッファ（`msghdr`・`iovec`）は Future の状態か `op` テーブルにあり、提出までの間も動かない。ここは変更前と同じ条件で、
`Pin` された Future と `op` テーブルのスロットが生きている間だけ SQE が存在する。

### `IORING_SETUP_COOP_TASKRUN`

完了の通知に IPI を使わない（リングはスレッド専用で、CQE は park の `io_uring_enter` で受け取る）。5.19 未満のカーネルと SQPOLL では `EINVAL` になるので、付けずに作り直す。
`DEFER_TASKRUN` は同じ値で制約が増えるだけだったので使わない。

### HTTP/2 の初回 poll をインラインにする

`TaskPool::spawn_inline_with`（reactor と同じ実装）を io_uring にも移植した。ストリームの future はプールのスロットの中で作り、作ったその場で 1 回 poll する。
温かいうちに走り終わるか、最初の待ちまで進む。F-158 の「io_uring は −4.6%」は SQE を 1 本ずつ提出していた頃の値で、提出の位置が変わって前提が消えた。

## 計測（aofish、WSL2、Ryzen AI Z2 Extreme 8C/16T。サーバ CPU 0-7、負荷 8-15）

### 提出の間隔（1024 接続、`/baseline11`）

| 周回の途中で提出する間隔 | 閉ループ rps | 450k 固定の p99 |
|---|---:|---:|
| 8 回の poll ごと | 465k | |
| 16 | 490k | |
| 32 | 541k | 22 ms |
| 64 | 628k | 9.8 ms |
| 128 | 669k | 8.1 ms |
| 提出しない | 669k | 4.3 ms |

周回の途中の提出は費用になる。束ねるほど相手の起床がまとまるからで、`SUBMIT_INTERVAL` を普段の周回より十分大きい 1024 にした。

### セットアップのフラグ（間隔 1024）

| フラグ | 閉ループ rps | 500k 固定の p50 |
|---|---:|---:|
| なし | 693k | 553 µs |
| `COOP_TASKRUN` | 699k | 379 µs |
| `DEFER_TASKRUN` | 698k | 375 µs |

### インライン初回 poll（同じコードで `spawn` と `spawn_inline_with` を交互に 3 回）

| シナリオ | `spawn` | `spawn_inline_with` | サイクル/要求 | 命令/要求 |
|---|---:|---:|---|---|
| gRPC c256 m100 | 882,872〜899,897 | 1,696,319〜1,800,665 | 33,000 → 15,000 | 20,300 → 20,100 |
| gRPC c64 m10 | 892,227〜932,245 | 933,759〜1,001,455 | 19,000 → 18,300 | 変わらず |
| h2 GET c256 m100 | 1,075,901〜1,089,553 | 2,408,698〜2,577,539 | 27,600 → 10,600 | 12,400 → 12,100 |

命令数は変わらずサイクルが半分以下になった。原因の見立てのとおりキャッシュの局所性で、F-297 の「命令数ではなくサイクルで判定する」の例になっている。

## テスト

- `runtime::uring::tcp::tests::test_f300_dropping_an_op_flushes_the_queue`: 実行中の Future を drop すると積まれた SQE がカーネルへ渡る。
- `runtime::uring::tcp::tests::test_f300_a_spinning_task_does_not_hold_back_sqes`: 自分を起こし続けるタスクがいても SQE が提出される。
- `runtime::uring::executor::executor_tests::task_pool_inline_*`: その場で完了したタスクはキューにもスロットにも残らない、pend したら `spawn` と同じ状態で残る、タスクの中から入れ子で呼べる。
