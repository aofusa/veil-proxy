# F-234: HTTP/1.1・HTTP/2・HTTP/3 の要求処理の共通化（L7 の共通の段）

**状態: 完了（feat/v080-release、2026-10-16。範囲は下の「判断」）**

## 目的

ルート解決の後の段が、HTTP/1.1・HTTP/2（`src/proxy.rs`）と HTTP/3（`src/http3_server.rs`・`http3_stream.rs`）の 3 箇所に
別々に書かれている。

- 段の内容: セキュリティ検査（IP・メソッド・レート制限）→ JWT → Wasm の要求ヘッダの段 → `[route.traffic]` →
  静的配信・キャッシュ・Admin・Handler・Respond・Proxy の分岐。
- これまでの不具合: 1 つの経路だけ直し忘れたものがある（B-99: HTTP/1.1 のプロキシ圧縮だけ zstd の文脈を作り直していた）。
- 今後の追加: F-226（タイムアウト・リトライ・ミラー・遅延）・F-229（ext_authz）は、3 箇所すべてに同じ段を足すことになる。

この共通の部分を 1 箇所にまとめる。

## 設計

### 何を共通にし、何を残すか

- **共通にする（`src/l7/` の新しいモジュール）:** 要求の head が手に入ってから、Backend の行き先が決まるまでの判定。
  - 判定の結果は列挙型 `L7Decision` で返す。
    - `Respond(FixedResponse)`
    - `Static(..)`
    - `Cache(..)`
    - `Admin`
    - `Handler(Arc<..>)`
    - `Proxy(ProxyPlan)`
    - `Reject(status, reason)`
    - `NeedWasm(..)`
  - 判定に入れるもの: 要求の head（`&[u8]` のメソッド・パス・ヘッダの借用）、接続の文脈（送信元 IP・TLS の情報）、ルート。
  - プロトコルの書き出しはしない。各経路が結果を受けて、自分の形で応答を書く。
- **残す（各プロトコル）:** フレーミングと送受信。HTTP/1.1 の splice・kTLS、HTTP/2 のフロー制御・アクター、HTTP/3 の quiche の
  ストリームと、ワーカーの `FuturesUnordered`（B-97）。
- **非同期の段（Wasm・JWKS の取得・F-229 の ext_authz）:**
  - 判定は同期の関数にする。非同期が要るところで `NeedWasm` などを返して、一度止める。
  - 各経路はその Future を自分の方法で待つ（HTTP/3 はワーカーの中）。待ち終えたら、共通の段の続きの関数を呼ぶ。
  - こうして、共通の段に `.await` を持ち込まない。HTTP/3 のメインループで待たないこと（B-97）を、型で守る。

### ゼロコストにするための条件

- 共通の関数は、要求ごとにアロケーションしない。判定に要るヘッダは借用で受け、結果の型はルートが持つ `Arc` の clone
  だけにする。
- プロトコルごとの差（HTTP/1.1 の `Host`・HTTP/2 と 3 の `:authority` など）は、トレイト `RequestView` で受ける。
  - トレイトは 3 つの具体型に単相化する（`dyn` にしない）。
  - トレイトのメソッドには `#[inline]` を付ける。
- 判定の順序は今の HTTP/1.1 の経路を正とする。3 経路で順序が違うところがあれば、移す前に表にする。違いを残すべきもの
  （例: HTTP/2 の plan の下見は乱数を引かない。`find_backend_preview`）は、引数で明示する。

### 段階

1. 3 経路の今の判定の順序と、分岐の違いを表にする。違いは、意図したものとバグに分ける。
   - バグは、このチケットの前に B- チケットとして直す。直すと挙動が変わるので、リファクタリングとは混ぜない。
2. 最初にセキュリティ検査と JWT を共通にする。`proxy.rs` の「共通セキュリティチェック」は既に一部を共用しているので、
   これを `l7/` へ移し、HTTP/3 からも使う。
3. 次に Backend の分岐（`L7Decision`）を共通にする。
4. Wasm の要求ヘッダの段を共通にする（`NeedWasm` の段）。
5. 各段で、3 経路の E2E（同じ設定に対して HTTP/1.1・2・3 で同じ結果になる）を足す。`tests/standalone_e2e.rs` に、
   プロトコルの行列の試験として置く。

## 受け入れ条件

- （必須）既存のプロキシの性能が退行しない（`tools/perf/suite_ab.sh` の main との交互 A/B、比の中央値 0.98 以上・0.95 未満なし。
  h1・h2・h3、両バックエンド、3B と 54KB）。allocs/req が増えない（`alloc-stats` のビルドで確かめる）。
- 段階 1 の表を、このチケットに残す。
- 3 経路の判定の関数が 1 つになり、ルートの判定の分岐（`match backend`）が `src/l7/` の外に無い。
- プロトコルの行列の E2E が通る。既存の E2E（io_uring・epoll）・mesh の kind の試験も通る。
  mesh は `src/mesh/` の独自の L7 なので対象外だが、`jwt_verify` などの共有部品が壊れないことを確かめる。


## 実装の結果

### 段階 1 の表（3 経路の違い）

| 段 | HTTP/1.1 | HTTP/2 | HTTP/3 | 扱い |
|---|---|---|---|---|
| 検査の順 | IP → メソッド → 本文 → レート制限（手書き） | IP → メソッド → レート制限 → 本文 | HTTP/2 と同じ | バグ（B-132）。HTTP/1.1 の順に揃えた |
| 本文の長さ | content-length | 受け取った本文 | content-length だけ（省略できる） | バグ（B-132） |
| ルートが無いとき | 404 | authority を空にしてもう一度 | HTTP/2 と同じ | 2 回目は何も見つけない照合だった（ホストの条件の無いルートは常に候補）。削った |
| Respond・Redirect のセキュリティ | 既定値 | 既定値 | 既定値 | バグ（B-133）。ルートの設定を持たせた |

### 判断

- 共通にしたのは「ルートの照合」と「セキュリティの検査」（`src/l7.rs` の `resolve_route`・`check_security`）。3 経路とも
  これだけを使う。
- Backend ごとの分岐（`match backend`）は各プロトコルに残した。分岐の各腕は、そのプロトコルの書き出し（HTTP/1.1 の
  splice・kTLS、HTTP/2 のアクターのチャネル、HTTP/3 の quiche のストリームとワーカーのタスク）そのもので、共通の
  `L7Decision` に置き換えても各経路に同じ数の腕の `match` が残るだけになる。代わりに、片側だけ直し忘れる類の不具合
  （B-99）は、プロトコルの行列の E2E（`standalone_e2e::f234_protocol_matrix_same_decisions`。同じ設定に HTTP/1.1・h2c・
  HTTP/3 が同じ状態コードを返す）で防ぐ。この試験を足した時点で B-132・B-133 が見つかった。
- Wasm の要求ヘッダの段は、3 経路のヘッダの型（HTTP/1.1 の `Bytes` の組・hpack の `HeaderField`・`h3::Header`）が違い、
  変換のコスト（ホスト API の境界の `Vec<u8>`）も同じなので、共通化しても得が無い。今の形のままにした。
