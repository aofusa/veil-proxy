# F-153: 静的配信のパス解決を `canonicalize` から カーネル封じ込め（`RESOLVE_BENEATH`）へ

- 優先度: P1
- 状態: 完了
- 関連: `docs/perf/README.md`「h2c 平文が対 nginx 0.65」、F-123（FreeBSD capability mode の dirfd 相対化）、F-145、F-146、B-26、B-64

## 背景（何を解こうとしているか）

F-150/F-151 の後、FreeBSD 計測で **h2c 平文だけが対 nginx 0.65** と差が残っていた
（HTTP/1.1 TLS 0.97・HTTP/2 TLS 1.05・HTTP/3 1.25 はいずれも同等以上）。

これは **h2c 固有の問題ではない**。h2c は TLS の暗号コストが無いぶん
**1 リクエストあたりの固定費がそのまま露出する**ため、他プロトコルでは
暗号処理に隠れていた静的配信パスの無駄が見えていただけである。

## 調査（Linux で再現し、1 変数の実験で原因を確定）

### 再現（Linux x86_64、veil 2 スレッド / h2load 別コア）

| 配信ファイル | veil | nginx | 比 |
|---|---|---|---|
| 2 バイト | 7,005 | 10,313 | **0.68**（FreeBSD の 0.65 と一致） |
| 54KB | 4,551 | 4,770 | 0.95（`-c10` では veil が上回る） |

**小さい応答でだけ負ける**＝帯域ではなく**リクエスト単価**の問題。

### syscall プロファイル（`strace -f -c`、h2c 3,000 リクエスト）

```
readlink  21,019 calls / 21,019 errors   ← 1 リクエストあたり 7 回、全部失敗
statx      6,020                          ← 2 回
write      6,002                          ← 2 回
openat     3,026 / close 3,038            ← 1 回ずつ
io_uring_enter 18,383                     ← 6 回
futex      6,638                          ← offload スレッド往復
```

**`readlink` が 1 リクエストあたり 7 回、しかも全件エラー**（`EINVAL` = シンボリックリンクではない）。
これは `std::fs::canonicalize()` が**パスの全コンポーネントに `readlink` する**ためで、
静的ルートのパスが深いほど増える。nginx の同条件は open + fstat 程度（5〜6 syscall）。

### 実験 1: `open_file_cache` を有効化（canonicalize + metadata + offload を丸ごと省く）

| 構成 | rps | 対 nginx |
|---|---|---|
| 既定（キャッシュ無効） | 7,005 | 0.68 |
| `open_file_cache` 有効 | **14,028** | **1.36** |

**2 倍**。この経路が原因であることの確定と、改善の上限値。

### 実験 2（決定的）: 静的ルートのパス深さだけを変える

**コード・ファイル・設定すべて同一で、静的ルートのパス深さ（= `readlink` の回数）だけ**を変えた:

| 静的ルート | rps |
|---|---|
| 7 コンポーネント | 6,989 |
| 4 コンポーネント | **9,075（+30%）** |

コンポーネントを 3 つ減らすだけで +30%。**`canonicalize` が一次要因**であることが確定した。

## 改修内容

### 方針: 「解決してから検査する」を「カーネルに封じ込めさせる」へ

現在の静的配信は
1. `canonicalize()` でシンボリックリンクを解決（= 全コンポーネントに `readlink`）
2. 結果が設定ルート配下かを `sendfile_base_contains` で検査
3. その後あらためて `open`

という流れで、**検査と open の間に TOCTOU の窓**がある。

これを **root の dirfd に対する相対 open + カーネルの `RESOLVE_BENEATH`** へ置き換える。
カーネルが `..`・絶対パス・ルート外へ出るシンボリックリンクをすべて拒否するため、
**`readlink` はゼロ**になり、**検査と open が原子的**になって TOCTOU の窓も消える。

これは **FreeBSD で F-123 が既に採用している設計**（`openat` + `O_RESOLVE_BENEATH` +
`init_static_dirfds`）を、Linux とその他の経路へ広げるものである。

| プラットフォーム | 使う機構 |
|---|---|
| Linux 5.6+ | `openat2(2)` + `RESOLVE_BENEATH \| RESOLVE_NO_MAGICLINKS` |
| FreeBSD 13+ | `openat` + `O_RESOLVE_BENEATH`（F-123 の既存実装を capability mode 以外へも適用） |
| その他 / 古いカーネル | 従来どおり `canonicalize()`（フォールバック、挙動不変） |

**io_uring の新規オペコードは追加しない**（AGENTS.md のホットパス絶対規則）。
`openat2`/`fstat` は従来どおり `runtime::offload` の専用ワーカースレッド内で実行し、
イベントループはブロックしない。削るのは**オフロード内の syscall 数**である。

### あわせて: offload 往復と重複 open の削減

現状は「offload で `canonicalize`+`metadata`」→「あとで配信のためにあらためて `open`」と
なっており、1 リクエストで **FS 往復が 2 回**ある。`openat2` は fd を返すので、
**1 回の offload で fd + `fstat` 結果をまとめて返し**、後続の open を無くす。

## 期待効果

1 リクエストあたりの FS syscall: **`readlink`×7 + `getcwd` + `statx`×2 + `openat`** →
**`openat2`×1 + `fstat`×1**。上限は実験 1 の 2 倍（14,028 rps ≒ 対 nginx 1.36）。

## セキュリティ上の注意（レビュー観点）

本改修は**パストラバーサル防御の中核**を触る。以下を必ず担保すること。

- `..` を含むリクエストパスがルート外へ出られないこと。
- **ルート外を指すシンボリックリンク**を辿れないこと（`RESOLVE_BENEATH` が拒否）。
- ルート**内**で完結するシンボリックリンクの扱いが従来と変わらないこと
  （変わる場合は挙動差として文書化する）。
- フォールバック経路（古いカーネル）でも従来と同じ防御が効くこと。
- `openat2` が `ENOSYS`/`EPERM`（seccomp 等）を返した場合に**安全側**へ倒すこと
  （フォールバックへ落ちる。決して「検査なしで open」しない）。
- seccomp 許可リスト（`src/security.rs`）へ `openat2` を追加すること。**追加しないと
  静的配信が全部 404 になる**（B-13 と同じ失敗モード）。

## 実装中に判明した重要な挙動差: `RESOLVE_BENEATH` は**絶対**シンボリックリンクを常に拒否する

`openat2(2)` の `RESOLVE_BENEATH` は
> This causes absolute symbolic links (and absolute values of pathname) to be rejected.

とあり、**リンク先がルート内であっても、絶対パスを指すシンボリックリンクは無条件に拒否**する
（errno は `EXDEV`）。これは
`/var/www/current -> /var/www/releases/v123` のような**デプロイで極めて一般的な形**が
静かに 404 になることを意味し、そのままでは受け入れられない回帰である
（実装中の単体テスト `allows_symlink_within_root` の失敗として検出された）。

### 対応: `EXDEV`/`ELOOP` は「そのリクエストに限り」フォールバックへ落とす

- `openat2` が `EXDEV`（`RESOLVE_BENEATH` 違反）または `ELOOP` を返した場合のみ、
  **そのリクエストに限って** `canonicalize()` + 含有チェックで解決し直す。
  - リンク先がルート内 → 従来どおり配信できる（**挙動が完全に一致**）
  - ルート外への脱出 → 含有チェックが拒否する（**防御も従来どおり**）
- **恒久フォールバックのメモ化フラグは立てない**。`EXDEV` は「このカーネルでは
  `openat2` が使えない」ではなく「このパスが該当した」だけであり、メモ化すると
  以後の全リクエストが遅くなる。恒久メモ化は `ENOSYS`/`EPERM`/`EOPNOTSUPP` のときだけ。
- **これはフェイルオープンではない**。速い経路で弾かれたものを安全な遅い経路で
  確認し直しているだけで、**最終判定は必ず含有チェックが行う**。

## テスト

- 単体: 解決ヘルパに対し、(1) 通常ファイル、(2) `..` によるルート外脱出の拒否、
  (3) ルート外を指すシンボリックリンクの拒否、(4) ルート内シンボリックリンクの許可、
  (5) 存在しないファイル、を実ファイルシステム（`tempfile`）で検証する。
  **フォールバック経路にも同じテストを通す**（両実装が同じ判定をすること）。
- 統合: 静的配信で `..` とシンボリックリンク脱出が 403/404 になること。
- E2E（`full` / `full,epoll`）: 既存の静的配信・Range・キャッシュ有効/無効の全シナリオ。
  パストラバーサル系の既存 E2E が引き続き通ること。

## 検証結果

### テスト

- `cargo test --lib --features full`: **861 passed / 0 failed**（`resolve` の単体テスト 7 件を追加）
- `cargo test --test integration_tests --features full`: **54 passed / 0 failed**
- `cargo build --features full` / `--no-default-features` /
  `cargo clippy --features full --all-targets`: いずれも **warning 0**

### 機構が効いていることの直接確認（syscall カウント）

`strace -f -c` で h2c 静的配信中の syscall を数えた（約 1,000 リクエストぶん）:

| syscall | 改修前 | 改修後 |
|---|---|---|
| `readlink` | **7,012**（全件エラー、= 7 回/リクエスト） | **12**（起動時のみ、= 0 回/リクエスト） |
| `openat2` | 0 | 1,000（= 1 回/リクエスト） |
| `statx` | 2,018 | 2,018（変化なし） |
| `openat` | 1,025 | 1,026（変化なし） |

**`canonicalize` 由来の `readlink` はリクエストあたり 7 回 → 0 回**になった。

### スループット（交互 A/B、各計測前にウォームアップ 5,000 リクエスト、6 ラウンド）

h2c・2 バイト応答・`-c100 -m10`、veil 2 スレッドを `taskset -c 0,1`、負荷生成は別コア。

| ラウンド | 改修前 | 改修後 |
|---|---|---|
| 1 | 7,644 | **9,057** |
| 2 | 7,258 | **10,952** |
| 3 | 7,701 | **9,150** |
| 4 | **9,981** | 9,113 |
| 5 | 7,985 | **8,767** |
| 6 | 7,938 | **10,871** |
| **中央値** | **7,820** | **9,132（+17%）** |

**6 ラウンド中 5 ラウンドで改善**。対 nginx 比は **0.69 → 0.81**（同時計測 nginx 中央値 11,272）。

### 追加検証: 改修後は `open_file_cache` の効果がほぼ消える（＝改修が効いている裏付け）

改修前は `open_file_cache` を有効にすると **2 倍**（7,005 → 14,028）になった（「実験 1」）。
これは キャッシュが `canonicalize` を丸ごと省いていたためである。
**改修後に同じ A/B を取ると差は +5% 程度まで縮む**:

| ラウンド | 改修後（ofc off） | 改修後（ofc on） |
|---|---|---|
| 1 | 8,343 | 10,073 |
| 2 | 10,959 | 11,623 |
| 3 | 10,610 | 11,097 |
| **中央値** | **10,610** | **11,097（+5%）** |

**「キャッシュを有効にしても、もう大して速くならない」= キャッシュが省いていた仕事を
本改修が既に省けている**、ということであり、改修が効いていることの独立した裏付けになる。

（当初は「残るギャップの主因は offload のクロススレッド往復」と考えたが、
この計測がそれを否定した。`open_file_cache` はヒット時に offload 往復ごと省くにもかかわらず
+5% しか動かないため、offload 往復は支配的コストではない。）

### 計測のばらつきについて（正直な但し書き）

本環境（4 コア・co-tenant あり）では同一バイナリでもラウンド間で **8,300〜11,000 rps** と
±20% 程度ばらつく。したがって**スループットの +17% という数字は幅を持って見るべき**である。
一方 **syscall カウント（`readlink` 7 回/リクエスト → 0 回）は決定的**で、ばらつきの影響を受けない。
本改修の効果の根拠としては、まず syscall カウントを、次に「6 ラウンド中 5 ラウンドで改善」
「ofc の効果が 2 倍 → +5% に縮んだ」という一貫した傍証を採るべきである。

対 nginx 比は改修前 0.69 に対し改修後 0.81〜0.94（ばらつきの範囲）で、
**`open_file_cache` を併用すると nginx とほぼ同等（11,097 対 11,272）**になる。

### FreeBSD では改善しない（そして、その理由）

FreeBSD 14.3 amd64（QEMU/KVM）で同じ h2c 計測を取ったところ、
**対 nginx 比は 0.68 で改修前（0.65）からほぼ変わらなかった**。原因を調べた結果、
**本改修の効果は Linux 固有**であることが分かった。

`truss -f -c` による FreeBSD の syscall カウント（2,000 h2c リクエスト、改修後）:

| syscall | 回数 |
|---|---|
| `__realpathat` | **2**（起動時のみ。= 0 回/リクエスト、本改修で除去済み） |
| `openat` | 2,000（1 回/リクエスト） |
| `fstatat` | 2,002（1 回/リクエスト） |
| `write` | 4,000（2 回/リクエスト） |
| `read` | 9,445（約 4.7 回/リクエスト） |

**本改修は FreeBSD でも正しく効いている**（`__realpathat` が 0 回/リクエストになった）。
しかし **FreeBSD の `canonicalize` は `__realpathat` という単一の syscall** で実装されており、
**元から 1 回/リクエストしか消費していなかった**。一方 Linux の glibc は `realpath` を
ユーザ空間で実装しており**パスの全コンポーネントに `readlink` する**（実測 7 回/リクエスト）。

> **教訓**: `canonicalize()` のコストは **libc 実装依存で桁が違う**。
> Linux（glibc）= パス深さに比例した `readlink` の連発、FreeBSD = 単一の `__realpathat`。
> 「同じ Rust の API だから同じコスト」と考えてはいけない。

したがって **FreeBSD の h2c ギャップ（0.68）の主因はパス解決ではない**。
残る候補は 1 リクエストあたり `write` 2 回・`read` 約 4.7 回・offload 往復であり、
**別チケットで調査する**（本チケットのスコープ外）。

### 設計との差分（実装で見送った点）

設計では「`openat2` が返す fd をそのまま配信に使い、後続の `open` を無くす」としていたが、
実装では fd を破棄している（`openat` が 1 回/リクエスト残っているのはこのため）。
上記のとおり残るボトルネックは offload 往復であり、`openat` 1 回の削減は
効果が小さいと判断して見送った。将来 offload 往復を解消する際に併せて対応する。
