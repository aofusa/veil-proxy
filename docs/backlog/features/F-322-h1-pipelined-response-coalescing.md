# F-322: HTTP/1.1 のパイプラインの応答をまとめて送る（次の要求が届いている間は書かずに溜める）

**状態: 着手（2026-11-25、feat/httparena-perf。F-317 の子）**

## 今の状態（測った値）

HttpArena の pipelined（`GET /pipeline` を 16 本ずつまとめて送る、4096 接続。2026-11-24 の結果）:

| エントリ | rps | 1 要求の CPU（µs） |
|---|---|---|
| okena | 27.12M | 2.4 |
| agensio | 4.96M | 12.4 |
| h2o | 4.94M | 13.0 |
| nginx | 4.04M | 15.8 |
| veil-api | 3.43M | 19.0 |
| veil（Proxy-Wasm） | 0.60M | 104.7 |

- okena は 16 本の応答を 1 回の送信にまとめていると考えると合う（1 要求 2.4 µs は、16 要求ぶんの `recv` 1 回 + `send` 1 回 + 解析
  16 回の費用の大きさ）。他の 12〜19 µs は 1 応答 1 送信に近い（baseline の 1 要求 1 往復の 16〜26 µs と大きく変わらない）。
- ノート PC（1 ワーカー）でも、Wasm の `/pipeline`（16 本ずつ）は 1 要求 36.1 µs で、パイプラインでない GET（37.1 µs）と同じ
  （`docs/artifacts/benchmark/httparena-perf/results/m1.tsv`）。まとめる効果が出ていない。

## 原因（コード）

- `src/proxy/h1.rs` の要求のループは、前の要求の後ろに次の要求が丸ごと届いていれば読まずに処理する（B-129 の `pipelined_ready`）。
  しかし応答は要求ごとにすぐ `write_all` する（`Respond`・Wasm の `send_local_response`・ハンドラ・エラー応答・メモリの静的配信のどれも）。
  16 本届けば `send(2)`（TLS は暗号化と `writev(2)`）が 16 回になる。
- 応答を書く時点で、後ろに届いている分（`pipelined`）は分かっている（`handle_request` へ `&mut pipelined` で渡している）。

## 改修内容

1. 接続の書き込み口に「溜める」状態を持たせる。要求のループが、後ろに次の要求のヘッダが丸ごと届いている（`pipelined` に
   `\r\n\r\n` がある）ときだけ溜める状態にして応答の処理へ入る。溜める状態の `write_all` はワーカーのプールのバッファへ足すだけにする。
2. 次の時点で溜めた分を 1 回で送る:
   - 次の要求が丸ごと届いていない（読み取りの待ちに入る前）。
   - 溜めた量が上限（例 64 KiB）または本数の上限（例 32 本）を超えた（1 つの接続が他を飢えさせない・メモリを抑える）。
   - 応答がソケットを直接使う経路に入る前（`sendfile`・`splice`・ストリーミングの本文・上流への中継・アップグレード・kTLS の送信）。
   - 接続を閉じる前（`Connection: close`・エラー・graceful shutdown・タイムアウト）。
3. TLS（rustls）は平文を溜めずにセッションへ書き、暗号文の送出（`flush_tls_writev`）を同じ時点まで遅らせる（レコードは応答ごとに
   分かれるが、`writev` は 1 回になる）。kTLS は平文を溜めて 1 回で送る。
4. 書き込みの失敗は溜めた全部の失敗として扱い、接続を閉じる（今と同じく、送れなかった応答のアクセスログは書かない）。

## 実装（2026-11-25）

- `src/response_hold.rs` の `ResponseHold`（溜めたバイト列と「今の要求の応答を溜めてよいか」）をサーバ側の TLS ストリーム
  （`ktls_rustls::KtlsServerStream`・`simple_tls::SimpleTlsServerStream`）が持つ。バッファはスレッドのプールから借り（容量 16 KiB。
  溜め始めた接続だけが借り、送ったら返す）、上限を超える応答は溜めない（バッファを伸ばさない）。本数の上限は設けない
  （1 回に処理するのは読み取りバッファに届いた分だけで、上限のバイト数で区切られる）。
- `write_or_hold`: 今の要求の後ろに次の要求のヘッダが丸ごと届いていれば溜める。届いていなければ、溜めた分に足して 1 回で送る。
  使うのは固定応答（`Respond`）・Wasm の要求ヘッダの段のローカルレスポンス・ハンドラの本文まで 1 つのバッファに収めた応答。
- `proxy/h1.rs` は本文を切り出した時点で `set_hold_next(!client_wants_close && 後ろに要求のヘッダが丸ごとある)` を設定し、
  次を守る: 読みを待つ前（ループの先頭）・ソケットへ直接書くバックエンド（上流への中継・静的配信）の前・WebSocket のトンネルの前・
  応答の後に閉じる前に溜めた分を送る（`flush_held`）。
- ストリームの読み書き（`read`・`write`・`write_all_vectored`・`shutdown`）は溜めた分を先に送る（溜めない書き込みが続いたときの
  順と、送らずに読みを待って止まらないことの保険。まれなので `Box::pin` に入れて読み書きのフューチャを太らせない）。`Drop` は
  溜めたまま閉じる経路の保険として待たずに送る。
- TLS（rustls）は平文を溜め、送るときにまとめて rustls へ渡して 1 回の `writev(2)` で送る。kTLS・平文は 1 回の `send(2)`。
- 計画との違い: アクセスログは溜めた時点で書く（カーネルの送信バッファへ書けた時点で書くのと同じ扱い。送るときに失敗したら
  接続を閉じる）。
- 試験: `tests/standalone/pipeline_tests.rs`（平文・TLS で、次の要求の無い要求での送出、溜めた後の sendfile・上流への中継・
  リダイレクト・HEAD、上限を何度も超える 300 本、途中の `Connection: close`）。溜めた分を捨てる変異を入れると両方とも落ちる
  （溜める経路を通っている）ことを確かめた。`response_hold` の単体試験。

### 残りの費用（aofish の perf、f322、pipe-plain）

- 要求の処理の本体（`handle_requests`）が約 30%、`BytesMut` の共有の参照カウント（`shared_v_clone`・`shared_v_drop`）約 7%、
  ルートの照合・キャッシュ約 5%、`httparse` 約 4%。io_uring だけ時計（`clock_gettime`）が 6〜7%（epoll は 1%）で、その 4.8% は
  要求の処理から: io_uring の `timeout()` はタイマーを作るときに正確な時計を読み、溜める書き込み（その場で終わる）にも払っていた。
- `runtime::uring::timer::timeout`・`timeout_idle` を、内側の Future が最初の poll で終わらなかったときだけタイマー（`Sleep`）を作る
  形にした（期限は最初の poll から。作った直後に poll する使い方では同じ）。reactor の `Sleep::new` は粗い時計なので変えない。

## 気を付けること

- 応答の順序は要求の順のまま（同じ接続の 1 本の書き込み口なので崩れない）。100-continue（本文を待つ前に送る）は溜めない。
- 書き込みのタイムアウト（`WRITE_TIMEOUT`）は送るときに掛ける。HEAD・304・`Connection: close` の応答も同じ経路で溜められる。
- 溜める状態はパイプラインのときだけ。パイプラインでない要求（ほとんどの利用者）の経路・システムコールの数は変えない。

## 確かめ方

- ノート PC の交互 A/B: veil-load `--pipeline 16`（`Respond` の `/pipeline`、Wasm の `/pipeline`、静的配信）とパイプラインなしの GET。
  `strace -c -f` で 1 要求あたりの `send`・`writev` の数も見る。
- aofish で HttpArena の gcannon（`-p 16`、4096 接続）でも測る。

## 受け入れ条件

- ノート PC で `Respond` の `/pipeline`（16 本ずつ）の 1 要求の CPU が 1/3 以下。パイプラインなしの経路は悪化しない（±3%）。
- 単体・E2E: パイプラインの順序、途中の `Connection: close`、上限で区切られる、溜めた後に静的配信（sendfile）や上流への中継が来る、
  書き込みの失敗、TLS・kTLS・HTTP/1.1 の平文。io_uring と epoll の両方。
