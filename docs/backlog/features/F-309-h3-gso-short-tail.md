# F-309: HTTP/3 の応答の最後の短いパケットを GSO の束に入れる

**状態: 実装中（feat/beat-nginx、2026-11-14）**

## 背景

HTTP/3 で 1 要求あたりにサーバが送るデータグラム（GSO の束）が nginx より多かった（lab43・lab44 の `-m10` で nginx 1.1・
veil 1.4、lab46 の 1 接続 1 ストリーム `-m1` で静的配信 nginx 1.00・veil 2.00、中継 nginx 2.07・veil 3.05〜3.29）。
`-m1` の静的配信で veil は nginx より 13.6% 遅く（29,254 対 33,840 rps）、中継は 8〜10% 遅かった。ACK の遅延（F-308）では
変わらなかった。

lab47 でサーバのネットワーク名前空間の UDP を tcpdump で採ると、`-m1` の静的配信で nginx は 1 要求に 48KB を超える
束を 1 つだけ送るのに対し、veil は束 1 つと 201〜1,500 バイトのパケット 1 つを送っていた（どちらも要求の数と同じ）。
中継では両者とも要求ごとに ACK だけのパケット（60 バイト以下）を 1 つ送り、veil だけが短いパケットをさらに 1 つ送る。

原因は `http3_server::event_loop::gso_batch_must_flush_before_append`。束のセグメント長と違う大きさのパケットの前では
必ず束を切っていたので、応答の最後の短いパケットは毎回別の送出になった。UDP の GSO は最後のセグメントだけ短くてよく
（カーネルは cmsg のセグメント長で切り、残りを最後のセグメントにする）、関数の説明にもそう書いてあったが、判定は
`write != seg_size` だった。`-m1` では後ろの短いパケットが届くまで応答が終わらず、クライアントの次の要求が遅れる。

## 対応

- 束を先に切るのは、追加するパケットがセグメント長より**大きい**ときだけにする（`write > seg_size`）。短いパケットは同じ束の
  最後のセグメントとして入れ、入れた後で束を確定する（呼び出し側の既存の `write < seg_size`）。
- GSO を使わない送出（BSD・macOS・`gso_gro_enabled = false`）はパケットごとに送るので変わらない。

## 計測

（lab48 で、変更前（beatack）・変更後と nginx を `-m1`・`-m10` で交互に採る）
