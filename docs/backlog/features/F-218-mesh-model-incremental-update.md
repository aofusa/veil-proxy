# F-218: メッシュモデルとリソース単位の動的更新（F-211 の 4〜6 を含む）

**状態: 完了（feat/mesh-dataplane-impl、2026-10-15）**

## 目的

Istio・Linkerd の制御プレーンからの設定を、制御プレーンに依存しない 1 つの型（メッシュモデル）で持ち、リソースごとに
差し替える。今の設定の更新は TOML の合成 → 全体の検証 → 全体の `ArcSwap`（`config_override::apply_to_toml_str`、VDS もこの経路）で、
エンドポイント 1 件の変更でも設定全体をやり直す。メッシュではエンドポイントの入れ替え（ロールアウト・オートスケール）が
秒単位で起き、サービス数も数千になるので、この経路では間に合わない。

## 設計

- **型**（`src/mesh/model.rs`、`mesh` feature）: `Listener`・`FilterChain`・`RouteTable`・`VirtualHost`・`Route`・`Cluster`・
  `EndpointSet`・`Policy`・`Identity`（F-215 の全体設計の 1）。各型は不変（作ったら変えない）で、更新は新しい値を作って差し替える。
- **格納**: `MeshState { listeners: ArcSwap<ListenerTable>, routes: ArcSwap<HashMap<Name, Arc<RouteTable>>>, clusters: … }`。
  クラスタは `Arc<ClusterRuntime>`（LB の状態・接続数・外れ値検出・ヘルスチェッカー＝プロセスで 1 個、F-156）を持ち、
  その中の `ArcSwap<EndpointSet>` だけをエンドポイントの更新で差し替える（LB の状態は引き継ぐ。重み付き・一貫性ハッシュは
  新しい集合で表を作り直す）。
- **参照**: データプレーンは接続の受理時に `ListenerTable` を 1 回、要求ごとに `RouteTable` を 1 回 `load` する（`Arc` の
  clone のみ。ホットパスで `HashMap` を作らない）。ルートの照合はロード時にコンパイル済み（ホスト名の完全一致は表引き、
  ワイルドカード・正規表現は前もって構築）。
- **整合性**: 参照しているクラスタが無いルート（xDS の順序で一時的に起きる）は 503 ではなく「ウォーミング」として、
  クラスタが届くまで古いルート表を使う（Envoy と同じ）。削除は参照が無くなってから（`Arc` のカウントで自然に解放）。
- **更新の入口**: アダプタ（F-222・F-223）・VDS は専用スレッドで「リソースの追加・更新・削除」の列を作り、検証してから
  まとめて差し替える（1 回の xDS の応答は 1 回の差し替え）。失敗したリソースだけ NACK（Delta xDS のリソース単位の版）。
- **VDS との関係**: F-211 の 4（EDS 相当）・5（Delta）・6（ロカリティ・優先度 LB）はこのモデルの上で実装し、VDS の
  `Route`・`Upstream` もこの型へ変換して使えるようにする（同じ更新経路を 2 本持たない）。今の TOML のルートは当面そのまま。
- **ロカリティ・優先度**: `EndpointSet` にロカリティ（region / zone / subzone）と優先度を持たせ、自分のロカリティを優先する LB
  （Istio の locality load balancing、フェイルオーバー）。
- **メモリ**: 大きなメッシュでは Envoy のサイドカーは全サービスの設定を持つ（Sidecar リソースで絞る）。名前（文字列）は
  インターン、エンドポイントは `SocketAddr` + 小さなメタデータで持ち、ワーカー間で共有する（スレッドごとに複製しない）。

## 受け入れ条件

- （必須、F-215）既存のプロキシの性能が退行しない（`tools/perf/suite_ab.sh` の main との交互 A/B、比の中央値 0.98 以上・0.95 未満なし）。
  コンテナで試すときのイメージは musl 版。

- 単体: エンドポイントの差し替えで LB の状態（ラウンドロビンの位置・接続数）が保たれる、ウォーミング、削除の後の解放、
  リソース単位の NACK。
- 規模の試験: 5,000 サービス・50,000 エンドポイントの更新列を流し、1 件の更新にかかる時間・メモリ・データプレーンの
  スループットへの影響（更新中の rps の落ち込み）を測る（`docs/artifacts/` に記録）。
- VDS の既存の試験（`tests/standalone_e2e.rs` の VDS・`f211_*`）が変わらず通る。F-211 の 4〜6 のチケット状態を本チケットへ寄せる。


## 実装の結果

- 制御プレーンに依存しないメッシュモデル（`src/mesh/model.rs`）。リソース単位で `ArcSwap` に差し替え、長い接続の要求も次の要求から
  新しい設定を使う。
- EDS の更新でエンドポイントの状態（同時要求数・連続 5xx・排出の期限）を同じアドレスに引き継ぐ（`EndpointSet::carry_from`、
  単体 `endpoint_update_keeps_lb_state`）。
- 規模の試験（`translate::tests::eds_scale_update_cost`、VEIL_MESH_SCALE_SERVICES）: 5,000 サービス × 10 エンドポイントの初回の適用
  55 ms・RSS +22.6 MB、1 サービスの EDS の更新 9.8 µs。
