# F-297: コア制限下の遅延（1 要求あたりの CPU を減らす）

**状態: 完了（feat/v0120-perf、2026-11-07）**

親: [F-295](F-295-v0120-perf-harness.md)。公平性は [B-332](../bugs/B-332-reactor-hot-connection-starves-others.md)。

## 現状

HttpArena の latency-500k-8cpu（`GET /baseline11?a=1&b=2`、8 論理 CPU、1024 接続、固定レート 500k、CO 補正）で
372,770 req/s、rate 0.7455、p99 6.2 s。1 要求あたり 21.4 µs の CPU で、8 CPU の容量が固定レートを下回っているので
遅延が積み上がる。上位は 14.7〜16.4 µs/req。つまり **1 要求あたりの CPU を 16 µs 程度へ下げる** のが本筋。

## 再現と分解（aofish の WSL、epoll 版、サーバ CPU 0-7、負荷 CPU 8-15）

- 飽和 378,353 rps（外部とほぼ同じ）。CPU はユーザ 1/3、システム 2/3。
- 1 要求あたりのシステムコール（LD_PRELOAD で数えた。飽和でも 200k の固定レートでも同じ）:

| read | send | poll | epoll_ctl | epoll_wait |
|---|---|---|---|---|
| 1.00 | 1.00 | 2.00 | 1.00 | 0.008〜0.46 |

`poll(2)` 2 本と `epoll_ctl(MOD)` 1 本は、キープアライブの待ちごとに「確認 → 再武装 → 起床後にもう一度確認」している分。

## 仮説

1. 要求ごとに 3 本のシステムコールを消せる（5 本 → 2 本 + `epoll_wait` の按分）。
2. ユーザ時間（約 7 µs）の上位は `handle_requests`・`handle_backend`・memmove・`Backend::clone`・`shared_v_*`。
   ヘッダの扱いと経路の解決で積み上がっている。

## 改修内容

### A. epoll の登録を要求ごとに触らない（AGENTS.md の B-75 の条項を改める）

`EPOLLONESHOT` + 待ちごとの `EPOLL_CTL_MOD` をやめ、**待機者がいる方向だけを level-triggered で武装したまま残す**:

- `register`: 既にその方向が武装済みなら Waker を置くだけ（システムコール無し）。
- `dispatch_event`: 起床させる待機者がいれば起こして武装を残す。待機者がいないのにイベントが来たら、その方向を `MOD` で下ろす
  （レベルで鳴り続けるのを止める）。次に待つときに `MOD` で上げ直すと、カーネルがレベルを再評価する（取りこぼさない）。
  （2 回続いてから下ろす案は、上げ下げの往復が実際には起きていなかったので取り下げた。[B-338](../bugs/B-338-epoll-unclaimed-read-rearm-churn.md)）
- 起こす順番: 読み取りの待ちは待ち始めた順に起こす。レベルトリガのカーネルは前の回に報告した fd を前の回の報告の順で先に返すので、
  そのまま起こすと CPU を使い切る負荷で一部の接続が毎回 2 周待つ（[B-339](../bugs/B-339-epoll-level-trigger-sticky-wake-order.md)）。

レベルトリガなので B-75 が避けた「読めないが再武装もされない」状態は起きない（`EAGAIN` の後の待機でカーネルの状態が
そのまま効く）。ET と違い、`EAGAIN` までの読み切りも要らない。

### B. 確認用の `poll(2)` を外す

- `Readable`・`ReadFuture` の `read` は try-first なので、キープアライブの待ちは「まず待ちに入る」（`readable_lazy`）。
- 待ちから起きた後は確認せずに読みにいく（`read` が `EAGAIN` なら Waker を置いて待つ。A により追加のシステムコールは無い）。
- `Readable` の `poll(2)` は、ヒントの無い汎用の待ち（`select` の中など）に残す。

B-75 のハングは「ヒントで `Ready` を返したが `register` を通らず disarm のまま」が原因の仮説で、A で再武装そのものが
不要になるので前提が消える。kTLS + HTTP/2 の再現手順（`wrk ×3 → h2load`）を回帰の手順に加える
（`tools/perf/ktls_h2_repro.sh`。最終のコードで epoll・io_uring とも h2load 10 万要求 × 3 回が全部成功した）。

`ReadableFd`（HTTP/2 の接続のループ・UDP の待ち）は確認を残した。「まず待ちに入る」形も試したが、もう読める接続が周回を 1 つ待つことになり、
HTTP/2 の 54KB の転送で −4%（下の「HTTP/2 の転送の退行」）。

### C. ユーザ時間

プロファイルの上位から、要求ごとの確保・コピー・クローンを減らす（`Backend::clone`、ヘッダの `to_vec`、タイマーの
登録・解除など）。実測で効いたものだけ入れる。

入れたもの:

- ヘッダの解析を同期関数 `parse_request_head` へ（`httparse` の作業用配列が `handle_requests` のフューチャの状態に載り、接続ごとの
  冷たいメモリを書いていた。フューチャは 8,920 → 6,448 B）。
- `CURRENT_CONFIG.load()` を 1 回に（1 回で 100〜160 命令。`resolve_route_in` へ渡す。「有効か」だけを見る値は保存する箇所の隣で静的な値へ写す）。
- `Prometheus`・管理 API の判定はバイト列で（`from_utf8` を要求ごとに走らせない）。Wasm のフィルタの無いルートはヘッダを写さない。
- `handle_api_handler` の中の大きい枝（ストリーミング・本文の読み取り・チャンク）を `Box::pin` へ。本文の無い要求は読み取りを呼ばない。
- 接続あたりの `client_ip` の解析を `CallCache` で 1 回に。`form_lookup`・`percent_decode`・ヘッダ名の検査（`TCHAR` の表）を軽く。

採らなかったもの:

- **ハンドラの `Box` を外す案。** 確保とコピーが消えて命令数は −10% になるが、サイクルは +12%、rps は下がった。ハンドラの状態を
  接続ごとのフューチャの中へ持ち込むと、ワーカーの中で使い回していた温かいブロックが接続ごとの冷たいメモリに変わるため。
  **命令数でなくサイクルで判定する** きっかけになった（コメントを残した）。
- 遅延タイマー・ヘッダの 1 回走査・`Backend::clone` の削減: プロファイルが平坦で、手間に見合う差が見えなかった。

システムコール（`read` + `send`）は下限に来た。ループバックの `send` は相手の受信と起床の費用まで払う（外部の負荷ツールも同じ）。

## 計測

`python3 tools/perf/api_ab.py --scenario latency`。8 CPU に固定し、固定レートを段階的に上げて、達成率と p50/p99/p99.9 を見る。
システムコール数は `tools/perf/syscall_count/`。

## 受け入れ条件

- 1 要求あたりのシステムコールが `read` + `send` + `epoll_wait` の按分になる。
- 8 CPU の飽和スループットが改修前より大きく増え、固定レートでの p99 が下がる。
- epoll の E2E（`VEIL_E2E_FEATURES="full,epoll"`）と kTLS + HTTP/2 の再現手順が通る。

## 依存・リスク

- reactor の登録の意味論を変えるので、offload の eventfd（`wake_all_readers`）・WebSocket の中継・静的配信など
  同じ fd に別の待ち手がいる経路を読み直す。io_uring の経路は変えない。

## HTTP/2 の転送の退行（最後の A/B で発見）

`proxy_ab.py` の上流を直したら（下記）、epoll の HTTP/2 の 54KB の転送だけ main より遅かった（h2c・h2 とも −5.3%、勝ち 0/3、CPU +4%）。
システムコールは 1 要求あたり 1.4 本減っているのに、`send` 1 本の時間も nginx の CPU も数 % ずつ増えていた。コミットで分けると A・B の 1 つだけで起きていて、
要因を 1 つずつ外しても戻らず、組み合わせで効いていた（h2c の rps。CPU は µs/要求）:

| 変種 | h2c 54KB | h2 54KB |
|---|---:|---:|
| main | 104,492（76.2） | 88,033（90.5） |
| 修正前 | 101,049（78.8） | 84,750（93.5） |
| 予算を外す・間隔を外す・`ReadableFd` の順序を戻す、のどれか 1 つ | 99,334〜101,800 | 85,626〜86,368 |
| 3 つとも外す | 106,806（74.4） | 90,754（87.5） |
| インラインの poll の予算を分ける | 102,175（78.2） | 86,078（91.7） |
| 同 + `EVENT_INTERVAL` 256 | 105,618（75.3） | 88,283（90.6） |
| 同 + `ReadableFd` は確認から入る（採用） | 106,194（75.2） | 87,679（90.5） |

- **インラインの poll の予算。** ストリームの初回 poll が接続のタスクの予算を使っていた。束の 8 本目あたりで尽きて、要求を送る前の
  ストリームが `Pending` へ落ち、1 周回遅れていた。[B-332](../bugs/B-332-reactor-hot-connection-starves-others.md) の上限はタスクごとの意図なので、インラインの poll に別の予算を渡す。
- **`ReadableFd` の順序。** 先に待ちへ入ると、もう読める接続も次の `epoll_wait` まで待つ。上の変種で `EVENT_INTERVAL` を増やしても同じだけ戻るが、
  128 で gRPC の固定レートの p99 が 2 割悪くなる（200k: 2,146 → 2,638 µs、300k: 2,834 → 3,588 µs）。確認から入る形は gRPC のテールを変えず、飢えの上限は
  読み取りの `coop_proceed` が持つ（200k: 2,277 → 2,408 µs、300k: 2,966 → 2,834 µs、c256 m100 は 1.6M で同じ）。

効果の大きさは Hyper-V の下の値。`recv`（`MSG_PEEK`）のような軽い呼び出しまで数 % 遅くなっていたので、原因はキャッシュの局所性とみている（F-300 の
インラインの初回 poll と同じ型）。

**計測の教訓。** それまでの `proxy_ab` は上流の nginx が律速で（1 物理コアで nginx 直でも 8 万 rps）、転送の行に veil の差が出ていなかった。
さらに前の実行の nginx が残っていて `--backend-*` が効いていない回があった。律速を直して初めてこの退行が見えた。
