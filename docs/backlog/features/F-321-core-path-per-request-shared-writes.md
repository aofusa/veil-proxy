# F-321: 本体の要求の経路から「全ワーカーで共有する行への書き込み」を無くす（ルートのキャッシュの統計・共有の `Arc` の参照カウント・キャッシュの当たりの数）

**状態: 着手（2026-11-25、feat/httparena-perf。F-317 の子。Wasm を通らない経路〈veil-api・`Respond`・静的配信〉の多コアでの膨らみ。Wasm の側は F-318）**

## 今の状態（測った値）

HttpArena（64 スレッド。2026-11-24 の結果）の 1 要求あたりの CPU（`cpu% × 10000 / rps`、µs）。veil-api は Proxy-Wasm を通らない
（ハンドラは veil のワーカーの上で動く）:

| プロファイル | okena | agensio | h2o | nginx | veil-api | ノート PC の veil（1 ワーカー・io_uring） |
|---|---|---|---|---|---|---|
| baseline-4096（HTTP/1.1） | 16.4 | 17.2 | 18.1 | 19.6 | 25.8 | 12.3（`Respond`） |
| limited-conn-4096 | 20.7 | 23.2 | 23.4 | 23.7 | 32.8 | — |
| baseline-h2c-256 / 1024 / 4096 | 1.2 / 1.3 / 1.3 | 1.1 / 1.0 / 1.1 | — | 26.9 / 26.6 / 25.8 | **10.5 / 13.1 / 16.2** | 4.5（16 接続 × 100 ストリーム） |

- HTTP/1.1 の 16〜20 µs の大半はループバックの TCP の処理（送る側がカーネルで受け手の処理まで払う）。veil-api はそこへ 6〜9 µs 多い。
- h2c は接続が増えるほど 1 要求の費用が上がる（10.5 → 16.2 µs）。ノート PC の 1 ワーカーの 4.5 µs の 2〜4 倍。
- 64 コアで費用が膨らむ形は F-318（Wasm）と同じ。全ワーカーが同じキャッシュラインへ書くと、ラインの持ち主がコアの間を往復し、
  1 回の書き込みが 100 ns を超える（1 本のラインが捌ける書き込みは毎秒数百万回で頭打ち）。機械の速さ・epoll と io_uring の差・
  TLS の有無も混ざっているので、下の伸び方の試験で切り分ける。

## 要求ごとに共有の行へ書いているところ（コードで確かめたもの）

1. **ルートのキャッシュの統計**（全プロトコル・全要求）: `upstream::select_route`（`src/upstream.rs:978`）→
   `OptimizedRouter::try_cache` → `RouteCache::get`（`src/routing/mod.rs:634`）が当たるたびに `hits.fetch_add(1)`、外れると
   `misses.fetch_add(1)`。`RouteCache` は設定に 1 つで全ワーカーが同じ値を書く。しかも同じ構造体の `generation`（要求ごとに
   読む）が同じキャッシュラインにあり、他のワーカーが数えるたびに読みも外れる（偽共有）。
2. **ルートが当たったときの `Arc` の複製**（`src/upstream.rs:993-1001`）: `route.resolved_path_prefix.clone()`、
   `route.resolved_compression.clone()`、`route_backend` → `load_backend` の `b.clone()`（`Backend` の中の `Arc`）。どれも設定に 1 つで、
   複製と破棄で参照カウントへ 2 回ずつ書く。AGENTS.md の「ホットパスは `Arc` clone のみ（F-148/F-159）」は確保を消す規則で、
   多コアではこの複製そのものが共有の書き込みになる。
3. **静的配信のキャッシュの当たり・外れの数**（静的の 3 プロファイル）: `cache/file_cache.rs:384,390,668,717`、
   `cache/content_cache.rs:320,339,369,427`、`cache/compressed.rs:171,275` の `hits`・`misses` の `fetch_add`（キャッシュに 1 つ）。
4. **接続の数**（limited-conn は 10 要求ごとに張り直す。veil-api で毎秒約 20 万接続、okena で約 28 万）: `metrics::ConnectionGuard`（`src/metrics.rs:402,409`）の
   `CURRENT_CONNECTIONS` の `fetch_add`・`fetch_sub`。
5. 未確認の候補: `perf c2c` で上位に出たもの（メトリクスの系列・アクセスログの世代・`stream_channel`・アロケータの解放の戻し等）。
   ワーカーごとの計測値（`active_workers`）は行を分けてあり問題ない。

## 改修内容（測ってから、効くものだけ）

1. ルートのキャッシュの統計はワーカーごとに数え（`thread_local` の `Cell`）、読むとき（`stats()`）に合計する。`generation` は読み専用の
   行に分ける（書くのはリロードのときだけ）。
2. ルートの `Arc` を要求ごとに複製しない: 要求は最初に 1 回読んだ設定（`CURRENT_CONFIG.load()` のガード）を持っているので、
   ルートの値はその借用か、ルートの添字で引く。借用が `await` をまたげない箇所は、ワーカーごとの設定の写し（世代が変わったときだけ
   作り直す）を使い、参照カウントの書き込みをワーカーの中に閉じる。AGENTS.md の該当の規則（F-148/F-159）も「共有の `Arc` の複製も
   コア間の書き込みになる」に直す。
3. キャッシュの当たり・外れの数と接続の数はワーカーごとに数え、メトリクスの読み出し・上限の判定で合計する（`max_concurrent_connections`
   の判定に要る精度を確かめる。上限を厳密に守る必要があれば、ワーカーごとの割り当てに分ける）。
4. 5 の候補は `perf c2c` の結果で足す。

## 進捗（2026-11-25）

- 改修 1（ルートのキャッシュの統計）: LRU の本体は前から `thread_local` だったので、当たり・外れの数もスレッドの `TL_ROUTE_CACHE`
  （`TlRouteCache`）へ移した。共有の `RouteCache` に残るのは要求ごとに読むだけの `generation`（書くのはリロードのとき）。
  `stats()`・`OptimizedRouter::cache_stats()` は呼んだスレッドの値になる（読むのは試験と `Debug` だけ。メトリクスには出していない）。
- 改修 3 のうちキャッシュの当たり・外れの数（`file_cache`・`content_cache`・`compressed`）: `src/striped.rs` の `StripedCounter`
  （128 バイトにそろえた 64 本の行。スレッドは最初に足したときに行を割り当てられ、読むときに合計する）に替えた。
  `cache` feature の無いビルドでは作らない。

## 確かめ方（実装の前と後）

- **伸び方の試験**: aofish（16 スレッド。計測は WSL のロック `/tmp/vp-bench.lock` を取る）で、ワーカーを 1・2・4・8・12・16 本にして、
  `Respond` のルートの 1 要求あたりの CPU（`/proc/<pid>/task/*/schedstat`）を HTTP/1.1・パイプライン・h2c（`-m 100`）・静的配信で測る。
  共有の書き込みが原因なら、改修前はワーカーが増えるほど費用が上がり、改修後は平らに近づく。epoll と io_uring の両方のビルドで測る。
- `perf c2c`（aofish の特権の perf コンテナ）で、上の 1〜4 の行が HITM の上位に出るのを改修前に確かめ、改修後に消えたのを確かめる。
- 交互 A/B（ノート PC）で単発の費用が悪化しない。

## 受け入れ条件

- aofish で、`Respond` のルートの 1 要求あたりの CPU が、ワーカー 1 本と 12 本とで ±15% 以内（改修前の値も記録する）。
- メトリクス（`veil_*` の接続・キャッシュの当たりの数）の値が改修の前と同じ意味で読める。リロードでルートのキャッシュが入れ替わる試験
  （B-172・B-386）が通る。単体・統合・E2E（io_uring・epoll）。

## 期待する効果

- 64 コアの機械での Wasm を通らない経路の 1 要求の費用（veil-api の全プロファイル、veil の静的配信・`/pipeline`）。F-325 で
  エントリをハンドラの組み込みにするなら、veil の点に直接効く。どれだけ効くかは伸び方の試験で決まる（試算には入れていない）。
