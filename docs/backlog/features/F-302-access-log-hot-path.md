# F-302: アクセスログの要求ごとの費用を下げる（行の整形をログスレッドへ移す）

**状態: 完了（feat/v0120-perf、2026-11-08）**

親: [F-295](F-295-v0120-perf-harness.md)。要求事項には無いが、[F-299](F-299-python-gil-lane.md) の計測の途中で見つけた
（ライブラリはアクセスログが既定で有効なので、要求事項の Python の行もこの費用を含む）。

## 問題

F-299 で Python のハンドラの 1 要求あたりの CPU が下がると、アクセスログ（ライブラリの既定で有効。標準出力へ 1 要求 1 行）の
費用がスループットの 1 割を占めるようになった。端末（i5-3320M。サーバは CPU 0-1、veil-load は 2 スレッド・64 接続で CPU 2-3。
Python は offload=True・2 スレッド。5 ラウンドの交互の中央値）で、plaintext は有効 43,658・無効 49,234 req/s（−11%）、
サーバの CPU は 1 要求あたり 45.3・40.1 µs。[F-274](F-274-library-production-guide.md) の計測（Python のハンドラが遅かった頃）では
差はばらつきの範囲だった。

従来の経路（[B-335](../bugs/B-335-access-log-writer-wake-per-request.md) の後）は、要求ごとに次のことをしていた。

1. `CURRENT_CONFIG.load()` で設定全体を読む（1 回で 100 命令を超える。F-297）。
2. スレッドローカルのバッファへ JSON/テキストの行を整形する。
3. `to_vec()` で 1 行を確保して `SyncSender::try_send` でログスレッドへ送る。
4. ログスレッドが書いて解放する（確保したのとは別のスレッドでの解放）。

費用の内訳は、同じバイナリの中で段階を切り替えて測った（環境変数で段階を選ぶ一時的なビルド。端末、4 ラウンドの交互の中央値）。

| 段階 | plaintext | json | サーバ CPU/要求 |
|---|---:|---:|---:|
| 無効 | 48,828 | 46,772 | 40.0 µs |
| 有効、何もしない（時刻・UA の検索・UTF-8 の確認まで） | 47,489 | 45,080 | 41.5 µs |
| 行を整形して捨てる | 45,771 | 43,678 | 43.2 µs |
| 整形して `to_vec` して捨てる | 45,830 | 43,654 | 43.4 µs |
| 従来の全経路（チャネル・ログスレッドでの書き込みと解放） | 43,918 | 42,068 | 44.8 µs |

時刻の取得などで約 1.5 µs、整形で約 1.7 µs かかっていた。行の確保はほぼ 0 で、受け渡し（チャネル・別スレッドでの解放・書き込み）は
約 1.4 µs だった。整形の分は ITIMER_PROF の標本では 0.3 µs にしか見えない（インライン化された `log_access` の中）。命令の数より、
ホットパスに乗るコードの量（命令キャッシュ）として効いていると見ている。

## 対応

1. **受け渡し**: 要求を処理するスレッドごとの溜め（`Mutex<Pending>`）へ追記する。ログスレッドは要求が流れている間、1ms ごとに
   各溜めの中身を空のバッファと取り替える。錠を取り合うのは自分のスレッドとログスレッド（1ms に 1 回）だけで、ワーカーどうしは
   取り合わない。バッファは使い回すので、要求ごとの確保も別スレッドでの解放も無い。ログスレッドは静かになると眠り
   （`flush_interval_ms` まで）、次に追記したワーカーが起こす（`idle` の旗。流れている間は Relaxed の読み取り 1 回だけ）。
2. **整形をログスレッドへ移す**: ワーカーは 1 要求の値を、固定長の数値と長さ付きのバイト列からなる記録として写すだけにした
   （`put_record`）。ログスレッドが溜めを取り替えたあとに束ねて JSON/テキストへ整形する（`render_records`）。出力は従来と
   1 バイトも変わらない（UTF-8 でない値の代わりの `GET`・`-` も同じ）。時刻は要求を終えた時刻を記録に入れる。
3. **設定**: 要求ごとの `CURRENT_CONFIG.load()` をやめた。書式・項目は、ログスレッドが持つ `ArcSwap<AccessLogConfig>` を束ごとに
   1 回読む。送り先（`Sink`）はスレッドローカルに世代付きで控え、リロードで世代が変わったときだけ `ArcSwapOption` を引き直す。
4. **時刻**: 所要時間とログの時刻に使う `Instant::now()` を 1 回にした（`logging::coarse_now_at`）。

最初の版（受け渡し・設定・時刻だけで、整形はワーカーのまま）は +2.5%（plaintext）にとどまった。整形を移した第 2 版を採った（下の計測）。

## 挙動の変化

- `channel_size` は、要求を処理するスレッドごとの上限になった（従来はプロセスで 1 本のチャネルの容量）。ログスレッドが書けない間
  （標準出力のパイプを誰も読まない等）に溜められる行の数で、超えた行は従来どおり黙って捨てる。
- 別々のワーカースレッドの行は 1ms ほどの範囲で前後し得る（nginx の `access_log buffer=` と同じ性質）。1 つのワーカースレッドの行は
  順序どおり。
- リロードでは新しいログスレッドを起動する。旧ログスレッドは溜めを閉じ、溜まっていた行を書き切ってから終わる（従来も旧チャネルの
  残りを書いてから終わっていた）。閉じた溜めに書こうとしたワーカーは新しい送り先を引き直すので、切り替えでは行を落とさない。
- FreeBSD の capability mode でのリロード（F-178）は、ログスレッドの設定を差し替えて同じパスで開き直させる（従来どおり、スレッドは
  作り直さない）。

## テスト

`src/access_log.rs` の単体テスト（18 件）:

- `writer_keeps_every_line_across_batches`: 4 スレッド × 2,000 行がすべて書かれ、スレッドごとの順序が保たれる。
- `reload_moves_lines_to_the_new_writer_without_loss`: 3 スレッドが書き続ける間にリロードする。旧・新の両方のファイルに行があり、
  合計が欠けず、スレッドごとの順序が保たれる。
- `slot_drops_lines_beyond_limit_until_collected`: `channel_size` を超えた行を捨て、ログスレッドが取り替えたらまた溜める。
- `finished_thread_is_written_then_dropped_and_closed_sink_takes_nothing`: 終わったスレッドの溜めは書いてから外し、閉じた送り先は
  何も受けない。
- `records_render_to_the_same_lines_as_direct_formatting`: 記録から整形した行が、従来の直接の整形と一致する（JSON・テキスト・項目の
  絞り込み・UTF-8 でない値）。
- 既存の書式のテスト（JSON・テキスト・`type` の項目・エスケープ・絞り込み）はそのまま通る。

E2E は既存のものが経路を通る: `tests/api/library_e2e.sh`（既定でアクセスログが標準出力に出る・無効にすると出ない）、
`tools/qemu/bsd-security-e2e-guest.sh`（FreeBSD の capability mode でのログの移動と SIGHUP の開き直し）、container_security の
フィクスチャ（アクセスログ有効）。
