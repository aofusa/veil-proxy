# F-185: 接続・異常切断・設定リロードの反復でメモリ・fd が増え続けないかの試験（リーク試験）

**状態: 完了（feat/f185-memory-leak-check）**

## 目的

接続や設定のリロードを繰り返すたびにメモリ消費が増え続けないか（リークしていないか）を確かめる。F-183 の
ソーク（`alloc_soak.sh`）は RSS の底の推移しか見ておらず、アロケータが空き領域を保持・返却する揺れと、
生きているヒープの増加を区別できなかった。

## 追加したもの

### `tools/perf/leak_check.sh`（+ `leak_check_summary.py`・`leak_abort_client.py`）

veil を 1 プロセス起動したまま、シナリオごとに「操作 1 回分 → 静定待ち → 採取」を繰り返し、採取値を
サイクル番号に回帰した傾き（1 サイクルあたりの増分）で判定する。リークはサイクルごとに一定量ずつ増える。
プール・キャッシュが満ちる飽和型の増加は先頭の `WARMUP` サイクルで除く。

| シナリオ | 1 サイクルの操作 |
|---|---|
| `h1_churn` | HTTP/1.1 TLS、1 接続 1 要求 × 1000（静的 54KB / 3B / キャッシュ / プロキシを 4 分の 1 ずつ） |
| `h2_churn` | HTTP/2 TLS、1 接続 1 要求 × 1000（静的 / プロキシ） |
| `h2c_churn` | h2c → 上流プロキシ、1 接続 1 要求 × 1000 |
| `h3_churn` | HTTP/3、1 接続 1 要求 × 300 |
| `abort` | 異常切断 × 600（TCP 接続だけ・ClientHello 途中・要求ヘッダ途中・HTTP/1.1 / HTTP/2 / h2c の応答途中で RST） |
| `reload` | SIGHUP × 10（設定 a / b を交互に書き換え。ルート・LB 方式・アクセスログの出力先が変わる。証明書の mtime も更新）。HTTP/2 → 上流プロキシの負荷を流しながら |

採取する値: 生存ヒープのバイト数と数（下記）、veil-alloc の使用中スロット・セグメント・ヒープ数、RSS・匿名メモリ、
fd 数、スレッド数、アクティブ接続数。リロードはログの成功行の数で実際に行われたかを確かめる。

### `alloc-stats` の生存バイト数・生存アロケーション数

`alloc-stats`（診断専用・既定オフ）に解放バイト数を足し、`veil_alloc_live_bytes`（確保 − 解放）と
`veil_alloc_live_allocs`（allocs − deallocs）を公開した。RSS や veil-alloc の使用中スロットはアロケータの
保持・返却で揺れるが、これは「生きているヒープ」そのものなのでリークの判定に使える。

## 結果（Linux x86_64、io_uring、`full,alloc-stats`、ワーカー 2、静定 5 秒）

### 全シナリオ 30 サイクル（B-115〜B-117 修正後、run3）

傾きは先頭 5 サイクルを除いた 1 サイクルあたりの値。括弧内は除外後の最初 → 最後。

| シナリオ | 生存バイト | 生存アロケーション数 | RSS | fd | スレッド |
|---|---|---|---|---|---|
| h1_churn（3 万接続） | +5KB/c（34.0 → 34.1MB） | +1.1/c（2599 → 2630） | 38.8 → 38.5MB | 90 → 110 | 18 |
| h2_churn（3 万接続） | +9KB/c（44.3 → 44.4MB） | +0.1/c（2849 → 2852） | 63.7 → 67.8MB | 195 → 281 | 18 |
| h2c_churn（3 万接続） | +6KB/c（63.2 → 63.3MB） | +0.1/c（3325 → 3326） | 90.9 → 95.0MB | 793 | 18 |
| h3_churn（9000 接続） | +372KB/c（72.7 → 81.9MB） | 5164〜15922 で上下（下記） | 125.9 → 138.5MB | 795 | 20 |
| abort（1.8 万回） | −22KB/c（73.6 → 72.5MB） | −0.3/c（3069 → 3053） | 120.2 → 114.3MB | 296 | 20 |
| reload（SIGHUP 300 回） | −56KB/c（71.0 → 69.4MB） | −0.9/c（3238 → 3214） | 115.7MB（横ばい） | 73 → 63 | 20 |

- 設定リロード 300 回・証明書リロード 300 回がすべて成功（ログの成功行で確認）。全シナリオで要求の失敗 0、
  異常切断の各種類はサーバが応答を返し始めてから切っている（`leak_abort_client.py` の集計）。
- fd の増加は上流（nginx）への接続プールで、後のシナリオでアイドル接続の回収により減る（h2c の 793 本 → 63 本）。
  スレッドは HTTP/3 の負荷を始めたときに 18 → 20 になり、以後は増えない。
- HTTP/3 の生存アロケーション数は、採取時点で残っている QUIC 接続（アイドルタイムアウト 30 秒 > 静定 5 秒）の
  数で上下する。底（5164）はサイクル 7〜24 で一定で、次の abort シナリオでは 3069 まで戻る。生存バイトの段階的な
  増加は接続表のハッシュ表の容量の倍増（下記）。

### 長時間（修正前のバイナリ、run2: 各 100 サイクル）

- リロード 1000 回・証明書リロード 1000 回: 生存アロケーション数 2484 → 2499 で横ばい。生存バイトは 36.0 → 48.5MB で、
  増分はすべて B-117 のタイマーヒープの倍増（ワーカー 2 本で 1 回ずつ +6MB）。
- HTTP/1.1 チャーン 10 万接続: 生存バイト 60.2 → 60.3MB、生存アロケーション数 2929 → 2880（減少）。

### LeakSanitizer（B-116 修正後の `e2e_sanitizer_chaos.sh`、ASAN ビルド）

HTTPS・HTTP の並列チャーン 60 秒 + SIGHUP 3 回 + 追加チャーンのあと SIGTERM で終了コード 0、リークの報告なし
（`LSAN_OPTIONS=verbosity=1` で全スレッドの走査を確認）。sanitizer ビルドの feature は http3・wasm を含まない。

### 増え続けないが、ピーク時の大きさを保持するもの

- io_uring のタイマーヒープ（B-117 で修正）。
- HTTP/3 の接続表（`HashMap<ConnectionId, Http3Handler>`）: 1 エントリに数 KB のハンドラを値で持つため、同時接続数の
  ピークに合わせて表が 1 → 2 → 4 → 8 → 16MB（ワーカーあたり）と倍増し、接続が減っても縮まない。60 サイクルの
  トレースではサイクル 20 以降は増えず、上限はある（F-186 で改善を検討）。

## 見つかった不具合

- **B-115**: SIGTERM で graceful shutdown しなかった（最初のコミットから。ネイティブは即終了、コンテナの PID 1 では
  無視されて `docker stop` は SIGKILL まで待っていた）。sanitizer 試験で終了を待つようにして発覚。
- **B-116**: E2E sanitizer カオスの LeakSanitizer が一度も走っていなかった（終了を待たずにログを見ていた。
  終了しても veil の seccomp・Landlock・特権降格が LeakSanitizer の ptrace を妨げていた）。
- **B-117**: io_uring のタイマーヒープがキャンセル済みエントリで「要求レート × タイムアウト」まで膨らむ
  （リロードのシナリオで生存バイトが +6MB ずつ跳ねたのを、確保元のバックトレースで特定）。
- **B-118**: graceful shutdown の待ちが切れて接続が残っていると終了時に abort（コアダンプ）していた（B-115 の確認中に
  キープアライブ接続を残して SIGTERM を送って発覚）。
- 関連して、graceful shutdown がアイドルなキープアライブ接続も待つ件を F-187、HTTP/3 の接続表のピーク保持を F-186 として起票。
