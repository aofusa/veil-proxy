# F-336: `proxy_on_log` で応答のステータスとヘッダを見せる（全経路。Envoy 互換）

**状態: 未着手（[F-329](F-329-wasm-single-fiber-entry-per-request.md) から分けた。2026-11-26）**

## 現状

- `proxy_on_log` の context は、段の間の `recycle` の後に要求の属性（`set_request_attrs`: `:authority`・`:scheme`・プロトコル・
  メソッド・パス）だけを入れ直したもの。応答のステータス（`response.code`・`:status`）は 0、応答ヘッダは空。要求のそれ以外のヘッダ・
  本文・クライアントのアドレス（`source.address`）も見えない。プロキシした応答・ローカル応答・veil が返したエラー（502 等）のどれでも同じ。
- Envoy の `onLog` は、応答のステータスとヘッダ・トレーラ、要求ヘッダ、接続の属性を見せる（応答ヘッダは読み取りだけ。
  `source/extensions/common/wasm/context.cc`）。アクセスログ・メトリクスを `proxy_on_log` で書く Envoy 向けのフィルタは veil では
  ステータスが 0 になる。
- F-329 はローカル応答の要求のログの段を要求の段に続けて呼ぶ（1 モジュール・`instance_reuse`）。そこだけ見せるとモジュールの数や
  `instance_reuse` で見え方が変わるので、見え方は今の経路と同じにした（`docs/artifacts/proxy-wasm-perf/gemini/ans-06-design-F-329.md` の
  5-0・5-1）。

## 案（実装の前に設計を詰める）

1. **ステータス**: 要求の並び（`RequestSessions`）に `Cell<u16>` を持ち、ローカル応答を決めたとき（エンジン）・応答ヘッダの段（エンジン。
   段の無いルートはプロトコルの側で応答の頭を作るとき）・veil が返すエラー（プロトコルの側）で置く。ログの段の context に入れる。
   要求ごとの確保は無い。
2. **応答ヘッダ**: ローカル応答は、ヘッダを `std::mem::swap` で context へ貸し、ログの段の間は応答ヘッダの表への書き込みを
   `BadArgument` にする（`response_headers_read_only`。Envoy も読み取りだけ）。呼んだ後に戻す（トラップでも）。プロキシした応答は、
   応答の段の後もヘッダを残すか写すかの費用を測ってから決める（写すなら要求ごとの確保が増える。ログの段を持つモジュールだけにする等）。
3. **要求ヘッダ・クライアントのアドレス**: 同じ考え方で、ログの段を持つモジュールだけに見せるかを決める。
4. 見せる値はモジュールの数・`instance_reuse`・プロトコル・F-329 の経路に関わらず同じにする。

## 受け入れ条件

- `proxy_on_log` から、プロキシした応答・ローカル応答（ヘッダの段・本文の段・応答ヘッダの段・外部呼び出しの応答で決めたもの）・veil の
  エラー応答のステータスが、HTTP/1.1・HTTP/2・HTTP/3、1 モジュールと 2 モジュール、`instance_reuse` の有無のどれでも見える（E2E）。
- 応答ヘッダを見せるなら、ログの段で書き換えても送る応答は変わらない。
- ログの段を持たないモジュールのルートの 1 要求の費用が変わらない（交互 A/B）。
- ガイド（英日）の Proxy-Wasm の章の「`on_log` から見える値」を直す。
