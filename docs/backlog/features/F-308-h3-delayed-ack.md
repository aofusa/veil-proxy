# F-308: HTTP/3 の要求のパケットへの ACK を応答に載せる（ACK の遅延）

**状態: 見送り（feat/beat-nginx、2026-11-14。交互 A/B で効果が無く、1 接続 1 ストリームでは遅くなった）**

## 背景

F-307 の計測（lab43、aofish、h2load-h3 `-c100 -m10`、54KB）で、1 要求あたりにサーバが送るデータグラム（GSO の束）が
nginx 1.11〜1.12 に対して veil 1.43〜1.51 だった。quiche は ACK を求めるパケットを受け取ると次の `send()` で必ず ACK を
作るので、上流を待つ中継では要求のパケットごとに ACK だけのデータグラムを送っているのではないかと考えた（nginx は
1-RTT の ACK を、ACK を求めるパケットが 2 つ溜まるか `max_ack_delay` が過ぎるまで待たせる。`ngx_quic_generate_ack`）。

## 試したこと

vendoring の quiche に `Config::enable_delayed_ack` を足した（RFC 9000 §13.2: 前の ACK から最初の、順番どおりに届いた
パケットだけ ACK を通知した `max_ack_delay` まで待たせ、2 つ目・穴の後・入れ替わりは今すぐ。期限は `timeout_instant()`
に入れる）。veil は `[http3] delayed_ack` で使う。quiche の上流の試験は変更の前後で同じ 75 件が失敗（aws-lc で証明書を
置いたときの既知の失敗）、追加した端から端までの試験（1 要求は待ち、応答に載り、2 つ目で今すぐ、期限で単独）は通った。
差分は消したので、再び試すときはこの節を起点に作り直す。

## 計測（aofish、同じバイナリで `delayed_ack` を切り替え、交互に 3 回、中央値）

| 条件 | 指標 | 無効 | 有効 | nginx |
|---|---|---|---|---|
| 中継 `-m10`（lab44） | rps | 32,313 | 31,926 | 31,852 |
| | データグラム/要求 | 1.42 | 1.39 | 1.13 |
| 溜める中継 `-m10`（lab44） | rps | 30,856 | 31,090 | — |
| 静的 `-m10`（lab44） | rps | 40,712 | 39,884 | 41,043 |
| 中継 `-m1`（lab45） | rps | 24,742 | 23,356（−5.6%） | 25,684 |
| | データグラム/要求 | 3.23 | 3.19 | 2.04 |
| | サーバの CPU µs/要求 | 287.8 | 297.0 | 260.6 |

- `-m10` では 1 接続に 10 本の応答が流れ続けるので、ACK はもともと応答のデータに載っていた（0.02〜0.03 しか減らない）。
- `-m1` では、クライアントの窓の更新（ACK を求める）と次の要求で「2 つ目」になり、待たせても ACK だけのデータグラムは
  残る。要求の ACK を待たせた分だけ遅くなった。
- nginx との差（`-m1` で 1 要求あたり約 1 データグラム）の原因は ACK ではなく、応答の最後の短いパケットを GSO の束から
  外して別に送っていたこと（lab47 の tcpdump で確認。F-309）。中継では nginx も要求ごとに ACK だけのパケットを送っている。

## 結論

採らない（差分を外した）。`-m10` の差は輻輳制御の設定でも縮まらなかった（lab45: `hystart = false` 30,811 rps・1.44、
`cc_algorithm = "reno"` 31,820・1.29、`pacing = false` 32,091・1.42、既定 31,434・1.43、nginx 30,785・1.12。どれも
揺れの内側）。
