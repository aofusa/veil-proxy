# F-151: HTTP/3 メインループの全接続スイープ排除（イベント駆動化）

- 優先度: P1
- 状態: 対応中
- 関連: `docs/perf/README.md`「残存ボトルネック（未対応）」の 2 件目、F-32、F-115、F-129、F-130、B-12

## 背景（何を解こうとしているか）

`docs/perf/README.md` の FreeBSD ネイティブ計測で **未対応として残っていた 2 件**のうちの 1 件:

> **HTTP/3 が nginx 比 0.5 倍**（veil 5,869 / nginx 11,665 rps）。データグラム syscall
> 律速ではない（上限見積り 37,000 rps に対し両者ともはるかに低い）ため、
> QUIC の暗号処理・輻輳制御側の調査が必要。

「syscall 律速ではない」ところまでは実測で確定している。本チケットは
**残る候補のうち、コードリーディングで機構的に確実に存在すると特定できたコストである
「1 イテレーションあたり全接続を何度もスイープする構造」** を潰す。

## 事前実験（実装前に仮説を確定させた）

詳細は [`docs/artifacts/f151_h3_loop_scaling_experiment.md`](../../artifacts/f151_h3_loop_scaling_experiment.md)。
Linux x86_64 / io_uring / ホスト loopback で実施。

1. **接続数スケーリング**: 1〜32 接続では約 3,200 rps で頭打ち（接続数非依存）だが、
   **64 を超えると急落し 128 接続で 1/3（約 950 rps）**になる。昇順・降順の両方向で再現。
2. **cc/pacing の A/B**（`bbr`+pacing vs `cubic`+pacing 無効、c=8 で 3 ラウンド交互）:
   **有意差なし**。`docs/perf/README.md` に書かれていた「QUIC の暗号処理・輻輳制御側の
   調査が必要」という当初の仮説を**計測が否定した**。
3. **クライアント律速でないことの確認**: `h3load` 2 プロセス並走で合計 3,390 rps
   （単一時と同水準）＝ サーバ側が上限。
4. **決定的な実験 — `mmsg_batch_size` の A/B（c=128、交互 2 巡）**:
   `8` → 577 / 680 rps、`128` → 2,049 / 2,006 rps。**バッチ 16 倍でスループット 3.2 倍**。
   トラフィック量・暗号処理量・輻輳制御は同一で、**変わったのはループイテレーション回数だけ**。

→ 高接続数での劣化は **1 イテレーションあたりの O(N_conn) 固定費**であることが確定した。

## 調査（コードリーディングで特定した事実）

`src/http3_server.rs` の HTTP/3 メインループは、**1 イテレーションごとに接続マップ
（`ConnectionMap`）の全要素を最大 6 回走査**している。

| # | 箇所 | 内容 | 実行条件 |
|---|---|---|---|
| 1 | タイムアウト算出 | 全接続の `conn.timeout()` の最小値を取る | 毎回 |
| 2 | タイムアウト処理 | 全接続に `conn.on_timeout()` | 毎回（期限切れ接続が 0 件でも） |
| 3 | 受信後の送出 | `send_pending_packets` = 全接続に `conn.send()` | パケット受信時 |
| 4 | H3 イベント処理 | 全接続に `init_h3` + `handle_writable_streams` + `process_h3_events` | 毎回 |
| 5 | ストリーム駆動 | 全接続に `drive_proxy_streams` | 毎回 |
| 6 | 末尾の送出 | `send_pending_packets` = 全接続に `conn.send()` | 毎回 |

つまり **接続数 N・イテレーション数 I に対して O(N × I)** の固定費が乗る。
1 接続にパケットが 1 通届くだけで、他の N-1 接続すべてに対して
`on_timeout` / `poll` / `send` を呼び出す。しかも `send_pending_packets` は
**パケット受信時には 1 イテレーションで 2 回**呼ばれる（#3 と #6）。

計測ハーネス（`tools/perf/freebsd/run_perf_freebsd.sh`）の既定は
**64 コネクション**、Docker 側の HTTP/3 計測も `-c100` であり、
まさにこの固定費が効く領域で測っている。

`process_h3_events` を毎イテレーション呼ぶこと自体は B-12（h3 イベントが
`poll()` でしか取り出せず、パケット到着時のみの poll だとデッドロックする）の
修正で意図的に入れたものであり、**「呼ぶ頻度」ではなく「呼ぶ対象」を
絞る**必要がある（B-12 を再発させない）。

## 改修内容

接続ごとに「次に何かする必要があるか」を管理し、**必要な接続だけを触る**。

### 1. ダーティ集合（`dirty: VecDeque<ConnId>` + `Handler::dirty: bool`）

以下のいずれかが起きた接続だけをダーティにする。

- そのイテレーションでデータグラムを受信した（`process_datagram_segments` 内で印付け）
- バックエンドタスクがレスポンス断片を積んだ（後述の per-connection 通知）
- quiche のタイマー期限が到来した
- 前回の処理で「まだ送り残し／進め残しがある」と判定された
  （`send` が `Done` を返さなかった、`drive_proxy_streams` が部分送信で止まった 等）

`Handler::dirty` フラグで多重登録を防ぐ（`VecDeque` は最大 N 要素）。

**B-12 の不変条件**: 「H3 イベントが滞留したまま誰も poll しない」状態を作らないこと。
これは上記 4 条件が「quiche/h3 が新しいイベントを生成しうる契機」を網羅していることで
担保する。加えて、`process_h3_events` / `drive_proxy_streams` が
**1 件でも仕事をしたら再度ダーティのまま残す**（`Done` を見るまで降ろさない）ことで、
「イベントが残っているのにダーティを降ろす」経路を構造的に排除する。

### 2. タイマーの最小ヒープ（`BinaryHeap<Reverse<(Instant, ConnId)>>`）

`conn.timeout()` の最小値を求めるためだけの全走査（#1）と、
期限が来ていない接続まで `on_timeout` する走査（#2）を廃止する。

- 各接続の処理後に `conn.timeout_instant()` をヒープへ push（遅延削除方式。
  pop 時に接続マップの現在の期限と一致しなければ捨てる）。
- ループ先頭では **期限が到来したエントリだけ** pop して `on_timeout` + ダーティ化する。
- `select` の sleep 時間はヒープ先頭の期限から算出する（従来と同じ意味）。

### 3. 送出スイープの単一化とダーティ限定化

`send_pending_packets` を **ダーティ接続だけを走査**する形に変え、
1 イテレーション 1 回（末尾）に統一する。受信直後の呼び出し（#3）は削除する
（同一イテレーション内で末尾の呼び出しが必ず走るため、送出が遅れることはない）。

sendmmsg / io_uring SENDMSG のバッチ構築ロジック（F-115 第 2 段・F-130）は
**一切変更しない**。走査対象の集合が変わるだけで、バッチの組み方・順序・
GSO セグメント分割の判定は現行と同一である。

### 4. バックエンド通知の per-connection 化

現在は 1 本の `Notify` でメインループを起こすだけで、
「どの接続が進んだか」が分からないため全接続を駆動している。
`ProxyStream` の生成時に接続 ID を持たせ、バックエンドタスクが
`Notify` を叩く前に共有の wake キュー（`Rc<RefCell<VecDeque<ConnId>>>`）へ
自接続 ID を積む。メインループはそれを排出してダーティ集合へ入れる。

## 期待効果

1 イテレーションあたりの接続走査回数が **最大 6N → 実際に仕事のある接続数のみ** になる。
`-c64`／`-c100` の計測条件では、パケット 1 通の処理に伴う無駄な
`on_timeout` / `poll` / `send` 呼び出しが **数十〜数百回 → 0 回** になる。

## 併せて実施する計測（設定チューニング）

事前実験 2 により **`cc_algorithm` / `pacing` は小レスポンスのスループットに
有意差を与えない**ことが Linux で確定したため、既定（`bbr` + pacing）は変更しない。
FreeBSD 実機では大レスポンス（54KB）でも同じかを確認するに留める。

`mmsg_batch_size` は事前実験 4 のとおり**現状はループ固定費を隠すためのパラメータとして
効いている**（本チケットの改修でその依存が消えるはず）。改修前後で同じ A/B を取り、
「バッチ幅を変えてもスループットが動かない」＝固定費が消えたことの確認に使う。

FreeBSD には `sendmmsg`/`recvmmsg`・UDP GSO が無く 1 データグラム 1 `sendto` に
なるため、Linux（GSO + io_uring SENDMSG バッチ）で最適だった既定が
FreeBSD でも最適とは限らない。

## テスト

- 単体: ダーティ集合の登録・重複排除・降格条件、タイマーヒープの遅延削除
  （期限更新後に古いエントリが来ても誤って `on_timeout` しないこと）。
- 統合: 多接続（≥ 32）で 1 接続だけにトラフィックを流したとき、
  他接続が処理対象に入らないこと（カウンタで検証）。
- E2E（`full` および `full,epoll`）: 既存の HTTP/3 シナリオ全件に加え、
  **B-12 の再発検出**（GREASE フレーム込みの fin・ストリーミングボディ・
  リクエストボディ大容量）を明示的に含める。
