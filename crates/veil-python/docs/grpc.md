# gRPC (`veil.grpc`)

veil does not depend on message serialisation; you choose protobuf, betterproto, JSON and so on. There are two
layers.

## Plain layer (no dependencies)

The decorators take the same argument names as grpcio:

```python
import veil, veil.grpc
from demo_pb2 import HelloRequest, HelloReply

@veil.grpc.unary_unary("/demo.v1.Demo/SayHello",
                       request_deserializer=HelloRequest.FromString,
                       response_serializer=HelloReply.SerializeToString)
def say_hello(request, context):
    return HelloReply(message="Hello " + request.name)

veil.grpc.add_health()                            # grpc.health.v1.Health
veil.run(listen_cleartext="127.0.0.1:50051")
```

`unary_stream`, `stream_unary` and `stream_stream` have the same form; streaming input is an iterator and
streaming output an iterator or generator. Without the serializer arguments messages are passed as `bytes`.
`async def` functions and async generators work.

## grpcio layer

With `pip install "veil-api[grpc]"`, code generated by `grpc_tools.protoc` runs unchanged:

```python
server = veil.grpc.Server()
demo_pb2_grpc.add_DemoServicer_to_server(MyServicer(), server)
server.add_insecure_port("127.0.0.1:50051")
server.start(); server.wait_for_termination()     # = veil.run(listen_cleartext=...)
```

The `context` has the main parts of grpcio's `ServicerContext` (`abort`, `abort_with_status`, `set_code`,
`set_details`, `invocation_metadata`, `send_initial_metadata`, `set_trailing_metadata`, `time_remaining`,
`is_active`, `peer`). Status codes may be `grpc.StatusCode` or {py:class}`veil.grpc.StatusCode`.

For TLS (HTTP/2 and HTTP/3) use `app.run(listen=..., tls_cert=..., tls_key=...)`; there is no
`add_secure_port`. Compression, deadlines, gRPC-Web and the `[api] grpc_*` settings are the same as for Rust
handlers.

Example: `examples/api/python-grpc/` in the repository (`VEIL_GRPC_MODE=grpcio|plain`).
